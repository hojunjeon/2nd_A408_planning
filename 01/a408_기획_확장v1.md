# 📄 [기획서] 사회초년생 & 청년 맞춤형 혜택 & AI 자산 케어 모바일 플랫폼: 셋업 (Setup)

## 1. 프로젝트 개요 (Overview)

* **프로젝트명**: **셋업 (Setup)** - 청년층(대학생·취준생·사회초년생)을 위한 AI 기반 **정책·세제·부채 통합 금융 자립 내비게이션**
* **팀 구성 및 R&R (총 6인)**:
  * **Frontend (2명)**: React Native / TypeScript 기반 **Android 전용** 모바일 앱, 정책·세제 로드맵·부채 대시보드·증빙 체크리스트 UI 개발
  * **Backend (2명)**: Spring Boot / Java 기반 RESTful API 서버, 정책·세법 버전 관리, 결정론적 Rule Engine, 할부·대출 상환 계산기, Database 설계
  * **AI · Data (2명)**: 공고문·세법 안내문 구조화, Agentic RAG, 정책 변경 감지, SMS/PUSH 문맥 파싱, 규칙 추출 품질 검증

* **타겟 사용자**: **20대~30대 청년층 전반 (대학생, 취준생, 비정기 소득 알바생, 사회초년생 직장인)**
  * *Unearned / Low-Income Thin-Filer (고정 소득이 없거나 금융 이력이 부족해 정책·세금·부채 관리 정보가 특히 부족한 청년층)*

* **핵심 미션**:
  1. 파편화된 **청년 정책 지원금과 세제 혜택을 하나의 타임라인으로 결합**하고, 자격·중복 제한·신청 기간·증빙을 근거와 함께 안내
  2. 정책 지원금뿐 아니라 **월세 세액공제, 중소기업 취업자 소득세 감면, 주택자금·청약 소득공제, 학자금대출 상환 교육비 세액공제**까지 포함한 연간 실수령 혜택 극대화
  3. 카드 할부와 학자금·신용·전세 등 대출을 하나의 부채 원장으로 통합해 **총 금융비용·월 상환액·중도상환 순편익·유동성 위험**을 비교
  4. LLM은 공고문을 읽고 설명하는 역할로 제한하고, 자격 판정과 금액 계산은 **출처·적용일·수식이 명확한 결정론적 Rule Engine**이 수행

## 2. 문제 정의 및 해결 방안 (Problem & Solution)

### 🔴 Problem (기존 서비스의 한계)

1. **청년 정책과 세제 혜택이 서로 다른 시점·기준으로 분리됨**:
정책 서비스는 지원금 신청만, 연말정산 서비스는 세금 공제만 보여주는 경우가 많다. 그러나 실제 청년의 가처분소득은 **정책 지원금 + 세금 감면·공제 + 금융비용 절감**의 합으로 결정된다. 같은 월세 지출도 신청 기간에는 청년월세지원 대상인지, 연말에는 월세액 세액공제 대상인지, 전세자금대출을 이용했다면 원리금 상환액 소득공제 대상인지 따로 판단해야 한다.

2. **자격 기준·중복 제한·증빙 기준의 혼동**:
정책마다 나이, 거주지, 졸업 여부, 취업 상태, 가구·개인 소득, 재산, 지원 이력, 신청 기간의 기준일이 다르다. 세제 혜택도 총급여, 무주택 여부, 세대주·세대원, 계약자·납부자 명의, 전입 여부, 회사·업종 요건을 함께 본다. 단순 키워드 추천은 이런 **기준일과 증빙의 차이**를 놓쳐 실제 신청 단계에서 탈락하기 쉽다.

3. **소득 SMS만으로는 정책상 공식 소득을 확정할 수 없음**:
급여·입금 문자는 현금 흐름을 빠르게 보여주지만, 정책이 판단하는 소득은 건강보험료, 국세청 확정소득, 최근 소득, 가구원 소득 등 사업별 산정방식이 다르다. 따라서 문자 합계만으로 “자격 박탈 확정”을 안내하면 오히려 잘못된 행동을 유도할 수 있다.

4. **할부와 대출을 별개로 관리하여 총 금융비용이 보이지 않음**:
노트북·학원비·교재비 카드 할부, 학자금대출, 전세대출, 비상금대출은 모두 미래 현금 흐름을 잠식하지만 서로 다른 앱과 명세서에 흩어져 있다. 사용자는 월 납입액만 보고 선택하며 **총이자, 할부수수료, 중도상환수수료, 금리 변동, 만기 집중 위험**을 함께 비교하기 어렵다.

5. **공시 금리와 실제 승인 조건의 차이**:
공식 비교공시의 금리는 탐색에는 유용하지만 실제 한도·금리는 신용도, 소득 인정, 기존 부채, 담보, 금융회사 심사에 따라 달라진다. 프로젝트가 승인 가능성을 확정하거나 특정 대출을 중개하는 순간 데이터·규제·책임 범위가 급격히 커진다.

### 🟢 Solution (셋업의 차별화된 해결책)

1. **청년 정책 + 세제 혜택 통합 로드맵 Engine**:
유저의 나이, 지역, 취업·재학 상태, 총급여·소득 구간, 가구, 주거 형태, 임대차·대출 정보를 분석하여 **신청 가능한 정책, 연말정산 혜택, 필요한 증빙, 다음 행동 시점**을 하나의 연간 타임라인으로 제공한다. 중복 제한은 “우회”하지 않고 **공고문을 준수하면서 조건부 중복·선후 관계를 판정**한다.

2. **Expected Benefit(예상 순혜택) 중심 우선순위**:
단순히 지원금 액수가 큰 순서가 아니라 다음 식으로 행동 우선순위를 계산한다.

$$
\text{Action Score}
= \text{예상 순혜택}
\times \text{자격 신뢰도}
\times \text{마감 긴급도}
- \text{유동성 위험}
- \text{증빙 공백 패널티}
$$

* **예상 순혜택**: 지원금 + 예상 세금 절감 + 회피 이자·수수료 - 신청·중도상환·대환 비용
* **자격 신뢰도**: 확인된 공식 데이터와 자기입력 데이터의 비율, 공고문 규칙 추출 검수 여부
* **마감 긴급도**: 신청 종료일, 서류 발급 소요시간, 계좌개설 기간 반영
* **유동성 위험**: 중도상환 후 비상자금 부족, 다음 달 필수지출 부족 가능성

3. **Tax Calendar & Evidence Locker**:
연말정산 직전에 한꺼번에 찾는 방식 대신, 월세 이체증·임대차계약서·주민등록등본·중소기업 감면신청서·주택자금 상환증명서·학자금대출 상환내역을 혜택별로 연결한다. 앱은 “가능/불가능”만 말하지 않고 **누락된 증빙과 제출처**를 표시한다.

4. **Installment & Loan Liability Optimizer**:
카드 할부와 대출을 공통 원장으로 관리하고, 원리금균등·원금균등·만기일시상환 방식별 현금 흐름을 계산한다. 중도상환 또는 대환은 단순 금리 차이가 아니라 **회피 이자 - 중도상환수수료 - 부대비용 - 유동성 손실**로 비교한다.

5. **Evidence-Linked AI 설명**:
모든 추천 카드에 `근거 출처`, `기준일`, `확인된 조건`, `추가 확인 조건`, `최종 판단 기관`을 표시한다. 정책·세제·대출의 세계에서 “AI가 그렇다고 했다”는 증빙 서류가 되지 않으므로, 설명 가능성이 기능의 일부가 된다.

#### 💡 실제 예시로 보는 '정책 + 세제 + 부채 로드맵' 알고리즘

> **[상황 1: 무소득/비정기 소득 대학생 B양 (만 22세, 서울 자취, 알바 수입 월 60만 원)]**
> * **기준일**: 2026년 8월 24일
> * **기존 서비스의 문제**: “청년월세지원 가능”이라는 일반 정보만 보여주지만, 2026년 신청기간은 3월 30일~5월 29일이므로 현재 신규 신청은 종료된 상태이다. 재학 중이므로 서울시 청년수당의 최종학력 졸업 요건도 충족하지 않는다.
> * **셋업(Setup)의 추천 로드맵**:
>   1. **즉시**: 2026년 청년월세지원은 `신청 마감`으로 표시하고, 다음 정기 모집·지자체 월세사업 공고 알림을 예약한다. “상시사업”과 “연중 신청 가능”을 혼동하지 않는다.
>   2. **학기 중 자금 필요 시**: 2026학년도 2학기 한국장학재단 학자금대출의 신청기간·금리·한도를 공식 공고 기준으로 안내하고, 고금리 카드 할부와 총비용을 비교한다. 대출은 필요한 금액만 입력하도록 제한한다.
>   3. **세제 혜택**: 현재 근로소득세 납부액이 거의 없다면 월세액 세액공제의 즉시 실익이 작을 수 있음을 설명한다. 대신 임대차계약서·전입·월세 이체증을 보관하고, 취업한 연도의 실제 공제 가능성을 다시 계산한다.
>   4. **졸업 시점**: 서울시 청년수당·국민취업지원제도 등은 그해 공고의 졸업·취업·중복 조건을 다시 불러와 비교한다.
>
> * 🎯 **결과**: “이미 마감된 지원금 신청”이라는 헛걸음을 막고, 당장 필요한 학비·생활비는 저비용 수단부터 비교하며, 향후 세제 증빙까지 이어지는 **시간축 기반 의사결정**을 제공한다.
>

>   2. **월세액 세액공제 검토**: 총급여 5,500만 원 이하이고 무주택·전입·계약·납부 명의 요건을 충족한다고 가정하면, 연 월세 720만 원 × 17% = **122만 4천 원**의 공제 후보액을 계산한다. 다만 중소기업 소득세 감면 적용 후 남은 결정세액에 따라 실제 환급액은 줄어들 수 있음을 함께 표시한다.

>   4. **대출 최적화**: 기존 신용대출 1,000만 원, 연 8%, 36개월 원리금균등을 입력하면 월 상환액 약 **313,364원**, 총이자 약 **1,281,092원**을 산출한다. 같은 잔여기간·원금에서 연 6% 조건이 실제로 가능하다고 가정할 때 총이자는 약 **951,897원**으로 줄지만, 대환 수수료·중도상환수수료·심사 결과를 차감한 순편익으로 판단한다.
>
> * 🎯 **결과**: 지원금 추천에 그치지 않고 **예상 세금 절감 + 저축 기여금 + 대출비용 절감**을 하나의 연간 순혜택으로 비교한다.

> * **잘못된 접근**: 카드 할부를 무조건 먼저 갚거나, 금리가 더 낮다는 이유만으로 비상금대출을 늘려 할부를 상환한다.
> * **셋업(Setup)의 판단 순서**:

>   2. 비상금대출의 실제 금리·상환방식·중도상환수수료와 카드 할부의 잔여 수수료를 같은 날짜 기준 현금흐름으로 변환한다.
>   3. 상환 후 1개월 필수지출과 최소 비상자금이 유지되는지 확인한다.
>   4. 절감액이 양수이고 유동성 안전조건을 만족할 때만 `상환 고려`로 안내하며, 카드사·금융회사에서 최종 상환금액을 확인하도록 연결한다.
>
> * 🎯 **결과**: “금리 숫자 하나”가 아니라 **총비용과 생존 가능한 현금 잔액**을 함께 최적화한다.
>
> ※ 예시는 2026년 8월 24일 기준 공식 안내와 가정값을 구분해 작성하였다. 정책 신청기간·세율·상품조건은 적용연도와 공고가 바뀔 수 있으므로 앱 화면에는 반드시 기준일과 원문 링크를 표시한다.

## 3. 핵심 AI 기능 상세 명세 (Core AI Features)

### 🤖 ① [Agentic RAG] 공공 공고문 자동 파이프라인 & Layout-Aware 구조화

* **공식 출처 우선 수집 파이프라인 (Data Pipeline)**:
* Spring Boot Batch가 온통청년 OPEN API의 정책 메타데이터와 중앙부처·지자체 공식 공고 URL을 주기적으로 확인한다.
* 온통청년 API는 회원가입·인증키 신청·담당자 승인이 필요하며, HTTPS/XML 규격으로 제공된다. 키 발급 전에는 동일 스키마의 fixture/mock 데이터로 파이프라인을 검증한다.
* 공고 상세 페이지의 첨부파일은 **PDF → HWPX → HWP** 순으로 파싱 경로를 분기하고, 원문 파일의 해시값·수집시각·게시기관·공고기간을 함께 보관한다.
* 세제 규칙은 국세청 안내와 국가법령정보센터의 현행 법령을 우선 사용하고, 정책 보도자료만으로 세액 규칙을 확정하지 않는다.

* **Layout-Aware Parser + Rule Compiler**:
* LlamaParse/Unstructured 등으로 표·각주·신청기간·제외조건을 구조화하되, LLM의 추출 결과를 곧바로 판정에 사용하지 않는다.
* 추출 결과는 JSON Schema 검증 후 다음 구조로 변환한다.

```json
{
  "ruleId": "TAX_MONTHLY_RENT_2026",
  "ruleType": "TAX_CREDIT",
  "effectiveFrom": "2026-01-01",
  "effectiveTo": "2026-12-31",
  "sourceUrl": "https://www.nts.go.kr/...",
  "conditions": [
    { "field": "totalSalary", "op": "LTE", "value": 80000000 },
    { "field": "isNoHousehold", "op": "EQ", "value": true },
    { "field": "leaseAddressMatched", "op": "EQ", "value": true }
  ],
  "calculation": {
    "baseCap": 10000000,
    "rateBands": [
      { "maxSalary": 55000000, "rate": 0.17 },
      { "maxSalary": 80000000, "rate": 0.15 }
    ]
  },
  "reviewStatus": "HUMAN_VERIFIED"

```

* **품질 게이트**:
1. 원문 URL·시행일·마감일이 없으면 `추천 불가`
2. 금액·나이·소득 기준이 원문과 이중 대조되지 않으면 `확인 필요`
3. 새 공고와 기존 규칙의 Diff가 발생하면 자동 배포하지 않고 리뷰 큐로 전송
4. 화면에는 `확정 적격` 대신 `예상 적합 / 예상 부적합 / 추가 확인 / 마감`의 4단계 상태 사용


### 🤖 ② [Policy + Tax Orchestrator] 청년 정책·세제 통합 판정 Engine

### 🤖 ③ [할부 최적화 Agent] 실시간 수수료 절감 & 상환 스케줄러

* **기존 단일 수식의 한계**:
카드 할부수수료는 카드사, 회원 등급, 이용기간, 회차, 무이자·부분무이자 조건에 따라 달라질 수 있다. 따라서 모든 카드에 하나의 연이율 수식을 적용해 정확한 수수료라고 표시하지 않는다.

* **검증 가능한 계산 방식**:

$$
\text{잔여 할부비용}
= \sum_{k=\text{다음 회차}}^{n}
(\text{회차별 원금}_k + \text{회차별 수수료}_k)
$$

$$
\text{중도상환 순편익}
= \text{회피 가능한 잔여 수수료}
- \text{중도상환 관련 비용}
- \text{대체자금 조달비용}
- \text{유동성 안전 패널티}
$$

* **동작 프로세스**:
1. **데이터 입력**: 카드사 알림/SMS에서 카드사·승인금액·할부개월을 파싱하고, 회차별 수수료가 없으면 명세서 확인 또는 직접입력을 요청한다.
2. **신뢰도 표시**:
   * 명세서 회차별 금액 확보: `높음`
   * 카드사 공시 수수료율 + 이용기간 확보: `중간`
   * 승인금액·개월수만 확보: `범위 추정`
3. **상환 시뮬레이션**: 다음 결제일, 보유 현금, 예정 정책지원금·급여, 비상자금 하한을 반영해 유지·일부상환·전액상환 시나리오 비교
4. **최종 확인 연결**: 실제 즉시결제·선결제 금액은 카드사 앱 또는 고객센터에서 확인하도록 안내

* **AI PUSH 예시**:
> *"노트북 할부의 회차별 명세를 확인한 결과, 지금 선결제할 때 회피 가능한 수수료는 약 24,000원입니다. 다만 상환 후 다음 달 필수지출 대비 현금이 부족해져 현재 권장 상태는 `보류`입니다. 급여일 이후 다시 계산합니다."*


### 🤖 ④ [Loan Optimization Agent] 대출 총비용·대환·중도상환 Engine

* **지원 상환 방식**:
1. 원리금균등상환
2. 원금균등상환
3. 만기일시상환
4. 거치 후 분할상환

* **원리금균등 월 상환액**:

$$
M = P \times \frac{r(1+r)^n}{(1+r)^n-1}
$$

* $P$: 대출원금
* $r$: 월 이자율
* $n$: 총 상환개월
* $M$: 월 상환액

* **대환·중도상환 판단식**:

$$
\text{대환 순편익}
= \text{기존대출 잔여 총비용}
- \text{신규대출 총비용}
- \text{중도상환수수료}
- \text{인지·보증·플랫폼 등 부대비용}
$$

* **상환능력 보조지표**:

$$
\text{추정 DSR}
= \frac{\text{연간 원리금 상환액}}{\text{인정 연소득}} \times 100
$$

* 추정 DSR은 **사전 경보용**이며, 금융회사별 인정소득·대출 분류·규제 예외·스트레스 금리 적용이 달라 실제 심사 결과를 대체하지 않는다.

* **정책·공공 대출 연계 범위**:
* 대학생: 한국장학재단 학자금대출 공고·신청기간·금리·상환방식 안내
* 취준생·사회초년생: 서민금융진흥원 정책서민금융 상품의 공식 자격·한도·취급기관 링크 제공
* 주거: 주택도시기금·한국주택금융공사·마이홈의 청년 주거금융 상품 원문 연결
* 일반 신용·전세대출: 금융감독원·금융회사 공시 정보를 탐색용으로 제공하되, 실제 견적·승인으로 표시하지 않음

* **규제상 MVP 경계**:
특정 금융회사의 상품을 수수료 기반으로 배열하거나 신청·계약으로 직접 연결하는 온라인 대출 비교·추천·중개는 등록·알고리즘 요건 검토가 필요하다. 따라서 학생 프로젝트 MVP는 **사용자 보유대출 분석, 공공상품 자격 사전진단, 중립적 조건 비교, 공식 사이트 링크**까지만 제공한다.


### 🤖 ⑤ [소득·증빙 Risk Agent] 정책 자격 변화 가능성 경보

* **현금흐름과 공식 소득을 분리**:
* SMS/PUSH의 급여·입금은 `현금흐름 추정치`
* 건강보험료·국세청 소득·가구소득 등은 `정책 판정용 공식값`
* 두 값이 다르면 자동으로 하나를 정답으로 선택하지 않고 `기관 확인 필요` 상태를 만든다.

* **경보 단계**:
1. `안전`: 확인된 공식값 기준 여유가 충분
2. `주의`: 추정 현금흐름이 기준에 근접하나 공식 산식 미확인
3. `확인 필요`: 소득 변동·가구 변경·취업 등으로 재심사 가능성 존재
4. `공고상 부적합`: 기준일과 공식값으로 명확히 조건 미충족

* **금지되는 가이드**:
근무일·급여 지급일을 임의로 조정하거나 소득을 누락하도록 유도하지 않는다. 대신 소득 변동이 정책에 미치는 **합법적 영향과 운영기관 문의 항목**을 안내한다.

* **AI PUSH 예시**:
> "⚠️ **[자격 재확인 필요]** 최근 급여 입금이 늘었지만, 이 정책은 문자 입금액이 아니라 공고상 소득 산정자료로 판단합니다. 현재 결과는 `주의`이며 지원 중단을 확정할 수 없습니다. 변경신고 의무와 공식 산정기간을 원문에서 확인하세요."

## 4. 데이터 수집 및 마이데이터 제약 극복 전략

### ⚠️ 금융·세무 개인데이터 접근의 현실적 경계

* 학생 프로젝트가 은행·카드사의 마이데이터 표준 API나 개인 금융계정 데이터를 **당연히 사용할 수 있다고 가정해서는 안 된다**. 실제 접근은 사업자 자격, 제휴·위탁 계약, 사용자 인증, 보안·컴플라이언스 심사 등 별도 조건이 필요하다.
* 반대로 “모든 금융 데이터 접근이 법적으로 불가능하다”는 표현도 과도하다. 공개 공시·공공 API, 사용자의 직접입력, 사용자가 제공한 명세서, 적법한 상용 중계서비스 계약 등은 서로 다른 접근 경로이다.
* MVP는 정식 마이데이터 사업자 지위를 전제로 하지 않고 **공식 공개데이터 + 사용자 자기입력 + 로컬 알림 파싱 + mock/fixture**로 완성한다.

### 💡 데이터 확보 3계층 전략

```text
[1. Official Public Data : 정책·세법·공공상품의 근거]
 ├─ 온통청년 OPEN API: 정책·공간 메타데이터(XML, 인증키 승인 필요)
 ├─ 중앙부처·지자체 공식 공고: 신청기간·제외조건·증빙 원문
 ├─ 국세청·국가법령정보센터: 귀속연도별 세제 요건·한도·서식
 └─ 교육부·한국장학재단·서민금융진흥원·금융감독원 등: 공공·정책금융 안내

[2. User-Provided Data : 실제 개인 진단]
 ├─ 자기입력: 나이, 지역, 취업·재학, 소득 구간, 주거, 보유부채
 ├─ 문서 업로드: 임대차계약서, 카드명세서, 대출상환계획표의 필요한 항목만 추출
 ├─ Android 알림 파싱: 승인·입금 알림에서 구조화 필드만 로컬 추출
 └─ 민감 원문은 서버 전송 전 마스킹하고, 사용자가 확인·수정

[3. Optional Commercial Adapter : 확장 검증]
 ├─ CODEF 등 상용 중계서비스는 Sandbox/Demo 제공 여부와 최신 약관을 계정에서 확인 후 사용
 ├─ 프로젝트 내부 표준 DTO로 Adapter를 분리해 공급자 교체 가능
 └─ 상용 계약·본인인증·상품별 제공 필드가 확정되기 전에는 실데이터 연동을 핵심 기능으로 약속하지 않음
```

### 📱 Android SMS/PUSH 수집 기술 검증

* `NotificationListenerService`는 사용자가 설정에서 알림 접근 권한을 부여하면 새 알림을 수신할 수 있어, Android APK 데모에서 카드·은행 앱 알림의 구조화 파싱이 가능하다.
* SMS 권한은 Google Play에서 고위험·민감 권한으로 엄격히 제한된다. 따라서 **APK 직접 배포형 프로젝트 시연**과 **Play Store 상용 배포**를 분리한다.
* Android 15 이상에서는 OTP 등 민감 알림 내용이 가려질 수 있으므로, 인증번호 수집에 의존하지 않고 거래금액·가맹점·입금자 등 비인증 정보만 대상으로 한다.
* 권장 구현은 `알림 원문 전체 서버 전송`이 아니라 다음의 로컬 우선 처리다.

```json
{
  "sourceApp": "CARD_APP",
  "eventType": "INSTALLMENT_APPROVAL",
  "amount": 1200000,
  "installmentMonths": 6,
  "merchantCategory": "EDUCATION_OR_DEVICE",
  "occurredAt": "2026-08-24T14:30:00+09:00",
  "rawTextStored": false,
  "userConfirmed": true
}
```

### 💡 CODEF Sandbox/Demo 적용 원칙

> **상용 중계 API는 “실데이터 접근을 보장하는 마법 열쇠”가 아니라, 우리 백엔드가 외부 금융 DTO를 처리할 수 있음을 보여주는 선택적 Adapter이다.**

| 환경 | 프로젝트에서의 역할 | 완료 기준 |
| --- | --- | --- |
| **Local Mock** | 고정 fixture로 카드·대출 DTO 파싱과 계산 검증 | CI 테스트 통과 |
| **Sandbox/Demo** | 계정에서 실제 제공되는 샘플·본인 데이터 범위 확인 | 최신 개발가이드·응답 필드·이용한도 캡처 및 성공 로그 |
| **Production** | 상용 서비스 단계의 계약·보안·개인정보 처리 | 사업자·계약·법무·보안 검토 후 별도 추진 |

* 문서에는 특정 무료기간·일일 호출량·심사일수를 고정 사실로 기재하지 않는다. 이 조건은 공급자 정책에 따라 바뀔 수 있으므로 개발 콘솔의 최신 안내로 관리한다.
* 카드 승인내역에 `할부개월`이 있어도 회차별 수수료가 항상 제공된다고 가정하지 않는다. 부족한 필드는 카드명세서 입력 또는 범위 추정으로 보완한다.

## 5. 파트별 기술 아키텍처 및 역할 분담 (R&R)

### 🔹 Frontend (2명) - `React Native` + `TypeScript`

* **Android 전용 모바일 앱 구현**: React Native 기반 Android 앱. 프로젝트 시연은 APK 직접 배포를 기본으로 하고, Play Store 배포는 SMS 권한 제거 또는 정책 적합성 검토 후 별도 판단.
* **온보딩 & 프로필**: 나이, 지역, 재학·취업, 총급여·소득 구간, 가구, 주거, 임대차, 보유부채를 단계별 입력. 주민등록번호·계좌 비밀번호는 수집하지 않음.
* **Native Module 연동**: `NotificationListenerService` 기반 거래 알림 수신, 로컬 Regex/분류기 처리, 사용자 확인 후 구조화 이벤트 전송.
* **정책·세제 Timeline UI**: 신청기간, 예상 혜택, 자격 신뢰도, 누락 증빙, 공식 원문을 한 화면에 표시.
* **Liability Dashboard**: 카드 할부·대출의 월 상환액, 총비용, 금리변동, 중도상환 시나리오 Chart 시각화.
* **Evidence Locker UI**: 문서 전체를 보관하기보다 필요한 항목과 제출 상태를 중심으로 관리.

### 🔹 Backend (2명) - `Spring Boot` + `Java`

* **Policy/Tax Rule Service**: 귀속연도·시행일·지역·공고 버전별 규칙 저장, 조건 평가, 예상 혜택 계산.
* **Conflict Graph Engine**: 정책 간 `중복 불가 / 조건부 가능 / 선후 신청 / 확인 필요` 관계를 그래프로 관리.
* **Liability Engine**: `BigDecimal` 기반 원리금균등·원금균등·만기일시·거치식 상환 스케줄, 대환·중도상환 순편익 계산.
* **Source Version Service**: 원문 URL, 게시일, 시행기간, 파일 해시, 추출 버전, 검수자를 저장하고 변경 시 Diff 생성.
* **Adapter Layer**: 온통청년, 공공데이터, 선택적 CODEF 등 외부 소스를 내부 표준 DTO로 변환.
* **캐싱 및 알림**: Redis Caching, FCM 기반 마감·증빙·상환 재계산 알림.

### 🔹 AI / Data (2명) - `Python` + `LangChain` / `FastAPI`

* **Document Ingestion**: PDF/HWPX/HWP 파싱, 표·각주·제외조건 추출, 원문 문단 좌표 유지.
* **Rule Candidate Generator**: LLM이 자연어 공고를 JSON 규칙 후보로 변환하되 `DRAFT` 상태로만 저장.
* **Validation Pipeline**: JSON Schema, 숫자·날짜 범위, 원문 인용 일치, 변경 Diff, Golden Set 회귀 테스트.
* **SMS/Notification Parser**: 금융기관별 Regex + 경량 분류 모델, 미확인 필드는 사용자 확인으로 보완.
* **RAG Explanation**: 결정론적 엔진의 결과와 근거 문단을 받아 사용자 친화적인 설명 생성. LLM이 금액을 독자 계산하지 않도록 Tool Calling으로 제한.

### 🧪 RAG·Rule 품질 검증 설계

| 검증 단계 | 합격 기준 |
| --- | --- |
| 원문 수집 | URL·게시기관·게시일·적용기간·파일 해시 100% 저장 |
| 구조 추출 | 표의 숫자·단위·부등호·각주가 원문과 일치 |
| Rule Compile | 필수 필드 누락 0, 스키마 오류 0 |
| Golden Set | 대표·경계·제외 사례에서 판정 일치율 목표 95% 이상 |
| 금액 계산 | 승인된 규칙에 대해 자동 테스트 100% 통과 |
| 변경 감지 | 핵심 숫자·기간·제외조건 변경 시 자동 배포 차단 |
| 사용자 설명 | 근거 URL·기준일·추가 확인 항목 포함률 100% |

* `Golden Set 95%`는 목표치이며, 달성 전에는 해당 정책을 자동 추천 상태로 승격하지 않는다.
* 세액·원리금 계산은 승인 규칙에서 100% 테스트 통과를 배포 조건으로 삼는다. 인간이 만든 제도에는 예외가 많지만, 적어도 컴퓨터가 같은 숫자를 두 번 계산하며 다른 답을 내는 참사는 막아야 한다.

* 전송구간 TLS, 저장 데이터 AES-GCM, 단말 토큰 Android Keystore, 접근 로그와 삭제 이력을 적용한다.

* **정책**: 최종 자격은 운영기관이 심사하며 앱 진단은 참고용이다.
* **세무**: 예상 공제·감면 계산과 증빙 안내만 제공하며, 신고 대행·세무대리로 표시하지 않는다.
* **대출**: 상환 시뮬레이션과 중립적 정보 제공만 수행하며 승인·최저금리·한도를 보장하지 않는다.
* **중개**: 특정 금융상품 신청을 대가성으로 연결하거나 수수료에 따라 순위를 조정하지 않는다.
