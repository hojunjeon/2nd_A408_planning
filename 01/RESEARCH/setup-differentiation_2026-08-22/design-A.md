## direction-1 — 결정론적 자격·중복 그래프

problem_id: P-01

user_moment: 월세·수당·취업지원·정책형 금융상품을 신청하거나 기존 상품을 바꾸기 직전, 사용자가 현재 가능한 제도와 안전한 신청 순서를 정하려는 순간이다.

solution_concept: 사용자가 직접 입력한 최소 프로필(지역, 연령, 가구 유형, 재학·재직, 기준연도 소득, 현재 수급·이전 수혜)과 출처가 검토된 규칙 카드로 자격 조건·중복 배제·선후 관계를 그래프로 계산한다. 결과는 `가능 / 불가 / 운영기관 확인 필요`와 근거 문장·기준일·다음 행동으로만 보여주며, `UNVERIFIED` 또는 현재 원문을 읽지 못한 `BLOCKED`는 보류한다.

why_current_method_fails: 온통청년·복지로·정부24 등이 발견·비교·진단을 제공해도 지역, 가구원, 기준연도·현재 소득, 이전 수혜, 기간·첨부 조건이 원문에 흩어진다. 사용자의 수동 표·스크린샷 비교는 순서와 버전을 함께 보존하지 못하고, 단일 답변은 표 예외나 상충 공고를 놓칠 수 있다는 설계 위험이 있다(실제 실패율은 `UNVERIFIED`; `problem-synthesis.md:21-42`).

provider_data_used: data 역할은 [온통청년 정책 검색·진단](https://www.youthcenter.go.kr/youthIntro/introduce/introAbout), [복지로 서비스·조건 API](https://www.data.go.kr/data/15090532/openapi.do), [정부24 보조금 API 변경 공지](https://www.data.go.kr/bbs/ntc/selectNotice.do?originId=NOTICE_0000000004156), [KINFA 상품 원문](https://www.kinfa.or.kr/financialProduct/youthFutureSavings.do)과 각 운영기관의 원문 URL·확인 시각이다. application 역할은 지자체·복지로·은행 등 실제 운영기관에 남기고, connection 역할은 그 신청 URL·상담 연락처로 연결한다. Setup은 제공자 대신 심사·지급하지 않으며, 은행 비밀번호·MyData·SMS·주민번호·가족의 실제 계정을 받지 않는다.

non_ai_alternative: 정책별 구조화 규칙 카드와 충돌 그래프를 사람이 검토해 갱신하고, 모르는 조건은 보수적으로 `운영기관 확인 필요`로 반환한다. 명시적 조건과 순서만 다루는 한 AI는 필요하지 않다.

ai_required_reason: 필수 아님. 정확한 원문 규칙을 구조화할 수 있는 제한된 범위에서는 결정론적 계산이 설명 가능성과 안전한 보류에 더 적합하다. AI는 나중에 후보 규칙을 제안할 수 있지만 승인된 규칙을 대체하지 않는다.

risks: 공고 변경·상충·API 지연으로 규칙이 낡거나 잘못된 순서가 될 수 있고, 예비 진단을 최종 승인으로 오해할 수 있다. 원문 버전·확인 시각·운영기관 재확인을 항상 표시하고, 현재 자료가 없으면 `UNVERIFIED/BLOCKED`로 중단한다. 실제 승인률·손실 회피·시간 절감은 측정 전이다.

how_to_test: 공식 원문에서 만든 소수의 고정 규칙 사례와 합성 프로필(가구 소득, 직전연도 소득, 이전 수혜, 중복·전환 순서, 누락 입력)을 재생해 기대 상태·근거·보류가 일치하는지 검사한다. 규칙 판정·순서의 오류와 근거 누락을 기록하되 실제 운영기관 승인 결과는 `UNVERIFIED`로 남긴다.

## direction-2 — 근거 제한형 AI 문서 해석 보조

problem_id: P-01

user_moment: 사용자가 여러 공고의 비슷한 표현·표·예외를 읽고 “내 조건에서 어느 제도를 먼저 확인해야 하나”를 묻는 순간이다.

solution_concept: 공개된 제공자 원문만 대상으로 AI가 조건·예외·중복·기준일 후보를 추출하고, 각 문장을 원문 위치에 연결한 비교 초안을 만든다. 결정론적 검증기가 초안과 사용자 입력을 대조하며, 인용이 없거나 문서 버전이 충돌하면 답하지 않고 `운영기관 확인 필요`로 넘긴다.

why_current_method_fails: 공식 정보는 존재하지만 PDF·표·페이지·외부 신청 링크에 나뉘고, 수동 비교는 새로운 공고의 표현 변화와 상충 버전을 모두 따라가기 어렵다. 반대로 출처 없는 범용 답변은 예비진단을 확정판정처럼 보이게 할 위험이 있다(`verifier-problem.md`의 `UNVERIFIED` 설계 위험).

provider_data_used: data 역할은 온통청년·복지로·정부24·KINFA가 공개한 정책 메타데이터와 원문/첨부 URL이다. application 역할은 각 정책 운영기관·지자체·참여 은행의 실제 신청 화면에 두고, connection 역할은 원문 인용·신청 링크·온통청년/복지로/KINFA 상담으로 연결한다. 개인 금융계정·로그인 정보·민감 문서를 AI 입력으로 요구하지 않고, 사용자는 최소 프로필만 직접 제공한다.

non_ai_alternative: 사람이 원문을 읽어 규칙 카드와 예외 표를 작성하거나, 구조화된 필드만 입력받아 비교한다. 문서 종류와 정책 수가 고정되면 이 방식이 더 단순하고 검증 가능하다.

ai_required_reason: 제품 범위가 미리 구조화되지 않은 공개 공고를 계속 읽고, 같은 의미의 표현·표 예외·문서 간 연결을 사람이 일일이 규칙화하지 않고 후보로 묶어야 한다면 AI가 필요하다. 다만 AI의 역할은 근거가 붙은 추출·요약 후보 생성까지이며, 자격·중복·신청 결과를 단독 결정하지 않는다.

risks: 잘못된 추출·환각 인용·오래된 원문 혼합·민감정보 노출이 가능하다. 원문 스냅샷과 인용 위치, 기준일, confidence 대신 `확인 필요` 상태를 저장하고 결정론적 규칙·사람 검토로 게이트한다. AI 정확도와 실제 승인·손실 회피 효과는 아직 `UNVERIFIED`; 원문 접근이 막히면 `BLOCKED`다.

how_to_test: 정책 종류·표 예외·중복 문구·서로 다른 버전으로 구성한 고정 공고 묶음과 사람이 만든 정답 주석을 사용한다. 조건 추출 정확도, 인용의 실제 원문 일치율, 충돌 시 보류율, 잘못된 확정판정 0건을 측정하고, 합성 프로필로 순서 계산을 별도 검증한다. 실제 제출·승인은 시험 범위 밖이며 `UNVERIFIED`다.

## direction-3 — UX 중심 결정 패킷

problem_id: P-01

user_moment: 사용자가 검색 결과를 본 뒤 신청·비교·갈아타기 중 무엇을 할지 고르고, 서류와 기존 수혜 상태를 확인해 실제 신청 화면으로 이동하려는 순간이다.

solution_concept: 첫 화면에서 목적을 하나 선택하게 한 뒤, 정책 카드를 `확인된 사실 / 내가 입력하지 않은 항목 / 운영기관에 물을 항목` 세 칸으로 나눈다. 카드에는 중복·전환 순서의 이유, 필요한 첨부, 기준일, 원문 링크, 진행 상태를 함께 두고 기존 상품 해지·신청 완료 같은 되돌리기 어려운 행동은 확인 전 잠근다.

why_current_method_fails: 제공자 포털의 검색·진단과 실제 신청·첨부 완료 확인·상담이 분리되어 사용자는 비교표, 메모, 스크린샷으로 상태를 이어 붙인다. 가족 동의·서류·접속 대기 마찰은 공개 사례에서 확인됐지만 발생률은 `UNVERIFIED`다(`worker-A.md`, `worker-B.md`).

provider_data_used: data 역할은 제공자 원문·조건·필요 서류·상태 문구를 출처 카드로 저장하는 것이고, application 역할은 복지로·지자체·은행·운영기관의 실제 신청·심사에 남긴다. connection 역할은 해당 기관의 딥링크·상담 번호·완료 확인 안내로 제공한다. 개인정보 동의 없이 검색·비식별 예비진단을 사용할 수 있게 하며, 가족·계좌·SMS·MyData 연동은 기본 흐름에 넣지 않는다.

non_ai_alternative: AI 없이 점진적 입력, 비교 카드, 체크리스트, 저장·재개, 제출 전 확인 화면과 접근성 있는 대체 경로만으로 구현한다. 판단이 애매한 값은 사용자에게 다시 묻거나 공식 상담으로 보낸다.

ai_required_reason: 필수 아님. 이 방향의 차별화는 추론보다 정보의 순서·가시성·되돌리기 안전장치에 있으므로 결정론적 상태와 명시적 문구가 적합하다.

risks: 카드가 단순화되면 사용자가 `가능`을 승인 보장으로 오해하거나, 필수 입력·가족 동의·오프라인 사용자를 배제할 수 있다. 세 상태와 최종 판단 기관을 반복 표시하고, 큰 글씨·키보드·저대역폭·비스마트폰 가족의 대체 절차를 검증한다. 완료율·시간 절감·지원금 확보는 아직 `UNVERIFIED`다.

how_to_test: 합성 사용자 시나리오로 “왜 보류인지”, “어느 원문을 확인할지”, “무엇을 먼저 신청할지”, “해지 전에 무엇을 확인할지”를 사용자가 설명하고 선택하게 한다. 기존 수동 비교 흐름과 과업 이해·근거 회상·잘못된 해지 의도·이탈을 비교하되, 표본 결과를 실제 정책 승인이나 금액 효과로 일반화하지 않는다.

## direction-4 — 버전 원장·중복 변경 자동화

problem_id: P-01

user_moment: 사용자가 신청하려는 시점에 정책의 모집 상태·이전 수혜 제외·중복 관계·기준 문서가 최근에 바뀌었는지 확인하려는 순간이다.

solution_concept: 공개 제공자 API와 원문 링크에서 정책 식별자·조건·신청 링크·확인 시각을 버전 원장으로 보존하고, 새 문서의 추가·삭제·변경과 중복/선후 관계 후보를 비교한다. 사용자 프로필에는 관련 항목만 연결해 변경 근거와 확인 필요 알림을 보여주며, 자동 신청이나 자동 해지는 하지 않는다.

why_current_method_fails: 정책 마감·예산 소진·이전 수혜·신청 링크·기준연도는 제공자별로 바뀌고 개인의 메모·스크린샷은 최신 여부를 판별하지 못한다. API·페이지 접근 권한, 스키마, 현재 원문 상태도 조사에서 모두 실사용 검증된 것은 아니므로 자동화 성공을 전제할 수 없다(`worker-C.md`의 `UNVERIFIED/BLOCKED`).

provider_data_used: data 역할은 온통청년·복지로·정부24/보조금24·KINFA의 공개 메타데이터와 원문 버전이다. application 역할은 운영기관의 신청·심사 시스템에 남기고, connection 역할은 변경된 원문·운영기관 신청·상담으로 연결한다. 인증키·개인 금융 데이터·주민번호·SMS를 수집하지 않고, API 승인·호출이 없으면 해당 항목을 `BLOCKED`로 표시한다.

non_ai_alternative: 문서 해시·구조화 필드·명시적 상태값·원문 링크의 변경분만 비교하는 자동화로 시작한다. 의미가 불명확한 변경은 사람 검토 큐로 보내며 AI 없이도 최신성·출처 보존을 검증한다.

ai_required_reason: 필수 아님. 제공자가 구조화된 필드와 버전을 주는 범위에서는 일반 diff와 규칙으로 충분하다. 서로 다른 문서 레이아웃의 같은 조항을 의미상 연결하는 범위까지 자동화하려면 AI가 선택적으로 필요하지만, 그 확장은 별도 검증 없이는 채택하지 않는다.

risks: 제공자 API 인증·트래픽·약관, 페이지 차단, 스키마 변경, 잘못된 변경 감지와 과잉 알림이 위험이다. 원문·확인 시각·변경 전후를 보존하고, 알 수 없는 변경은 알림 대신 `UNVERIFIED/BLOCKED`로 보류한다. 최신성·알림 도달·실제 신청 성공은 측정 전이다.

how_to_test: 보관한 공식 문서와 합성 변경본을 재생해 정책 식별, 조건 추가·삭제, 이전 수혜/중복 관계 변경, 링크 변경을 감지하는지 확인한다. 변경 근거 링크와 보류 조건을 검수하고, 실제 제공자 API 호출·신청·개인 알림 도달은 이 조사 범위에서 검증하지 않아 `UNVERIFIED`로 기록한다.
