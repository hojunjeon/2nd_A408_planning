# AGENTS.md — Setup 프로젝트 작업 지침

## 설득력과 기술력의 구분

### 설득력 (Persuasion)

- 문제 정의 → 개념적 솔루션 → 핵심 기능 → 기술 선택으로 이어지는 탑다운 서사다.
- 각 전환에서 다음 세 가지 `왜`에 답해야 한다:
  1. 왜 이 문제를 이 솔루션으로 해결하는가?
  2. 왜 이 솔루션을 이 기능들로 구성하는가?
  3. 왜 이 기능을 이 기술로 구현하는가?
- 새 기능·기술은 어떤 문제·솔루션·기능에서 파생됐는지 명시한다. 세 가지 `왜`에 답할 수 없으면 추가하지 않는다.
- 정량·정성 데이터, 행동과학 원리, 기존 서비스 공백 분석으로 뒷받침.
- 수치·사례·구현 결과는 출처와 기준일, 검증 수준을 표시한다. 증거가 없으면 `UNVERIFIED`, 진행할 수 없으면 `BLOCKED`로 구분한다.
- 시연도 문제 공감 → 솔루션 제시 → 기능 확인 → 기술 증명 순서로 구성한다.
- 산출물 형태: 설득력 설계도(표), 문제-솔루션 매핑, 차별화 요약.

### 기술력 (Technical Feasibility)

- 논리 중심. "선택한 기술이 실제로 적합하고 구현 가능한가"를 검증.
- 평가 항목:
  1. **적합성** — 해당 기능을 풀 때 이 기술이 올바른 도구인가?
  2. **구현 가능성** — 주어진 시간(5주)·팀 규모(6인) 내에 동작하는가?
  3. **난이도** — 학습 곡선, 통합 부담, 디버깅 비용은 어느 정도인가?
  4. **대안 비교** — 왜 다른 기술(F+G)이 아닌 D+E인가? 배제 근거는 무엇인가?
  5. **고도화 방안** — MVP 이후 확장 경로가 존재하는가? 어떤 조건에서 업그레이드하는가?
  6. **검증 방법** — 구현 전에 사전 검증(spike, PoC)으로 리스크를 줄일 수 있는가?
- 산출물 형태: 기능 × 기술 × 적합성/난이도/대안/고도화 매트릭스(표), PoC 결과, 리서치 인용.

### 두 축의 관계

- 설득력이 없으면 프로젝트 자체가 납득되지 않고, 기술력이 없으면 발표에서 "실제로 되나?"라는 질문을 못 넘긴다.
- 두 축은 별개의 문서로 관리한다:
  - `Setup_설득력.md` → 설득력 중심
  - `Setup_기술력.md` → 기술력 중심
- 기획 문서의 기술 매핑은 "왜 이것을 선택했는가"(설득력)만 담고,
  기술력 문서는 "정말 구현 가능한가, 대안은 무엇인가, 어떻게 고도화하는가"(기술력)를 담는다.

## Git 작업 규칙

- 모든 작업은 이 저장소의 `main` 브랜치에서 직접 수행한다. Git 상태를 변경하는 명령 직전에 `git branch --show-current`로 `main`인지 확인한다.
- 독립적으로 검증 가능한 작업 단위마다 관련 경로만 명시적으로 스테이징해 한글 커밋 메시지로 커밋한다. 각 커밋은 즉시 `origin/main`에 푸시한다.
- 커밋·푸시 후 로컬 `HEAD`, 추적 브랜치, 원격 `main`의 커밋 SHA가 일치하는지 확인한다.
- 기존 변경으로 작업이 막히면 worktree·stash·reset으로 우회하지 말고 중단하여 보고한다.
