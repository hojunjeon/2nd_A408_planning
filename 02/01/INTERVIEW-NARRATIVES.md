## 0. 기존 전략의 약점 진단 (왜 다시 하는가)

CANDIDATE-003(PolicyOS: Policy Compiler + Digital Twin + Adversarial Audit)은 개념 완성도와 출처 규율은 높지만, 면접 서사 관점에서 네 가지가 약하다.

1. **알고리즘 축이 없다.** AI 아키텍처(컴파일러/감사) 이야기만 있고, "핵심 도메인 문제를 어떤 알고리즘으로 정식화해서 풀었나"가 없다. 6인 팀 중 FE/BE 4명이 면접에서 쓸 수 있는 서사가 사실상 없다.
2. **전부 설계 단계다.** 모든 Result가 UNVERIFIED. "재현된 실패 → 도입 → 전후 비교"의 실측 서사가 하나도 없다.
3. **기술 신규성이 조합 수준이다.** Rules as Code + LLM 검증의 결합이라는 평가(연구 에이전트 분석)가 이미 내부 검증 문서에서도 나왔다.
4. **이야기가 기술 중심이다.** "왜 이게 청년의 문제를 푸는가"에서 출발하지 않고 아키텍처에서 출발한다.

## 0.1 서사 설계 원칙 (모든 후보에 공통 적용)

면접에서 강한 서사는 항상 같은 뼈대다: **① 재현 가능한 실패를 먼저 만들고 → ② 단순한 방법(v1)이 왜 무너지는지 원인을 분석하고 → ③ 그 원인을 정면으로 겨냥한 기술을 도입하고 → ④ 같은 테스트셋으로 전후를 정량 비교하고 → ⑤ 남은 한계를 스스로 고백한다.**

따라서 아래 서사들은 전부 "v1을 일부러 건너뛰지 않는다"는 규칙을 갖는다. if-else 버전, Regex 버전, 순수 벡터 RAG 버전을 **먼저 만들고 실패 로그를 커밋에 남기는 것 자체가 서사의 재료**다. 처음부터 최종 기술로 직행하면 "개발 도중 발생한 문제를 해결했다"는 이야기는 성립하지 않는다.

숫자 규율은 PLAN.md와 동일하다: 측정 전 수치는 절대 말하지 않는다. 아래 각 서사의 "측정 지표"는 구현 중 채워야 할 빈칸이지, 지금 주장할 값이 아니다.

## A. 획기적 아이디어 (제품의 '한 방')

### N-01 정책 신청 로드맵을 조합 최적화 문제로 정식화 — "로드맵 엔진의 심장" ★신규 핵심

- **한 줄 피치**: "중복수혜 금지·선후관계·기간 제약을 만족하며 총 수혜액을 최대화하는 신청 순서를, if-else가 아니라 **DAG 위상정렬 → ILP(정수계획법)** 로 정식화해 '이 로드맵이 최적'임을 수학적으로 보장했다."
- **문제 (재현할 실패)**: v1 if-else 판정기는 정책 N개에 대해 배제쌍·선후쌍이 늘 때마다 분기가 조합적으로 폭증하고, "청년수당을 먼저 받으면 국취제를 못 받는데 총액은 국취제 먼저가 더 큰" 식의 순서 의존 케이스에서 준최적/오답 로드맵을 낸다. 합성 프로필 테스트셋으로 이 오답을 재현해 둔다.
- **도입 기술 (RA 자료집 근거)**:
  - 정책 = 노드, 선후관계 = 방향 간선인 **DAG + 위상정렬(O(V+E))** 로 유효 순서 공간을 정의.
  - 중복배제는 `x_i + x_j ≤ 1`, 선후관계는 `x_i ≤ x_j` 제약, 목적함수 `max Σ(수혜액·x_i)`인 **ILP**로 풀고 OR-Tools(CP-SAT) 솔버 사용. 정책 10~50개 규모면 초 단위 해결.
  - 대안 경로: 정책 15개 이하면 비트마스크 DP(2^n 상태)로 직접 구현해 "솔버 없이도 원리를 안다"를 증명.
- **왜 단순 방법보다 나은가**: if-else는 yes/no만 주지만 ILP는 **최적성 갭(MIP gap)** 을 준다 — "현재 로드맵은 최적 대비 몇 % 이내"라고 말할 수 있다. 새 정책·새 제약 추가가 부등식 한 줄 추가로 끝나 유지보수가 선형이다.
- **측정 지표**: 합성 프로필 100케이스에서 그리디/if-else 대비 총 수혜액 차이, 오답(제약 위반) 건수 0 검증, 정책 수별 풀이 시간.
- **예상 반문과 방어**: "정책 몇십 개에 ILP는 과한 것 아닌가?" → 규모가 아니라 **정합성 보장**이 목적. 제약 위반 로드맵 하나가 사용자에게 수백만 원 손실이므로, 휴리스틱의 '아마 맞음'이 아니라 솔버의 '위반 불가능'이 필요했다고 답한다.
- **담당**: Backend 2명 (핵심 어필 서사).

### N-02 PolicyOS — 정책 공고를 실행 가능한 프로그램으로 컴파일 (CANDIDATE-003 유지·피치 강화)

- **한 줄 피치**: "Setup은 정책을 요약하는 챗봇이 아니라, 공고문을 Policy IR로 **컴파일**하고, 스키마·타입·반례 검증을 통과한 프로그램만 결정론적 런타임이 실행하는 시스템이다."
- **서사의 핵심 실패**: "JSON 스키마는 통과했는데 정책 의미가 틀린" 컴파일 결과(표의 예외 행을 일반 조건으로 흡수)를 재현하고, symbolic runtime + 반례 생성이 이를 거부하는 로그를 남긴다. (PLAN.md STARR-3 그대로 실행)
- **왜 어필되는가**: "LLM이 판정했다"가 아니라 "LLM은 번역만 하고, 프로그램이 검증을 통과해야만 실행된다"는 **신뢰 아키텍처** 이야기. 금융 도메인 면접에서 책임 경계 질문에 정면 대응된다.
- **측정 지표**: Policy IR 필드·의미 정확도, 반례 탐지율, 허위 확정 0건.
- **담당**: AI 2명. N-01의 ILP 엔진이 이 IR을 입력으로 받으면 두 서사가 하나의 시스템으로 연결된다(컴파일러가 제약을 뽑고, 최적화기가 로드맵을 푼다).

### N-03 개인 정책 디지털 트윈 — "취업하면?"의 반사실 실행

- **한 줄 피치**: "현재 자격 조회가 아니라, 사용자의 미래 이벤트(취업·이사·소득 변화)를 상태 그래프 위에서 가상 실행해 **바뀌는 조건의 delta만** 보여주는 what-if 엔진."
- **서사의 핵심 실패**: 기존 진단형 서비스(온통청년 예비진단 포함)가 현재 스냅샷만 답해, "다음 달 취업 예정"인 사용자에게 곧 무효가 될 안내를 주는 케이스를 시연으로 재현.
- **왜 어필되는가**: 예측이 아니라 **규칙 delta 계산**이라는 절제된 정의가 오히려 신뢰를 준다. 영향받는 정책만 재실행하는 증분 재계산(의존 그래프 캐시 무효화)은 시스템 설계 어필 포인트.
- **측정 지표**: 시나리오 영향 범위 정확도(불필요 재계산률), 과업 성공률.
- **담당**: AI 1명 + FE 1명(시나리오 UX).

## B. 개발 도중 발생한 문제 → 새로운 기술의 도입

### N-04 Regex 지옥에서 탈출 — SMS 파싱을 문자열 알고리즘으로 재설계 ★FE/BE 공용 서사

- **한 줄 피치**: "카드사·은행별 문자 형식이 늘수록 정규식이 100개로 불어나고 서로를 깨뜨렸다. 정규식 나열을 버리고 **Aho-Corasick 다중 패턴 매칭 + BK-tree 오타 허용 매칭 + Thompson NFA 계열(RE2) 엔진**의 3층 파서로 바꿨다."
- **문제 (재현할 실패)**: v1 순수 Regex 파서로 실제 수집한 문자 코퍼스(팀원 개인 문자, 비식별화)를 돌려 (1) 신규 형식 미스매치, (2) 정규식 추가가 기존 케이스를 깨는 회귀, (3) 백트래킹 폭주(ReDoS성 지연) 사례를 기록.
- **도입 기술 (RA 자료집 근거)**:
  - **Aho-Corasick**: 가맹점·기관명 사전을 트라이+실패링크로 한 번의 선형 스캔에 전부 탐색. 형식이 늘어도 코드가 아니라 **사전만 갱신**.
  - **BK-tree(편집거리)**: "농협" vs "NH농협", 띄어쓰기 변형 등 근사 매칭.
  - **RE2(Thompson NFA/DFA)**: 남는 금액·날짜 패턴은 백트래킹 없는 선형 시간 엔진으로 실행해 지연 폭주 원천 차단.
- **왜 어필되는가**: "라이브러리를 썼다"가 아니라 "파싱 문제를 **사전 매칭(고정 문자열) / 근사 매칭(변형) / 구조 패턴(정규 언어)** 세 계층으로 분해했다"는 문제 분해 이야기. 자료구조(트라이, 메트릭 트리) 지식이 실전에 쓰인 드문 사례.
- **측정 지표**: 형식 커버리지(기관 수), 파싱 정확도/재현율 전후 비교, 신규 형식 대응 소요 시간(코드 수정 → 사전 1행 추가), 최악 지연.
- **담당**: AI·Data 1명 + FE 1명(Android 수신부).

### N-05 순수 벡터 RAG의 배신 — 구버전 혼입·표 예외 누락을 잡는 검색 고도화

- **한 줄 피치**: "임베딩 유사도만 믿은 RAG가 2025년 구공고를 2026년 답변에 섞었다. **BM25+HNSW 하이브리드 검색 → 유효기간(버전) 하드 필터 → 원문 span 인용 검증**의 3단 게이트로 재설계했다."
- **문제 (재현할 실패)**: 같은 정책의 구공고·신공고를 함께 인덱싱한 뒤 소득 기준 질의를 던져, 순수 벡터 검색이 (의미상 더 유사한) 구버전 조항을 상위로 올리는 것을 로그로 재현. 표의 예외 행이 청크 분할에서 소실되는 사례도 함께.
- **도입 기술 (RA 자료집 + PLAN.md 근거)**:
  - **하이브리드 검색**: "중위소득 60%" 같은 정책 고유 용어는 BM25(정확 매칭)가, 표현이 다른 질의는 HNSW 벡터가 잡는다. 상호 보완으로 recall 병목 해소.
  - **버전 하드 필터**: 검색 점수가 아니라 메타데이터(유효 시작·종료일)로 후보를 먼저 자르는 결정론적 게이트. VersionRAG의 문제의식을 제품 규칙으로 옮김.
  - **인용 span 검증**: 답변의 모든 조건이 원문 위치와 기준일에 연결되지 않으면 UNVERIFIED로 보류.
- **왜 어필되는가**: "RAG 써봤다" 지원자가 넘치는 시장에서 "RAG가 **어떻게 실패하는지 재현하고 게이트를 설계했다**"는 한 단계 위의 이야기.
- **측정 지표**: 구버전 인용률 전후, 예외 행 recall, unsupported 답변률.
- **담당**: AI·Data 2명.

### N-06 매일 새벽 배치가 같은 공고를 다시 긁는다 — 수집 파이프라인의 자료구조 처방

- **한 줄 피치**: "정책 수집 배치가 커질수록 중복 수집·중복 파싱(비싼 Vision 파싱 호출)이 비용을 태웠다. **Bloom filter 선차단 + 콘텐츠 해시 sort-merge 중복 제거**로 재수집·재파싱을 구조적으로 없앴다."
- **문제 (재현할 실패)**: v1 배치의 일일 수집 로그에서 신규 공고 대비 중복 URL 비율, 변경 없는 문서의 재파싱 호출 수(LlamaParse 등 호출당 과금)를 측정해 낭비를 수치화.
- **도입 기술 (RA 자료집 근거)**:
  - **Bloom filter**: 기수집 URL/ID의 부재 판정을 메모리 수 MB로 O(1) 처리, DB 조회 자체를 건너뜀. false positive율과 비트 배열 크기의 트레이드오프를 계산해서 설정했다는 디테일이 어필 포인트.
  - **콘텐츠 해시 + 배치 정렬 중복 제거**: URL이 달라도 본문이 같은 재게시 공고를 잡는다. 개별 lookup 반복 대신 배치 sort-merge.
  - (선택) 도메인 구조 활용: 기관/연도별로 비교 범위를 분할하는 structured dedup.
- **왜 어필되는가**: 확률적 자료구조를 "비용 절감"이라는 비즈니스 언어로 연결하는 서사. Backend 포지션 면접에서 배치/파이프라인 설계 질문에 바로 쓰인다.
- **측정 지표**: 중복 수집률 전후, 파싱 API 호출 수·비용 전후, 배치 소요 시간.
- **담당**: Backend 2명.

## C. 기존 기술의 한계를 극복하기 위한 고도화

### N-07 "기준 초과했습니다" 사후 통보의 한계 — 확률적 조기 경보로 고도화

- **한 줄 피치**: "임계값 비교식 경고(v1)는 이미 초과한 뒤에야 운다. 소득 입금 이력을 확률 분포로 모델링해 **'이 추세면 3개월 내 자격 상실 확률 N%'를 동적계획법으로 계산**하는 조기 경보로 바꿨다."
- **문제 (재현할 실패)**: 합성 소득 시계열(비정기 알바 패턴)에서 v1 임계값 경고가 초과 직전월에야 발화해 사용자가 대응할 시간이 없는 케이스를 재현.
- **도입 기술 (RA 자료집 근거)**: 상태를 `dp[월][소득구간] = 박탈 누적 확률`로 정의한 **확률 전이 DP**(Bellman 형태). 월별 전이 확률을 사전 계산하면 질의는 O(1). 고도화 여지로 부분관측(신고 누락) 대응 POMDP를 '검토했으나 규모 대비 과해서 기각'한 의사결정 자체도 서사에 포함.
- **왜 어필되는가**: 단순 알림 기능이 "불확실성 하의 의사결정 모델링" 이야기로 격상된다. "왜 ML 예측 모델이 아니라 DP인가?"에 대해 "데이터가 적고 설명 가능성이 필수인 금융 경고에는 명시적 확률 모델이 맞다"는 기술 선택 논리를 준비할 수 있다.
- **측정 지표**: 경고 리드타임(초과 몇 개월 전 발화), 오경보율/미탐율 전후.
- **담당**: AI·Data 1명.

### N-08 그리디 상환 권고의 한계 — 할부 스케줄을 최적화 문제로

- **한 줄 피치**: "'여윳돈 생기면 바로 중도상환' 그리디 권고(v1)는 중도상환 수수료·지원금 입금 시점이 얽히면 손해를 본다. 남은 원금×기간을 상태로 한 **DP(또는 연속 변수면 LP)** 로 총 이자+수수료 최소 스케줄을 계산했다."
- **문제 (재현할 실패)**: 중도상환 수수료가 있는 케이스에서 그리디가 최적 대비 손해 보는 반례를 구성해 시연.
- **도입 기술 (RA 자료집 근거)**: `dp[남은원금][남은개월] = 최소 비용` DP + 경로 복원으로 월별 상환 일정 자동 생성. LP로 풀면 **민감도 분석**("금리가 1%p 오르면 총 이자가 얼마나 변하나")까지 덤으로 제공 — 이것이 시뮬레이션 기능(기획서 기능 ④)과 자연 연결된다.
- **측정 지표**: 그리디 대비 절감액 분포(합성 케이스), 계산 지연.
- **담당**: AI·Data 1명 + BE 1명.

### N-09 단일 LLM 답변의 한계 — 적대적 감사로 "그럴듯한 오답"을 거부 (CANDIDATE-003 STARR-5 실행)

- **한 줄 피치**: "유창한 단일 LLM 답변이 다른 지역 공고의 예외를 섞어 확정 안내를 만든 실패를 재현하고, **반례 생성 에이전트 + 인용 감사 + 결정론적 런타임**이 그 답을 거부해 UNVERIFIED로 보류하는 파이프라인을 세웠다."
- **왜 어필되는가**: "AI를 더 똑똑하게"가 아니라 "AI의 오답이 사용자에게 도달하지 못하게"라는 방향 전환 자체가 차별화. 다수결이 아니라 반례에도 원문·실행 trace를 요구한다는 디테일로 멀티에이전트 유행어 소비와 선을 긋는다.
- **측정 지표**: 허위 확정률, 보류 정밀도, 단일 LLM/일반 RAG/PolicyOS 3자 비교 (PLAN.md C3 케이스 재사용).
- **담당**: AI·Data 2명.

### 서사를 '진짜'로 만드는 실행 규칙

1. **v1을 반드시 먼저 만든다.** if-else 판정기, 순수 Regex 파서, 순수 벡터 RAG를 먼저 커밋하고, 실패 케이스를 테스트 코드로 고정한다. 이 커밋 이력이 "개발 도중 문제를 만났다"의 증거다.
2. **실패 로그를 산출물로 취급한다.** `RESEARCH/failure-log/`에 실패 재현 케이스·원인 분석·기술 선택 비교표(채택안 vs 기각안과 기각 사유)를 날짜와 함께 남긴다. 면접 답변의 Reflection 재료가 된다.
3. **전후 비교는 같은 테스트셋으로.** 각 서사의 v1과 v2를 동일한 합성 케이스에 돌린 수치만 말한다. 측정 전에는 PLAN.md 규율대로 UNVERIFIED.
4. **팀원별로 주 서사 1개 + 보조 서사 1개를 배정한다.** 6명 전원이 "내가 만난 문제 → 내가 도입한 기술"을 1인칭으로 말할 수 있어야 한다.
5. **기각한 기술도 기록한다.** "POMDP를 검토했으나 관측 데이터 규모 대비 과해서 확률 DP로 결정" 같은 기각 사유가 채택 사유만큼 강한 어필이다.
