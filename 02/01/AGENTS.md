# A408 Setup project instructions

이 파일은 `a408` 프로젝트의 작업 기준이다. 작업을 시작하기 전에 반드시
`a408_기획.md`와 `(핀테크) 프로젝트 소개 및 사전질문 양식_A408.pptx`를 먼저 읽는다.
`PLAN.md`의 보완 설계는 원기획을 대체하지 않으며, 원기획의 네 가지 제품 핵심을
항상 기준선으로 유지한다.

## 기획 서사 원칙 — 탑다운, 그 중심의 `왜`

모든 기획·보강·발표·시연 구성은 다음 탑다운 서사를 따른다.

> "문제 정의로부터 솔루션을 도출하고, 솔루션을 위한 기능을 구상하고,
> 기능을 구현하기 위해 기술을 적용한다."

단계 사이마다 `왜`가 있어야 하며, 이 `왜`가 문서와 발표의 중심이다.

1. 왜 이 문제를 이 솔루션으로 해결하는가 (문제 → 솔루션)
2. 왜 이 솔루션은 이런 기능으로 구상했는가 (솔루션 → 기능)
3. 왜 이 기능은 이런 기술로 구현하려 했는가 (기능 → 기술)

적용 규칙:

- 새 기능·기술 제안 시 어느 단계에서 파생되었는지(어떤 문제/솔루션/기능에서
  나왔는지) 반드시 명시한다.
- 세 단계의 `왜`에 답할 수 없는 기술 스택이나 기능은 추가하지 않는다.
- 시연·데모도 이 서사 순서대로 구성한다: 문제 공감 → 솔루션 제시 →
  기능 확인 → 기술 증명 순으로 보여준다.

## 절대 잊지 않을 핵심 기능

### 1. 정책 찾기·신청 로드맵

- 온통청년·공공데이터·운영기관 공고를 자동 수집하고 정리한다.
- 사용자의 지역·나이·가구·주거·재학/재직·소득 조건과 대조한다.
- 정책별 자격, 중복 수혜 제한, 선후 관계, 신청 가능 시점, 최적 신청 순서를 안내한다.
- 단순 정책 검색이나 목록 나열로 축소하지 않는다.

### 2. 자격 유지 컷오프 Agent

- Android의 사용자 동의 기반 SMS/PUSH에서 알바·단기·프리랜서 소득 후보를 파싱한다.
- 정책별 소득 기준일과 누적 소득을 비교해 자격 초과 위험을 사전 경고한다.
- 경고에는 계산 근거, 기준일, 확인해야 할 기관·서류·다음 행동을 함께 표시한다.
- 사용자의 근무·소득을 임의로 줄이라고 지시하거나 자격 회피를 유도하지 않는다.

### 3. 할부 수수료 절감 Agent

- 카드 할부의 잔여 원금·회차·수수료를 계산한다.
- 지원금 입금 시점과 사용자의 현금흐름을 반영해 중도상환 또는 유지 시나리오를 비교한다.
- 절감 예상액, 계산식, 가정, 상환 일정과 금융기관 확인 필요사항을 보여준다.
- 실제 카드사 데이터는 CODEF Sandbox/Demo, 자기입력 또는 mock으로 구분하며 실데이터 성공으로 과장하지 않는다.

### 4. 미래 자산 계획

- 절약한 지원금과 예·적금 조합을 입력받아 미래 자산 변화를 시뮬레이션한다.
- 기간·납입액·금리·정부기여금·현금흐름 가정을 명시하고 시나리오별 결과를 비교한다.
- 예측·수익·가입 가능성을 확정값처럼 말하지 않으며, 정책·금융기관의 최종 판단을 대체하지 않는다.

## 고도화 기능의 위치

Policy Compiler, Policy IR, symbolic runtime, Personal Policy Digital Twin,
Policy Test/Counterexample Generator, Adversarial Policy Audit는 위 네 기능을
강화하는 기술 계층이다. 이 기능들이 원래 제품을 대체해 `정책 문서 챗봇`이나
`PolicyOS 데모`만 남게 만들지 않는다.

- Policy Compiler: 공고문을 실행 가능한 조건·예외·기간·근거 구조로 변환한다.
- Digital Twin: 취업·이사·소득 변화가 네 핵심 기능의 결과에 미치는 변화를 가상 실행한다.
- Adversarial Audit: 자격·컷오프·할부·자산 계산의 버전 충돌, 예외, 근거 누락을 공격적으로 검증한다.
- 모든 고도화 결과는 원문 span, 기준일, 계산 trace, `UNVERIFIED/BLOCKED` 경계를 남긴다.

## 데이터·법적 경계

- 정식 마이데이터 사업자나 카드사 API 직접 연동을 기본 전제로 삼지 않는다.
- 정책 데이터는 온통청년·공공데이터 API와 운영기관 원문을 사용한다.
- 금융·소득 데이터는 SMS/PUSH 사용자 동의, 자기입력, mock, CODEF Sandbox/Demo로 명확히 구분한다.
- 금융 비밀번호·토큰·주민번호·가족 계정·자동 신청·자동 해지·법적 자격 확정을 요구하거나 약속하지 않는다.
- 신청·심사·지급·중단·환수·이의신청의 최종 결정은 운영기관에 남긴다.

## 작업 우선순위와 증거 규칙

1. 모든 기능 요약·계획·구현 검토에서 네 가지 핵심 기능을 먼저 표기한다.
2. 차별화 기능은 어떤 핵심 기능을 강화하는지 명시한다.
3. 원기획의 기능을 삭제·대체·축소할 때는 사용자 승인 없이는 결정하지 않는다.
4. 구현·실험·실데이터·정확도·절감액은 증거가 없으면 `UNVERIFIED`로 표시한다.
5. mock, Sandbox, 정적 계산, API 연결 성공을 실제 사용자·실계좌·운영 성과로 표현하지 않는다.
