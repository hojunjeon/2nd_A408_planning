# Design B — P-02 상태 변화 후 유지·중단·복구·이의신청 결정

## Direction 1 — 근거 고정형 상태 결정표

problem_id: P-02

user_moment: 수혜 중 또는 신청 직후에 소득 입금, 취업·퇴사, 이사·계약 변경, 반려 통지를 받아 지금 상태를 유지할지 중단·복구·이의신청할지 정해야 하는 순간.

solution_concept: 사용자가 사건 유형과 발생일, 현재 정책 상태를 직접 선택하면 버전·기준일이 붙은 규칙표가 네 가지 경로를 계산한다. 각 경로에는 적용 조항, 필요한 확인 항목, 신고·보완·재신청·상담의 다음 행동을 붙이고, 조건이 빠지거나 원문이 충돌하면 `UNVERIFIED`로 멈춘다.

why_current_method_fails: 포털의 상태 화면, 공고 PDF, 문자, 첨부 목록이 분리되어 있어 사용자가 기준일·중단 사유·신고기한을 직접 대조한다. 단순 알림은 어떤 조항에 근거한 경고인지와 복구·이의신청 가능성을 함께 보존하지 못한다.

provider_data_used: 온통청년·복지로·정부24의 공개 정책 목록·상세·기준·신청방법을 데이터로 사용하고, 실제 신청은 운영기관·복지로·정부24·지자체의 원문 신청 URL로 연결한다. 애매한 건은 온통청년·복지로·서민금융진흥원 등 공식 상담 연결로 넘긴다. 인증정보, 금융계정, 원문 SMS 자동수집, MyData·스크래핑은 사용하지 않는다. 근거 범위는 [problem-synthesis.md](problem-synthesis.md)와 [worker-C.md](worker-C.md)의 제공자 구분을 따른다.

non_ai_alternative: 같은 규칙표를 인쇄 가능한 체크리스트와 사용자의 수동 달력·스프레드시트로 제공한다. 자유 문장을 해석하지 않고 사건 유형을 직접 고르게 하면 AI 없이도 동일한 결정 경로를 재현할 수 있다.

ai_required_reason: 없음. 구조화된 사건, 버전 고정 원문, 명시적 분기만으로 충분하다. 정보가 부족하면 추정하지 말고 추가 입력 또는 공식 상담으로 보낸다.

risks: 정책 원문·API가 바뀌거나 사용자가 기준일을 잘못 입력하면 규칙표가 낡거나 잘못된 경로를 낼 수 있다. 예비 확인은 법적 결정이 아니며, 운영기관의 최종 판단·환수·중단 금액은 `UNVERIFIED`로 남긴다. 원문을 읽지 못하면 `BLOCKED`로 표시하고 신청 완료나 자격 유지를 약속하지 않는다.

how_to_test: 실제 제출 없이 소득 변동, 주소 변경, 반려, 보완 가능, 기한 누락, 원문 충돌을 포함한 비식별 합성 사례를 넣고 기대 분기·근거 조항·기준일을 대조한다. 원문 버전을 바꿨을 때 결과가 달라지는지, 누락·충돌 입력이 항상 `UNVERIFIED`가 되는지 확인한다.

## Direction 2 — 네 갈래 복구 콕핏

problem_id: P-02

user_moment: 중단 또는 반려 알림을 받은 직후, 긴 공고를 다시 읽기보다 “계속 받을 수 있나, 무엇을 언제 제출하나, 누구에게 물어보나”를 빠르게 정리해야 하는 순간.

solution_concept: 한 화면에 현재 상태, 상태가 바뀐 사건, 마지막으로 확인한 원문·기준일, 남은 기한, 네 갈래 카드(유지·중단·복구·이의신청)를 배치한다. 사용자가 카드를 선택하면 필요한 증빙과 기관 연결만 단계적으로 펼치고, 이전 확인 기록과 보류 사유를 유지한다. 결과는 판정이 아니라 다음 확인 행동이다.

why_current_method_fails: 현재 흐름은 마이페이지, 공고, 첨부, 상담번호를 오가며 사용자가 스크린샷·메모로 상태를 이어 붙여야 한다. 정보가 있어도 선택지와 기한이 한 화면에서 비교되지 않아 중단 후 재개·이의신청 같은 경로가 쉽게 누락된다.

provider_data_used: 공공 제공자의 정책 설명·구비서류·상태 확인 안내를 데이터 카드로 표시하고, 신청·보완은 각 운영기관·복지로·정부24·지자체 화면으로 연결한다. 이의가 애매하면 해당 기관과 온통청년·복지로·서민금융진흥원 상담을 연결한다. 제공자는 경쟁자가 아니라 원문·신청·상담 연결원이며, 개인 금융 로그인·가족 정보·SMS 원문은 기본 수집하지 않는다.

non_ai_alternative: 동일한 네 갈래 화면을 정적 웹 체크리스트와 인쇄물로 제공하고, 사용자가 상태·기한·증빙을 직접 입력한다. 공식 원문 링크와 전화·방문 경로만 붙여도 UX 개선 효과를 AI 없이 검증할 수 있다.

ai_required_reason: 없음. 이 방향의 핵심 가치는 정보 위계, 접근성, 보류 상태, 행동 선택의 UX다. 요약이 필요해도 사용자가 요청한 경우에만 원문 인용 기반으로 제공하고, 기본 흐름은 결정론적으로 유지한다.

risks: 카드가 단순화되면 복잡한 예외를 숨기거나 긴급성을 과장할 수 있고, 색상·알림이 확정 판정처럼 보일 수 있다. 정책 변경·정적 fetch 실패·접근성 문제는 `UNVERIFIED` 또는 `BLOCKED`로 표시하며, 운영기관의 결정과 실제 접수 결과를 대체하지 않는다.

how_to_test: 동일한 합성 사례를 기존 포털·메모 흐름과 네 갈래 화면에서 수행하게 해 사용자가 선택한 경로, 찾은 기한, 확인한 근거, 놓친 항목을 비교한다. 모바일·키보드·저시력 조건에서도 네 선택지와 보류 상태가 구분되는지 확인하고, 어느 화면에서도 “수혜 확정” 문구가 나오지 않는지 점검한다.

## Direction 3 — 이의·반려 문서 해석 보조

problem_id: P-02

user_moment: 반려 사유, 중단 통지, 보완 요청처럼 형식이 제각각인 문자·문서를 받은 뒤, 어떤 사실이 문제이고 유지·중단·복구·이의신청 중 무엇을 검토해야 하는지 해석해야 하는 순간.

solution_concept: 사용자가 민감정보를 가린 문서나 직접 입력한 문장을 선택적으로 제공하면 AI가 사건·사유·기한·요구 증빙의 후보를 추출하고, 관련 원문의 버전·문장을 함께 제시한다. 서로 맞지 않는 항목은 질문으로 되돌리고, 네 가지 경로는 “검토 후보”로만 보여준다. 제출물 작성과 접수는 사용자가 운영기관 원문 화면에서 직접 한다.

why_current_method_fails: 자유 형식 통지와 여러 공고를 사람이 수동으로 대조하면 날짜·예외·보완 기한을 놓치기 쉽다. 범용 챗봇은 출처·버전을 보존하지 않으면 그럴듯한 사유나 확정 판정을 만들 수 있고, 포털 상태값만으로는 반려 이유의 맥락을 설명하기 어렵다.

provider_data_used: 온통청년·복지로·정부24와 해당 운영기관의 공개 원문·정책 상세·신청방법을 근거 데이터로 사용한다. 추출 결과의 신청 링크는 운영기관·복지로·정부24·지자체로 연결하고, 애매한 사례는 공식 상담으로 연결한다. 문서·문자·금융계정·주민번호를 서버에 기본 전송하지 않으며, MyData·스크래핑·제공자 로그인 대행은 하지 않는다.

non_ai_alternative: 사용자가 통지에서 사건 유형·사유·날짜·기한을 직접 입력하는 구조화 양식과 조항별 체크리스트를 제공한다. 입력 부담은 크지만 검증 가능한 보수적 대안이며, 해석이 안 되면 상담기관으로 보낸다.

ai_required_reason: 이 방향의 한정된 보조 단계에는 AI가 필요하다. 통지의 표현·순서·문서 형식이 제각각이라 사건·기한·요구 증빙을 사람이 미리 정한 필드로만 받으면 누락된 표현을 포착하기 어렵기 때문이다. 다만 원문 연결·규칙 확인·최종 선택은 결정론적 검증과 사용자 확인이 담당하며, AI가 없거나 불확실하면 위의 수동 양식으로 폴백한다.

risks: 잘못된 추출·요약, 낡은 조항 연결, 민감 문서 노출, AI 답변에 대한 과신, 이의신청 사유의 과장 위험이 있다. 모든 문장에 원문·기준일을 붙이고 근거가 없으면 `UNVERIFIED`, 원문을 확인할 수 없으면 `BLOCKED`로 중단한다. 실제 탈락·환수·이의 결과와 금액은 주장하지 않는다.

how_to_test: 사건 유형별로 개인정보를 제거한 합성 통지·반려문·보완요청을 만들고, 추출된 사건·사유·기한·증빙을 정답 표와 비교한다. 출처 문장과 버전이 빠진 출력, 기관이 불명확한 출력, 날짜가 충돌하는 출력은 자동 보류되는지 확인하며 실제 기관 제출은 하지 않는다.

## Direction 4 — 상태 변화 장부와 출처 변경 자동화

problem_id: P-02

user_moment: 신청 후 여러 달 동안 소득·주소·가구·계약과 정책 원문이 각각 바뀌어, 어떤 정책 기록을 다시 검토하고 신고·보완·재신청·이의신청 기한을 놓치지 않아야 하는 순간.

solution_concept: 사용자의 확인·변경 사건을 누적 장부로 기록하고 정책별 상태, 근거 원문 버전, 기준일, 증빙, 기한을 연결한다. 공개 정책 데이터·페이지의 새 버전이나 사용자 사건이 관련 상태를 바꿀 때만 “검토 필요” 작업을 자동 생성하고, 신청·신고·이의 제출은 항상 사용자가 확인한 뒤 제공자 화면에서 수행한다.

why_current_method_fails: 스크린샷, 메모, 캘린더는 상태와 근거 버전을 연결하지 않아 정책 변경이나 새로운 소득 사건이 기존 판단을 무효화했는지 알기 어렵다. 한 번의 마감 알림은 중단 후 복구·대체·이의 경로와 증빙 누락을 추적하지 못한다.

provider_data_used: 온통청년·복지로·정부24의 공개 정책 목록·상세·지원조건 API/페이지를 데이터로 받아 출처 버전을 기록하고, 운영기관·복지로·정부24·지자체의 신청 URL과 공식 상담을 연결한다. 실제 수급 상태는 사용자가 입력하거나 제공자 화면에서 확인한 값만 기록하며, 계좌·가족·SMS 자동수집, 금융 MyData, 스크래핑, 자동 제출은 범위 밖이다.

non_ai_alternative: CSV 또는 스프레드시트 장부, 공식 페이지 북마크, 수동 달력과 변경 확인 체크리스트를 제공한다. 자동화가 중단되어도 사용자는 마지막으로 확인한 원문과 보류 작업을 내보낼 수 있어야 한다.

ai_required_reason: 없음. 출처 버전 비교, 사건-정책 연결, 중복 작업 제거, 기한 계산은 데이터 모델과 결정론적 규칙으로 처리한다. 자유 문장을 받지 못하면 구조화 입력을 요구하고 `UNVERIFIED`로 남긴다.

risks: API 응답·페이지 구조 변경, 오래된 캐시, 오탐 변경 감지, 중복 알림, 민감한 사건 장기 보관, 자동 작업이 제출을 재촉하는 위험이 있다. 모든 작업에 출처·확인 시각·버전을 남기고, 연결 실패·최신성 미확인은 `UNVERIFIED`/`BLOCKED`로 표시하며 사용자의 확인 없이는 외부 기관에 요청하지 않는다.

how_to_test: 버전이 다른 정책 원문과 합성 사건 스트림을 넣어 영향받은 정책만 검토 작업을 만드는지 확인하고, 같은 사건을 재처리해 중복 작업이 생기지 않는지 검증한다. 각 작업의 출처·기준일·보류 사유와 API 장애 시 상태가 보존되는지 확인하며 실제 계정 연결·신청·수급 결과는 테스트하지 않는다.
