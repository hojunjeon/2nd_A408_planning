# Setup: 청년 금융 내비게이션 통합 기획서

> Setup은 공식 근거를 확인한 조건과 계산 결과만 하나의 미래 자산 시나리오로 연결한다. 대학생·취준생·사회초년생이 정책 신청, 소득 변화, 할부 상환을 따로 판단하지 않도록 돕는 청년 금융 내비게이션이다.

| 항목 | 내용 |
|---|---|
| 대상 사용자 | 대학생·취준생·사회초년생 등 청년층 |
| 사용 시점 | 정책 신청 전, 정책 수혜 중, 할부 지출 후, 미래 자산 계획 시점 |
| 핵심 가치 | 자격·비용·미래 금액의 근거를 한 흐름에서 비교하고 사용자가 다음 행동을 직접 선택하도록 돕는다. |

## 1. 어떤 문제를 해결하는가

청년 금융 정보는 정책 포털, 공고문, 카드 명세, 자산 계산기에 흩어져 있다. 정책 신청 전에는 자격과 신청 순서를 확인해야 한다. 정책 수혜 중에는 소득 변화가 자격에 미치는 영향을 살펴야 하고, 할부 결제 후에는 유지와 중도상환 비용을 비교해야 한다. 이 판단이 서로 연결되지 않으면 한 선택이 미래 자산에 미치는 차이도 직접 계산해야 한다.

Setup이 해결하려는 핵심 문제는 정보의 양이 아니라 의사결정의 단절이다.

| 확인 수준 | 현재 근거 | 이 문서에서의 해석 |
|---|---|---|
| 확인된 배경 | 2024년 전국민 금융이해력 조사에서 20대 점수는 62.6점으로 성인 평균 65.7점보다 낮았다. ([한국은행](https://www.bok.or.kr/portal/bbs/B0000502/view.do?menuNo=201265&nttId=10091152)) | 청년층이 금융 의사결정을 이해하고 실행하도록 돕는 맥락은 확인됐다. |
| `UNVERIFIED` 문제 가설 | 정책별 자격·중복 제한·신청 시점이 달라 비교가 어렵다. | 정책 1~3종의 공고 원문과 사용자 조사로 확인해야 한다. |
| `UNVERIFIED` 문제 가설 | 단기 소득 변화가 정책 자격에 영향을 줄 수 있지만 사용자가 미리 계산하기 어렵다. | 정책별 소득 산정 방식과 기준일을 확인해야 한다. |
| `UNVERIFIED` 문제 가설 | 할부 유지와 중도상환의 비용 차이가 잘 보이지 않는다. | 카드사 공식 계산식과 실제 명세 예시로 확인해야 한다. |

마지막 세 항목은 원기획에서 출발한 가설이다. 공식 조항, 계산식, 사용자 조사로 확인하기 전에는 사실이나 성과로 표현하지 않는다.

## 2. Setup은 어떻게 해결하는가

Setup은 신청 전, 수혜 중, 지출 후에 흩어진 판단을 같은 입력값과 시간축으로 연결한다. 자격과 금액은 규칙과 계산식으로 산출하고, 확인되지 않은 혜택이나 절감액은 미래 자산에 자동으로 넣지 않는다.

```mermaid
flowchart LR
    A["입력<br/>프로필·거래·소득·할부 조건"] --> B["신청 전<br/>정책 자격과 신청 순서"]
    B --> C["수혜 중<br/>소득 변화와 자격 조건"]
    C --> D["지출 후<br/>할부 유지와 중도상환 비교"]
    D --> E["미래<br/>선택한 금액만 자산 시나리오에 반영"]
    E --> F["행동<br/>if-then 계획 저장"]
```

### 핵심 기능

| 기능 | 사용자가 하는 일 | 앱이 하는 일 | 사용자가 확인하는 결과 | 현재 경계 |
|---|---|---|---|---|
| 정책 찾기·신청 로드맵 | 나이, 지역, 소득을 입력한다. | 공식 근거를 확인한 정책 1~3종의 자격, 중복 제한, 기준일, 신청 순서를 규칙으로 비교한다. | 신청 가능성, 판단 근거, 다음 확인 순서를 본다. | 전체 정책의 최적 순서를 약속하지 않는다. 공고 조항과 API 응답은 `UNVERIFIED`다. |
| 자격 유지 컷오프 | 누적소득과 예상 소득 변화를 입력한다. | 정책별 소득 기준과 입력값의 차이를 다시 계산한다. | 조건이 달라질 가능성, 기준일, 확인할 운영기관을 본다. | 자격을 확정하거나 근무 축소를 권하지 않는다. 산정 방식은 `UNVERIFIED`다. |
| 할부 수수료 비교 | 잔여 원금, 수수료율, 남은 회차·결제일, 중도상환 예정액을 입력하고 확인된 지원금 입금 예정일을 선택한다. | 할부 유지와 중도상환의 예상 총비용을 같은 조건으로 계산한다. | 두 선택의 비용 차이와 계산 가정을 본다. | 계산식이 확인된 예시 1건으로 제한한다. 카드사별 조건은 `UNVERIFIED`다. |
| 미래 자산 계획 | 확정된 혜택과 실제로 저축할 금액을 선택한다. | 현재 경로와 선택한 시나리오의 미래가치 차이를 계산한다. | 선택 전후의 자산 차이와 적용한 금리·기간·납입액을 본다. | 투자 수익률을 예측하지 않는다. 사용자가 선택하지 않은 절감액은 반영하지 않는다. |

거래내역 입력·분류와 소비 변화 탐지는 네 기능에 필요한 공통 기반이다. 사용자는 카드사 파일을 한 번 올리고 분류 결과를 수정할 수 있다. 앱은 빈도, 시간대, 카테고리 변화를 계산해 미래 자산 시나리오의 입력 후보를 만든다. 반영 여부는 사용자가 결정한다. 선택한 시나리오는 “금요일 밤 배달 앱을 열면 마트 픽업으로 바꾼다”와 같은 if-then 계획으로 저장한다.

## 3. 왜 이 기능과 기술을 연결하는가

| 연결 | 이유 |
|---|---|
| 문제 → 하나의 내비게이션 | 정책, 소득, 할부를 따로 보면 한 선택의 전체 결과를 비교하기 어렵다. 같은 금액 산정 기준과 시간축으로 연결해야 한다. |
| 내비게이션 → 네 핵심 기능 | 사용자가 실제로 판단해야 하는 시점이 신청 전, 수혜 중, 지출 후, 미래 계획으로 이어지기 때문이다. |
| 핵심 기능 → 규칙과 계산식 | 정책 자격과 금액은 같은 입력에서 같은 결과가 나와야 하며, 근거와 계산 과정을 다시 확인할 수 있어야 한다. |
| 계산 결과 → LLM 설명 | LLM은 이미 계산된 구조화 결과를 읽기 쉽게 설명하는 데 쓰인다. 금액이나 자격을 직접 결정하지 않는다. |

### 판단과 설명의 경계

```mermaid
flowchart LR
    I["입력값"] --> R["규칙·계산식"]
    R --> O["출처·기준일·가정이 붙은 결과"]
    O --> L["LLM의 분류 후보·설명"]
    L --> U["사용자의 확인과 선택"]
```

| 담당 | 하는 일 | 하지 않는 일 |
|---|---|---|
| 규칙과 계산식 | 정책 조건 비교, 소득 임계값 비교, 할부 비용과 미래가치 계산 | 확인하지 않은 정책이나 카드 조건을 추정하지 않는다. |
| LLM | 새 가맹점의 분류 후보를 제시하고 구조화된 계산 결과를 문장으로 바꾼다. | 정책 자격, 지원금, 수수료, 미래 자산 금액을 판정하지 않는다. |
| 사용자 | 근거와 가정을 확인하고 시나리오 반영 여부를 선택한다. | 앱의 추정값을 확정 사실로 받아들이도록 요구받지 않는다. |

구조화 출력은 정해진 데이터 형식을 지키게 할 뿐 내용의 정확성까지 보장하지 않는다. 따라서 허용값 검사, 사용자 교정, 공식 근거 대조가 함께 필요하다. ([OpenAI Structured Outputs](https://openai.com/index/introducing-structured-outputs-in-the-api/))

## 4. 기술적으로 만들 수 있는가

| 기능 | 최소 구현 | 선택 이유 | 현재 검증 수준 |
|---|---|---|---|
| 거래 입력·분류 | Pandas·openpyxl로 파일을 정규화하고 규칙에 따라 먼저 분류한다. 새 가맹점만 LLM의 구조화 출력으로 보완한다. | 운영 금융 API 없이 여러 거래를 한 번에 처리하고 LLM 사용 범위를 줄일 수 있다. | 파일 파싱은 `[문서상 PoC]`, 한국 가맹점 분류 비교는 `[검증 예정]` |
| 소비 변화 탐지 | 카테고리별 주간 rolling z-score | 개인의 적은 거래에서도 기준을 설명하기 쉽고 ARIMA나 IsolationForest보다 단순하다. | `[검증 예정]` |
| 정책 자격·신청 순서 | 기준일이 있는 JSON 조건 판정기와 정책 간 충돌·선후 규칙 | 자격과 신청 순서는 문장 생성보다 출처가 있는 조건 비교에 가깝다. | API 필드와 공고 조항이 `UNVERIFIED` |
| 소득 컷오프 | 자기입력 누적소득과 정책별 임계값 비교 | 입력값과 정책 기준의 차이를 같은 방식으로 다시 계산할 수 있다. | 산정 방식과 기준일이 `UNVERIFIED` |
| 할부 비용 비교 | 자기입력 조건을 사용하는 결정론적 계산식 | 같은 입력에서 유지와 중도상환 비용을 재현할 수 있어야 한다. | 카드사별 계산식과 조건이 `UNVERIFIED` |
| 미래 자산 시나리오 | `numpy-financial fv()`와 시나리오 간 차이 계산 | 고정 금리·납입액·기간은 확률 모형보다 결정론적 계산이 알맞다. ([공식 문서](https://numpy.org/numpy-financial/latest/fv.html)) | 계산은 `[문서상 PoC]`, 현재 저장소에는 재현 코드가 없음 |
| 설명·실행 계획·차트 | 단순 템플릿, 제한된 LLM 문장 재작성, 기본 선형 차트 | 자유 생성과 복잡한 시각화 없이 계산 결과와 다음 행동을 전달할 수 있다. | 설계만 있으며 `[검증 예정]` |

`[문서상 PoC]`는 두 원문에 실행 검증을 했다고 적혀 있지만 이 저장소에서 다시 실행할 코드와 테스트를 확인하지 못했다는 뜻이다. `[검증 예정]`은 검증 방법만 정해졌고 결과가 없음을, `UNVERIFIED`는 공식 명세·근거·공수 중 하나 이상을 확인하지 못했음을 뜻한다.

정책 자격 유지와 할부 비교는 핵심 범위지만 공식 규칙과 공수가 아직 정해지지 않았다. 따라서 일부 계산의 구현 가능성과 별개로 전체 MVP를 5주 안에 완성할 수 있다는 판단은 현재 `UNVERIFIED`다.

## 5. 이번 기획의 범위

| 구분 | 내용 |
|---|---|
| 포함 | 카드사 파일 입력, 거래 분류·교정, 소비 변화 설명, 검증한 정책 1~3종의 자격·신청 순서, 소득 컷오프 시나리오 1종, 할부 비교 예시 1건, 미래 자산 비교, if-then 계획 |
| 조건부 | 정책·소득·할부 기능은 공식 공고와 계산식이 확인된 범위만 구현하고 시연한다. |
| 제외 | 실계좌 운영 연동, 웹 스크래핑, 자동 상품 가입·정책 신청, 근무 축소 권고, 투자 수익률 예측, Monte Carlo 시뮬레이션 |

CSV 업로드와 자기입력은 최종 제품의 차별점이 아니라 핵심 가설을 확인하기 위한 입력 수단이다. 운영 금융 데이터 연동은 이용 권한, 공식 명세, 보안 요건을 확보한 뒤 별도로 검토한다.

## 6. 구현 전에 확인할 사항

| 확인할 사항 | 확인해야 하는 이유 | 현재 상태 |
|---|---|---|
| 정책 1~3종의 공식 자격, 중복 제한, 신청 순서, 소득 산정 기준일 | 정책 로드맵과 컷오프 결과의 근거가 된다. | `UNVERIFIED` |
| 카드사 예시 1건의 잔여 원금, 수수료, 중도상환 조건 | 할부 유지와 중도상환의 예상 총비용을 재현하는 데 필요하다. | `UNVERIFIED` |
| 실제 카드사 파일 형식과 한국 가맹점 분류 결과 | 입력 파서와 분류 방식이 실제 데이터에서도 동작하는지 확인해야 한다. | 일부 `[문서상 PoC]`, 실측 `[검증 예정]` |
| 소득 컷오프와 할부 비교의 구현 공수 | 두 기능을 포함한 전체 범위의 구현 가능성을 판단해야 한다. | `UNVERIFIED` |

현재 명시적인 `BLOCKED` 항목은 없다. 다만 공식 근거를 확인하지 못한 기능은 범위를 넓히지 않고 검증된 예시로 제한한다.
