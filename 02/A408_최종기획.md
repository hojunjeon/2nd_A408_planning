  * **Frontend (2명)**: React / TypeScript 기반 **반응형 웹** 개발. 입력·시나리오 상태·접근성은 1명, 결과 표·차트·근거 서랍은 1명이 담당

  3. 근거 없는 추천 대신 출처·시행기간·가정·확인 필요 조건을 함께 보여주는 **제한된 AI 설명 계층** 제공

## 2. 문제 정의 및 해결 방안 (Problem & Solution)

### 🔴 Problem (기존 서비스의 한계)

1. **정책·세제·상품·대출 정보가 영역별로 분절됨**:
   정책 검색, 세액공제 조회, 예적금 비교, 대출 계산기는 각자 다른 기준일과 가정을 쓴다. 사용자는 서로 다른 화면의 금액을 직접 옮겨 적어야 하고, 하나를 바꾸면 나머지 현금흐름까지 달라진다는 점을 확인하기 어렵다.
2. **지급·정산·만기·상환 시점이 서로 다름**:
   청년월세는 월별로, 월세 세액공제는 과세연도 정산월에, 적금 이자와 정부기여금은 계약상 귀속일에, 대출 이자는 약정 상환일에 반영된다. 총액만 보면 어느 달에 현금이 부족한지 놓친다.
3. **개별 효과의 합과 결합 결과가 다른 이유가 보이지 않음**:
   정책 현금을 적금에 넣으면 이자 경로가 바뀌고, 대출에 넣으면 이자비용이 줄어든다. 그러나 기존 도구는 각 영역 안의 계산만 제공하므로 상호작용을 설명하지 못한다.

### 🟢 Solution (셋업의 차별화된 해결책)

1. **버전 규칙 기반 3상태 진단 Engine**:
   검수된 청년월세, 월세액 세액공제, 청년미래적금 규칙만 `ELIGIBLE`, `INELIGIBLE`, `NEEDS_CONFIRMATION`으로 판정한다. 증빙·예산·기관 심사·미확정 조합은 적격으로 단정하지 않고 원문 링크와 함께 남긴다.
2. **36개월 결합 원장 Simulation Engine**:
   정책 현금, 실현 가능한 세제 정산, 예금·적금 납입과 만기, 대출 원리금·추가상환을 같은 월별 원장에 배치한다. 기본·요소별·전체 결합 실행으로 개별 효과와 상호작용을 분리한다.
3. **계산 권한 없는 AI Explanation Layer**:
   AI는 합성 데이터의 확정 결과를 쉬운 문장으로 바꿀 뿐 금액·자격·스케줄을 만들지 못한다. 실패하면 결정론적 템플릿으로 전환하고 코어 데모는 AI 없이도 성립한다.

## 3. 핵심 AI 기능 상세 명세 (Core AI Features)

### 🤖 ① [Policy & Evidence Engine] 버전 규칙 판정 & 근거 서랍

* **수동 검수 스냅샷 기본값**:
  * 운영자가 공식 원문 URL, 게시·시행일, 확인일, 짧은 근거문, 해시를 저장한다.
  * 온통청년 API와 Finlife API는 1주차 선택 PoC로만 시도하고 실패하면 데모에서 제거한다. API 성공 여부가 코어 계산을 막지 않게 한다.

* **3상태 판정**:
  * `ELIGIBLE`은 필요한 입력과 규칙이 충족된 상태, `INELIGIBLE`은 확정 탈락, `NEEDS_CONFIRMATION`은 증빙·예산·상호작용·공고가 미확정인 상태다.
  * 규칙은 `DRAFT`, `APPROVED`, `NEEDS_REVIEW`, `RETIRED` 상태를 가지며 `APPROVED`만 계산에 쓴다. 원문 변경이나 출처 충돌은 즉시 재검토로 보낸다.

### 🤖 ② [Combined Ledger Engine] 36개월 결합 현금흐름 & 효과 분해

* **월별 원장 계약**:

$$NetWorth_t = Cash_t + Saving_t - Loan_t$$

* **동작 프로세스**:
  1. **입력**: 월 소득·지출, 거주·고용, 초기 가용현금과 최소 보유현금, 새 상품 원금·납입액, 대출 잔액·금리·방식·수수료를 받는다. 기존 계약 상품의 잔여 일정은 MVP 범위에서 제외한다.
  2. **재실행**: `N0`, 정책만, 세제만, 새 저축만, 추가상환만, 전체 결합 여섯 경로를 같은 입력으로 돌린다.
  3. **분해**: 개별 효과의 합과 결합 효과의 차이를 상호작용으로 표시하고, 각 경로를 독립 골든 원장과 원 단위 ±1원으로 대조한다.

* **결과 노출**:
> "36개월 말 순자산, 월별 현금 최저점, 저축·부채 경로, 개별·결합 효과에는 규칙 버전, 공식 링크, 시행기간, 기준일, 사용자 가정을 함께 연다."

### 🤖 ③ [Guarded Explanation Layer] 제한된 AI 설명 & 안전 폴백

* **AI 경계**:
  * 자격 판정과 금액 계산은 금지한다. AI는 구조화된 확정 결과 JSON과 인용 목록만 받는다.
  * 실제 사용자 입력은 외부 LLM에 전송하지 않고 합성 데이터 모드에서만 설명을 켠다.

* **안전 기준**:
  * 근거 없는 숫자·자격 0건, 상태 보존 100%, 인용 링크 유효 100%를 통과해야 한다.
  * 한 건이라도 위반이 재현되면 AI를 끄고 결정론적 문장 템플릿으로 전환한다.

## 4. 데이터 수집 및 마이데이터 제약 극복 전략

### ⚠️ 마이데이터 법적 제약 및 현주소

* 마이데이터 허가가 없는 프로젝트 팀은 은행·카드사 실계좌와 실대출 자료를 자동 조회할 수 없으므로 MVP는 실계좌 연동 자체를 범위에서 제외한다.

### ❓ 백그라운드: 왜 마이데이터 연동이 막혀있는가?

1. **법적 제약 (마이데이터 사업자 라이선스)**:
   신용정보법상 마이데이터 업무에는 허가 요건이 있으므로 학생·프로젝트 팀이 상용 계좌 API를 직접 호출할 수 없습니다. 관련 근거는 신용정보법 스냅샷으로 확인했습니다.
2. **운영적 제약 (인증·계약·보안)**:
   오픈뱅킹과 금융 마이데이터는 이용기관 계약·승인·OAuth·보안 검토를 필요로 합니다. 데모 목적으로 민감한 인증정보를 수집하는 것보다 집계값 입력이 안전합니다.

### 💡 팀원 및 심사위원 설득을 위한 데이터 해결책 (이원화 전략)

```
[1. 발표 & 심사용 (Technical Proof) : 검수 규칙 + 골든 원장]
 ├─ 이유: 실계좌 없이도 규칙·계산·근거 추적이 동작함을 증명해야 함.
 ├─ 방식: 청년월세·월세액 세액공제·청년미래적금 3규칙을 버전 JSON으로 구조화하고,
 │        예금·적금·대출·세제 골든 원장을 독립 계산표와 ±1원으로 대조함.
 └─ 실연: 결과 항목에서 규칙 ID → source ID → 공식 원문까지 3클릭 이내로 역추적함.

[2. 사용자 입력용 (Usability Proof) : 합성 데이터 + 자기입력]
 ├─ 1. 정책 데이터 : 검수된 중앙 원문 스냅샷, 선택형 온통청년 API PoC
 ├─ 2. 금융 상품 : ProductSnapshot(공식 조건) + SavingPositionInput(사용자 금액) 분리
 ├─ 3. 세제 : 과세연도별 TaxYearState(산출세액, 원천징수·기납부세액, 정산월) 입력
 └─ 4. Step-by-Step 진단 UI : 민감정보 없이 집계값만 입력하고 Check Answers로 재확인

```

### 🔍 공공·금융 API 접근성 검증 결과 (2026-08-23/24 확인)

* **실계좌·오픈뱅킹**: 자체 운영 사용은 BLOCKED다. 허가·계약 없이 조회 기능을 만들지 않는다.
* **온통청년 API**: 회원가입, 인증키 신청, 담당자 승인 구조가 공식 안내로 확인됐다. 실제 응답 필드·호출 한도는 PoC 전까지 UNVERIFIED다.
* **Finlife API**: 2026-08-24 재검사에서 2xx와 TLS timeout이 섞였고 실제 API 호출은 하지 않았다. 따라서 문서 접근성과 런타임을 UNVERIFIED로 두고 필수 경로에서 제외했다.
* **KOSIS Open API**: 통계 참고값 후보로 문서를 확인했으며 계산의 필수 입력으로 쓰지 않는다.

### 💡 해법: 버전 JSON 레지스트리란? (2026-08-24 감사 완료)

> **"API 실패나 정책 변경이 코어 데모를 멈추지 않게 하려고, 검수된 규칙과 상품 조건만 Git 코드 리뷰로 활성화하는 읽기 전용 근거 저장소"**입니다.

#### ① 저장 대상과 실행 대상의 분리

* **영속 JSON**: `SourceDocument`, `RuleSet`, `ProductSnapshot`만 보존한다. 원문 URL·날짜·해시·근거문과 상품의 공식 금리·기간·과세·귀속 계약이 들어간다.
* **비영속 입력**: 사용자의 새 상품 원금·납입액, 대출 계약값, 세금 정산값, 시나리오 결과는 응답 뒤 저장하지 않는다.
* **연결표**: `source_ids`로 규칙과 원문을 연결하고, 결과 화면에서 규칙 ID → 원문 → 확인일을 열 수 있게 한다.

#### ② 왜 이것이 기술적 증명(Proof)이 되는가?

검수 규칙은 다음처럼 상태와 유효기간을 명시합니다.

```json
{
  "example_only": true,
  "rule_id": "POLICY-2026-001",
  "program_code": "YOUTH_RENT_2026",
  "version": "2026-03-18",
  "rule_scope": "CONFIRMED_2026_AWARD_PAYMENTS",
  "application_window": {
    "from": "2026-03-30",
    "to": "2026-05-29"
  },
  "award_payment_window": {
    "start_field": "confirmed_award_payment_start",
    "end": "2028-12-31"
  },
  "benefit": {
    "formula_id": "CAP_MINUS_VERIFIED_OFFSETS",
    "parameters": { "cap_won": 200000 }
  },
  "review_status": "DRAFT",
  "confidence": "PARTIAL"
}
```

* **설득 논리**:
"위 JSON은 실행할 수 없는 스키마 예시입니다. 실제 APPROVED 규칙에는 연령 기준일, 가구·소득·재산, 증빙, 선정 상태, 지급 가능 기간을 모두 넣습니다. 신청 종료일과 기존 선정자의 지급 종료일을 한 필드에 섞지 않아 2027년 이후 조건을 자동 복사하지 않는 것이 핵심입니다."

## 5. 파트별 기술 아키텍처 및 역할 분담 (R&R)

### 🔹 Frontend (2명) - `React` + `TypeScript`

* **반응형 웹 구현**: React와 TypeScript 단일 웹으로 입력, Check Answers, 시나리오 편집, 결과 비교를 개발한다. 기기 전용 권한이 필요 없어 5주 배포 부담이 낮다.
* **결과 UI**: 월별 원장 표, 최소 차트, 효과 분해, 근거 서랍을 만든다. 차트에는 대체표와 텍스트 요약을 붙이고 색만으로 상태를 구분하지 않는다.
* **접근성**: 키보드 핵심 흐름과 상태 표시 대체를 검사한다.

### 🔹 Backend (2명) - `Spring Boot` + `Java`

* **규칙·API**: 버전 JSON 조건 트리, 3상태 판정, 출처·해시 추적, 선택형 API PoC를 담당한다.
* **계산 엔진**: Java `BigDecimal`과 `LocalDate` 순수 함수로 월별 원장, 예금·적금·대출·세제 계산을 만든다.
* **통합**: API 계약, 프런트 통합, 경계값·만료 규칙 테스트를 담당한다.

### 🔹 AI / Data (2명)

* **AI/Data 1**: 서비스 설계, 정책 원문·규칙 모델링, 참여자 모집과 과업 진행, 데모 서사를 담당한다.
* **AI/Data 2**: 골든 원장, 회귀·보안·접근성 독립 감사, 과업 관찰, Docker Compose 배포, 선택 AI 설명을 담당한다.
