## 0. 한 문장 제품 정의

사용자가 소득·지출·거주·고용·예금·적금·대출 조건과 바꾸어 볼 시점을 입력하면 앱이 출처와 시행 기간을 명시한 청년 정책·세제 규칙, 결정론적 금융 수식으로 36개월 현금흐름을 다시 계산한다. 미래 순자산 경로, 개별 효과, 결합 효과, 확인이 필요한 조건을 나란히 보여주는 서비스다.

| 사용자 행동 | 앱 처리 | 결과 |
|---|---|---|
| 현재 상황과 바꾸어 볼 값을 입력한다 | 정책·세제 자격을 판정하고 예금·적금·대출 조건을 월별 원장에 배치한다 | 기본 시나리오와 변경 시나리오의 현금, 저축, 부채, 순자산 곡선 |
| 정책 수혜, 세제 효과, 저축, 상환 시점을 하나씩 켜고 끈다 | 같은 입력과 규칙 버전으로 해당 요소만 다시 계산한다 | 개별 효과, 전체 결합 효과, 요소 간 상호작용 |
| 결과의 근거를 연다 | 규칙 버전, 원문, 시행 기간, 금리 기준일, 사용자 가정, 미확정 조건을 연결한다 | 계산 이유와 공식 기관에서 다시 확인할 항목 |

### 결과 상태와 출처 등급

- `VERIFIED`: 공식 원문과 운영 기관 자료 또는 독립 자료로 확인했다.
- `PARTIAL`: 공식 근거는 있으나 적용 범위나 세부 운영 규칙이 완전하지 않다.
- `INFERENCE`: 확인한 사실에서 도출한 제품·기술 판단이다.
- `UNVERIFIED`: 기준일에 확정 공고나 충분한 근거를 확보하지 못했다.
- `BLOCKED`: 계약, 허가, 법률 검토, 증빙이 없으면 진행할 수 없다.
- `ASSUMPTION`: 사용자가 비교하려고 직접 정한 값이다. 사실값과 구분한다.
- 출처 A는 법령·정부 원문·공식 통계·표준·동료 평가 연구, B는 공식 서비스·운영 기관·제품·API 문서, C는 전문 산업 자료를 뜻한다. D·E 등급은 핵심 수치의 단독 근거로 쓰지 않는다.

금리, 소득, 지출, 취업 시점, 월 납입액, 상환 시점은 사용자 입력 또는 기준일을 명시한 상품 스냅샷이다. 앱은 미래 금리, 정책 존속, 실제 수혜, 대출 승인을 예측하지 않는다.

## 1. 두 독립 기획안의 종합 판정

Sol안은 규칙·계산·근거의 정합성과 5주 범위를 상세하게 다뤘다. X Preview안은 제품 정의, 기능 구분, 화면 흐름을 짧고 명확하게 정리했다. 최종안은 X Preview안의 간결한 사용자 경험을 유지하되 구현 선택은 Sol안의 최소 구조를 따른다. 이는 문서 종합 판단이며 구현 성공의 증거가 아니다.

| 쟁점 | Sol안 | X Preview안 | 최종 결정 | 선택 이유 |
|---|---|---|---|---|
| 사용자 접점 | 모바일 우선 반응형 웹 | React Native·Expo 앱 | React·TypeScript 반응형 웹 | 기기 전용 권한이 필요 없고 5주 안에 접근성·배포·시연을 함께 검증할 수 있다 |
| 백엔드 | 단일 Spring Boot | Spring Batch + FastAPI | 단일 Spring Boot | 규칙 수와 계산 범위가 작아 서비스·언어 경계를 추가할 이득이 없다 |
| 데이터 저장 | 버전 JSON, 사용자 시나리오 비영속 | PostgreSQL 중심 | 검수 규칙·상품만 Git 버전 JSON | 운영자 다수, 사용자 계정, 동적 대량 데이터가 없는 MVP에는 DB가 필요 없다 |
| 정책 반입 | 수동 검수 스냅샷, API는 선택 PoC | API·배치 자동 수집 | 수동 검수를 기본값으로 두고 API는 1주차 PoC | 정책 변경과 API 승인 실패가 코어 데모를 막지 않는다 |
| 계산 | Java `BigDecimal`·`LocalDate` | Python `Decimal` 별도 엔진 | Spring Boot 내부 순수 함수 | 원화 반올림, 날짜, 규칙, API를 한 배포 단위에서 재현한다 |
| AI | 기본 OFF, 합성 데이터 설명만 | LLM 어댑터 상시 구조 | 선택 기능, 실패하면 템플릿 | AI가 없어도 제품 가치와 기술 증명이 성립해야 한다 |
| MVP 범위 | 규칙 3개, 예금·적금 중 1개, 대출 1개, 36개월 | 더 넓은 정책·대출 방식 | 규칙 3개, 상품 1개, 고정금리 대출 1개, 36개월 | 세 축의 결합 원리를 증명하면서 골든 테스트가 가능한 최대 범위다 |

## 6. 핵심 기능

### F1. 가정 입력과 3상태 진단

사용자는 기준일, 월 소득·지출, 거주·고용, 초기 가용 현금, 지키려는 최소 현금 `minimum_cash_reserve >= 0`, 새 상품 조건, 대출 조건을 입력한다. 최소 현금은 필수 사용자 입력이며 앱이 임의 기본값을 정하지 않는다. 기존 계약 상품의 잔여 일정은 MVP 계산에서 제외한다. 정책·세제 결과는 `ELIGIBLE`, `INELIGIBLE`, `NEEDS_CONFIRMATION`으로 나뉜다. 증빙, 예산, 기관 심사, 미확정 상호작용은 적격으로 단정하지 않는다.

### F3. 결합 현금흐름 시뮬레이션

정책 현금, 실현 가능한 세제 효과, 예금·적금 납입과 만기, 대출 원금·이자·추가상환을 하나의 월별 원장에 반영한다. 누적 예상 이자와 정부기여금은 실제 귀속일 전에는 장부 순자산에 더하지 않는다.

### F4. 상환 기간·시기 비교

시나리오당 고정금리 일반 대출 한 개를 지원한다. 입력값은 잔액, 연 명목금리, 상환 방식, 남은 기간, 정기 상환일, 추가상환 월·금액, 계약상 수수료다. 사용자는 약정 유지안, 추가상환안, 예금·적금 만기 뒤 상환안을 비교한다.

### F5. 가정·근거 노출형 결과

결과에는 월별 현금 최저점, 저축 잔액, 대출 잔액, 36개월 말 순자산, 개별 효과, 결합 효과가 함께 나온다. 모든 항목에서 원문 URL, 규칙 버전, 시행 기간, 기준일, 사용자 가정, 계산식을 확인한다. AI는 합성 데이터의 확정 결과를 쉬운 문장으로 바꿀 뿐 금액이나 자격을 만들지 못한다.

### 8.2 36개월 주요 사건표

엔진은 M1부터 M36까지 매월 계산한다. 문서에는 사용자의 판단에 필요한 주요 사건만 적는다.

|---|---|---|---|
| M1 | 주거·소득·정책 조건 확인, 기본 현금흐름 생성 | 급여·월세·저축 조건 확인 | 원금·금리·상환 방식·수수료 확인 |
| M3 | 승인된 정책 현금만 반영 | 월 납입액 변경안 비교 | 첫 추가상환안과 수수료 계산 |

정책 미확정 상태는 수혜액 0원과 다르다. 미확정 조합은 기본 원장에 넣지 않고 사용자가 켠 `ASSUMPTION` 실행에서만 계산한다.

### 8.3 개별 효과와 결합 효과

```text
N0   = 기존 자산·부채·필수 상환만 유지한 36개월 말 순자산
NP   = N0 + 확정 정책 현금
NT   = N0 + 실현 가능한 세제 이벤트
NS   = N0 + 새 예금·적금 행동
NL   = N0 + 선택한 추가상환 시점
NALL = 네 요소를 함께 적용해 월별 원장을 다시 계산한 순자산

정책 개별 효과 = NP - N0
세제 개별 효과 = NT - N0
저축 개별 효과 = NS - N0
상환 개별 효과 = NL - N0
결합 효과       = NALL - N0
상호작용        = 결합 효과 - 개별 효과의 합
```

`NP`는 청년월세처럼 상품과 독립된 정책 현금만 가진다. 청년미래적금의 정부기여금은 상품 가입·납입 없이는 발생하지 않으므로 은행 이자·세제와 함께 `NS`에 한 번만 귀속한다. 상호작용 항등식은 화면 합계를 검사할 뿐 계산 정확성을 증명하지 않는다. `N0`, `NP`, `NT`, `NS`, `NL`, `NALL`의 월별 현금·저축·부채 원장을 독립 기준표와 각각 대조한다.

월세액 세액공제 정산 흐름도 실행별로 고정한다.

| 실행 | 월세액 세액공제 정산 | 다른 요소 |
|---|---|---|
| `N0` | `TaxSettlementCashflowWithoutCredit` | 선택 행동 없음 |
| `NP` | `TaxSettlementCashflowWithoutCredit` | 독립 정책 현금만 켬 |
| `NT` | `TaxSettlementCashflowWithCredit` | 월세액 세액공제만 켬 |
| `NS` | `TaxSettlementCashflowWithoutCredit` | 새 예금·적금과 상품 고유 세제만 켬 |
| `NL` | `TaxSettlementCashflowWithoutCredit` | 추가상환만 켬 |
| `NALL` | `TaxSettlementCashflowWithCredit` | 네 요소를 함께 켬. 미확정 조합은 `ASSUMPTION`에서만 허용 |

### 8.4 전체 결합 통합검사

`QA_FIXTURE_ALL`은 청년월세 정책 현금, 월세액 세제 정산, 청년미래적금 납입·귀속, 고정금리 대출 추가상환을 모두 포함하는 합성 시나리오다. 실제 동시 적용을 주장하지 않는다. 공식 조합 규칙을 확보하지 못한 항목은 `ASSUMPTION`으로 표시한다. 숫자는 구현 저장소의 골든 원장에만 두고 공식 스냅샷 또는 테스트값이라는 라벨을 붙인다. 정기예금은 별도 `QA_FIXTURE_TIME_DEPOSIT`에서 개설 원금 1회 이전, 만기 이자·세금·현금 이전을 검증한다.

## 13. 결정론적 계산 엔진

### 13.1 월별 원장

```text
Cash[t]
= Cash[t-1]
+ Income[t]
+ PolicyCash[t]
+ TaxSettlementCashflow[t]
+ SavingTransferToCash[t]
- EssentialExpense[t]
- SavingContribution[t]
- ActualLoanScheduledPayment[t]
- ActualLoanPrepayment[t]
- LoanFee[t]

Saving[t]
= Saving[t-1]
+ SavingContribution[t]
+ CreditedGovernmentMatch[t]
+ CreditedGrossInterest[t]
- CreditedInterestTax[t]
+ SavingAdjustment[t]
- SavingTransferToCash[t]

Loan[t] = Loan[t-1] - ActualScheduledPrincipal[t] - ActualLoanPrepayment[t]
NetWorth[t] = Cash[t] + Saving[t] - Loan[t]
```

`Income[t]`는 원천징수와 급여 공제를 마친 실수령 현금이다. 정책 자격에 필요한 세전소득은 `EligibilityGrossIncome[t]`으로 분리한다. `PrepaidTax`는 급여명세서의 원천징수 누계 메타데이터이며 `Income[t]`에서 다시 빼지 않는다. 사용자가 세전소득만 입력하면 실수령 현금을 자동 추정하지 않고 `NEEDS_CONFIRMATION`을 반환한다.

`SavingTransferToCash[t]`는 저축에서 빠지는 금액과 현금에 들어오는 금액이 같다. 하나의 이전 이벤트를 원장의 양쪽에 반영해 이중 계상을 막는다. 예상 이자와 정부기여금은 실제 귀속일에만 순자산에 들어간다. `TaxSettlementCashflow[t]`는 환급이면 양수, 추가 납부면 음수다. 세액공제액을 곧바로 현금 환급으로 더하지 않는다.

월말 잔액과 월중 최저 잔액도 구분한다.

```text
CashAfterEvent[first_event_in_month_t]
= Cash[t-1] + SignedAmount[first_event_in_month_t]
CashAfterEvent[e] = CashAfterEvent[e-1] + SignedAmount[e]
Cash[t] = CashAfterEvent[last_event_in_month_t]
MinCash[t] = min(CashAfterEvent[e] for e in month_t)
MinCashHorizon = min(MinCash[t] for t in M1..M36)

if month_t has no event:
  Cash[t] = Cash[t-1]
  MinCash[t] = Cash[t]
```

`effective_date`와 `sequence`로 정렬한 모든 현금 사건을 위 식에 넣는다. 월별 합계만으로 현금 부족을 판정하지 않는다.

### 13.2 예금·적금

```text
TIME_DEPOSIT:
GrossInterestAtMaturity = Principal × annual_rate × term_months / 12

RECURRING_SAVINGS:
period_rate = annual_rate / 12
contribution_index k = 1..N
months_earning[k] = N - k + 1  // 월초 납입, N번째 월말 만기
GrossInterestAtMaturity
= Σ(contribution[k] × period_rate × months_earning[k])

NetInterest = GrossInterestAtMaturity - InterestTax
SavingBeforeTransfer[t]
= Saving[t-1]
+ SavingContribution[t]
+ CreditedGovernmentMatch[t]
+ CreditedGrossInterest[t]
- CreditedInterestTax[t]
+ SavingAdjustment[t]

if confirmed_maturity_or_full_termination[t]:
  SavingTransferToCash[t] = SavingBeforeTransfer[t]
  SavingAfterTransfer[t] = 0
  cancel_future_saving_events(position_id)
```

MVP는 정기예금과 월초 납입 정기적금 공식을 모두 구현하되 한 시나리오에는 한 상품만 둔다. 상품의 공식 방식이 위 계약과 다르면 정확한 계산 대상에서 제외한다. `SavingTransferToCash`는 만기와 검증된 전액 중도해지에 함께 쓰는 단일 이전 이벤트다. `SavingAdjustment`에는 확정된 중도해지 이자, 세금, 정부기여금 회수, 해지 비용을 부호와 함께 넣는다. 부분 인출은 지원하지 않는다.

입력 불변식도 고정한다. MVP는 시나리오 시작 뒤 새로 여는 상품만 계산하므로 `Saving[0]=0`이다. `Cash[0]`에는 새 상품에 아직 넣지 않은 가용 현금만 둔다. 정기예금 원금은 개설월의 `SavingContribution`으로 현금에서 저축으로 한 번만 옮긴다. 기존 계약 상품의 납입 이력·잔여 회차·중도해지 조건은 MVP 입력에서 제외하고 `NEEDS_CONFIRMATION`으로 표시한다. 공식 상품 조건은 `ProductSnapshot`, 새 상품의 원금·납입액·가입일은 `SavingPositionInput`으로 분리한다.

일반 이자소득은 공식 세율 스냅샷을 적용하며 비과세는 상품·자격·기간이 모두 확인된 경우에만 쓴다. 근거는 [국세청](https://www.nts.go.kr/nts/cm/cntnts/cntntsView.do?cntntsId=7914&mi=40359)(확인 2026-08-23, A), [소득세법 제129조](https://www.law.go.kr/lsLawLinkInfo.do?chrClsCd=010202&lsJoLnkSeq=1000226036)(시행 2026-01-01, A), [지방세법 제103조의13](https://www.law.go.kr/lsLinkCommonInfo.do?chrClsCd=010202&lsJoLnkSeq=1031061107)(시행 2026-07-01, A, `VERIFIED`)다.

### 13.3 대출 상환 기간·시기

원금 `P`, 월 금리 `r`, 남은 기간 `n`일 때 원리금균등 목표 납입액은 다음과 같다.

```text
A_raw = r == 0 ? P / n : P × r × (1+r)^n / ((1+r)^n - 1)
PaymentTarget = round_won(A_raw, HALF_UP)

B_before = Balance[t-1]
Interest[t] = round_won(B_before × r, HALF_UP)
PlannedPrincipal[t] = max(0, PaymentTarget - Interest[t])
ActualScheduledPrincipal[t] = min(B_before, PlannedPrincipal[t])
ActualLoanScheduledPayment[t] = Interest[t] + ActualScheduledPrincipal[t]
B_after_regular = B_before - ActualScheduledPrincipal[t]
```

원금균등은 최초 원금을 기준으로 월 원금 목표를 한 번 정한다.

```text
BasePrincipal = round_won(P / n, HALF_UP)
Interest[t] = round_won(B_before × r, HALF_UP)
ActualScheduledPrincipal[t] = min(B_before, BasePrincipal)
ActualLoanScheduledPayment[t] = Interest[t] + ActualScheduledPrincipal[t]
B_after_regular = B_before - ActualScheduledPrincipal[t]
```

두 방식 모두 정기 상환을 먼저 처리한다. 추가상환 입력은 `0 <= requested_prepayment <= B_after_regular`을 만족해야 한다. 초과하면 요청 전체를 거부하고 현금도 차감하지 않는다.

```text
ActualLoanPrepayment[t] = requested_prepayment
Balance[t] = B_after_regular - ActualLoanPrepayment[t]
LoanFee[t] = verified_fee_rule(ActualLoanPrepayment[t], contract_terms)
```

마지막 납입월에는 목표 납입액이 아니라 `Interest[t] + B_before`가 실제 정기 납입액이다. 현금 원장도 이 실제 금액만 차감한다. 추가상환 뒤에는 원리금균등의 기존 `PaymentTarget`, 원금균등의 기존 `BasePrincipal`을 유지해 기간을 줄이고 마지막 달에 남은 원금만 낸다.

추가상환 효과는 같은 기준일·금리·정기 납입 계약의 두 스케줄을 M1~M36 안에서 비교한다.

```text
avoided_interest_within_horizon
= Σ(t=M1..M36) Interest_baseline[t]
- Σ(t=M1..M36) Interest_prepayment[t]

PrepaymentEffect
= avoided_interest_within_horizon
- contract_prepayment_fee
- lost_after_tax_saving_interest_if_funded_from_savings

MinCashAfterPrepayment = MinCashHorizon in prepayment_scenario
CashShortfallFlag = MinCashAfterPrepayment < minimum_cash_reserve
```

`lost_after_tax_saving_interest`는 M1~M36 안의 차이만 반영하며 사용자가 자금 출처를 해당 저축으로 지정한 경우에만 계산한다. 중도해지 금리, 세제 추징, 정부기여금 손실, 해지 비용 중 하나라도 미확정이면 숫자를 만들지 않고 `NEEDS_CONFIRMATION`을 반환한다. 화면의 최종 금전 효과는 36개월 월별 원장에서 산출한 `NL - N0`다. 위 구성요소의 합은 이 값과 ±1원 이내로 일치해야 한다. M36 뒤의 평생 절감 이자는 `pending_after_horizon`에 설명만 남기고 금액을 계산하지 않는다.

저축을 상환 재원으로 쓰는 경로도 기존 `SavingTransferToCash`를 쓴다. 상품 원문으로 전액 중도해지의 실제 수령액을 계산할 수 있을 때만 해지 조정값을 반영하고 저축 잔액 전부를 현금으로 옮긴다. 부분 인출은 지원하지 않는다. MVP에서는 만기·해지 이전일이 추가상환일보다 최소 하루 앞서야 하며 같은 날 요청은 거부한다. 이전 뒤의 현금에서만 `ActualLoanPrepayment`와 `LoanFee`를 차감한다. 해지 수령액이 미확정이면 이전과 추가상환 이벤트를 모두 만들지 않는다.

MVP는 연 명목금리를 `r/12`로 바꾸는 월 단순화만 지원한다. 실제 요율·면제 조건은 사용자 계약값이다. 2025년 1월 13일 이후 보호 대상 신규 대출의 수수료 체계 개편은 [금융위원회 자료](https://www.fsc.go.kr/po010101/83833)(2025-01-09 게시, 2025-01-13 시행, A, `VERIFIED`)로 확인했다.

### 13.4 월세액 세액공제

```text
QualifiedRent[year] = max(0, Σ qualified_rent_paid[year])
EligibleRent[year] = min(QualifiedRent[year], max(0, legal_cap[year]))
CalculatedCredit[year] = EligibleRent[year] × credit_rate[year]
LiabilityBeforeCredit[year] = max(0, applicable_tax_liability_before_rent_credit[year])
RealizedCredit[year] = min(max(0, CalculatedCredit[year]), LiabilityBeforeCredit[year])
LiabilityAfterCredit[year] = LiabilityBeforeCredit[year] - RealizedCredit[year]

PrepaidTax[year] = max(0, verified_withheld_or_prepaid_tax[year])
TaxSettlementCashflowWithoutCredit[year] = PrepaidTax[year] - LiabilityBeforeCredit[year]
TaxSettlementCashflowWithCredit[year] = PrepaidTax[year] - LiabilityAfterCredit[year]
TaxCashEffect[year]
= TaxSettlementCashflowWithCredit[year] - TaxSettlementCashflowWithoutCredit[year]

TaxSettlementCashflowByYear[year][settlement_month[year]]
= selected_scenario_tax_settlement_cashflow[year]
TaxSettlementCashflow[t]
= Σ TaxSettlementCashflowByYear[year][t]
```

세액공제는 실제 세금 정산의 차이로만 현금 원장에 들어간다. 원천징수·기납부세액이 세액보다 적으면 `TaxSettlementCashflow`는 추가 납부액을 나타내는 음수가 될 수 있다. `N0`에는 `TaxSettlementCashflowWithoutCredit`, `NT`에는 같은 세전소득·실수령소득·기납부세액을 유지한 `TaxSettlementCashflowWithCredit`를 넣는다. `NT-N0`만 월세액 세액공제 효과다. 산출세액, 원천징수·기납부세액, 정산월 중 하나라도 모르면 기본 시나리오에는 세제 현금을 넣지 않는다. 사용자가 명시적으로 켠 가정 실행에서만 `ASSUMPTION` 이벤트로 계산한다. 자동 세무 계산은 범위 밖이다.

`qualified_rent_paid`의 기준도 고정한다. 승인된 `InteractionRule`이 월세 지원금을 세액공제 대상 월세에서 차감한다고 명시한 경우에만 본인 부담액을 쓴다. 공식 조합 규칙이 없으면 청년월세와 월세액 세액공제를 동시에 `CONFIRMED`로 계산하지 않는다. 가정 실행은 `GROSS_CONTRACT_RENT`와 `NET_OF_POLICY_SUPPORT` 중 하나를 사용자가 선택하게 하고 결과를 확정값이 아닌 민감도 범위로 표시한다. 같은 월세 지급액이 확정 정책 현금과 확정 세액공제에 동시에 들어가는 경로는 금지한다.

### 13.5 반올림·날짜 계약

- 내부 금액은 `BigDecimal` 원 단위로 계산한다. [Oracle `BigDecimal`](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/math/BigDecimal.html)(확인 2026-08-24, B, `VERIFIED`).
- 타임존은 Asia/Seoul, 날짜는 `LocalDate`로 고정한다. [Oracle `LocalDate`](https://docs.oracle.com/en/java/javase/17/docs/api/java.base/java/time/LocalDate.html)(확인 2026-08-24, B, `VERIFIED`).
- 월 이자 산출 뒤 원 단위 `HALF_UP`을 기본값으로 쓰되 공식 규칙이 다르면 해당 상품을 제외한다.
- 금리 0%는 월 납입액 `P/n`으로 분기한다.
- 마지막 달에는 남은 원금을 전액 반영해 잔액을 0원으로 보정한다.
- 정기 원금을 반영한 뒤의 잔액을 넘는 추가상환은 입력 오류로 반환하고 현금에서도 차감하지 않는다.
- 같은 입력 해시, 규칙 버전, 엔진 버전은 같은 결과를 내야 한다.

### 13.6 이벤트 순서·기간·효과 귀속 계약

- 모든 이벤트는 `effective_date`를 가진다. 날짜순으로 처리하고 같은 날에는 현금 유출을 유입보다 먼저 반영해 현금 최저점을 보수적으로 계산한다. 날짜를 모르면 확정 현금 최저점을 만들지 않고 `ASSUMPTION`으로 남긴다.
- 36개월 말 순자산에는 M1~M36 안에서 실제로 발생한 이벤트만 들어간다. 정산월·만기·지급월이 M36 뒤라면 `pending_after_horizon`에 금액·예정일·상태를 표시하고 `N36`에는 넣지 않는다.
- 월세액 세액공제 규칙은 `tax_year`별 버전이다. 2026 규칙을 2027년 이후 과세연도에 복사하지 않는다. 해당 연도 규칙을 검수하지 못하면 그 연도의 세제 이벤트는 `NEEDS_CONFIRMATION`이다.
- `ProductSnapshot`은 `signup_effective_from/to`, `contract_maturity`, `terms_locked_at_signup`, 규칙별 `tax_year`를 가진다. 신규 가입일이 가입 유효기간 안에 있고 사용자가 실제 계약을 확인한 경우에만 만기까지 계약 조건을 쓴다. 계약 뒤에도 바뀔 수 있는 정부기여금·세제 규칙은 검수한 연도 밖에서 `NEEDS_CONFIRMATION`으로 전환한다.
- 신규 신청 자격과 신청 이벤트는 `application_window` 안에서만 판정한다. 신청 종료일 뒤에는 새 적격·신청 이벤트를 만들지 않는다.
- 기존 선정자의 지급 이벤트는 신청 기간과 분리한다. `award_status=CONFIRMED`, `confirmed_award_payment_start`, `award_payment_window.end`, `award_survives_application_close=true`가 모두 있을 때 시나리오 기간과 지급 기간의 교집합에서만 만든다. `max_count`는 실행별로 적용한다. 확정 실행은 `CONFIRMED`, 가정 실행은 `ASSUMPTION` 이벤트 수를 각각 세며 두 실행 모두 상한을 넘지 못한다. `DISABLED`는 세지 않는다.
- 독립 정책 현금만 `NP`에 귀속한다. 청년미래적금처럼 상품 가입과 납입이 전제인 정부기여금은 은행 이자·세제와 함께 `NS`에 한 번만 귀속한다. `NP`와 `NS`가 같은 기여금을 공유하면 입력을 거부한다.
- `PrepaymentEffect`의 구성요소 합은 권위 있는 결과가 아니다. 최종 상환 효과는 전체 원장에서 산출한 `NL - N0`이며 구성요소 합은 이 값의 설명용 대조치다.

### 14.1 최소 스키마

```json
{
  "example_only": true,
  "rule_id": "POLICY-2026-001",
  "program_code": "YOUTH_RENT_2026",
  "version": "2026-03-18",
  "rule_scope": "CONFIRMED_2026_AWARD_PAYMENTS",
  "application_window": {
    "from": "2026-03-30",
    "to": "2026-05-29"
  },
  "award_payment_window": {
    "start_field": "confirmed_award_payment_start",
    "end": "2028-12-31"
  },
  "award_survives_application_close": true,
  "conditions": {
    "all": [
      { "field": "award_status", "op": "eq", "value": "CONFIRMED" }
    ]
  },
  "benefit": {
    "formula_id": "CAP_MINUS_VERIFIED_OFFSETS",
    "parameters": {
      "cap_won": 200000,
      "qualified_rent_field": "verified_monthly_rent_paid",
      "offsets_field": "verified_monthly_rent_offsets"
    },
    "schedule": {
      "type": "MONTHLY",
      "start_rule": "CONFIRMED_AWARD_PAYMENT_START",
      "max_count": 24
    }
  },
  "interaction_rules": [
    {
      "target_program_code": "RENT_TAX_CREDIT",
      "type": "UNVERIFIED_COMBINATION",

    }

```

위 JSON은 스키마 예시라 `example_only=true`, `DRAFT`이며 실행할 수 없다. 실제 `APPROVED` 규칙에는 연령 기준일, 가구·소득·재산, 신청 기간, 증빙, 기존 선정 상태, 지급 가능 기간을 모두 넣는다. 신규 신청은 `application_window`, 기존 선정자의 지급은 `award_payment_window`로 분리한다. 수식은 실행 문자열로 저장하지 않고 코드에 등록된 `formula_id`와 타입이 있는 매개변수만 쓴다. `DRAFT`, `APPROVED`, `NEEDS_REVIEW`, `RETIRED` 중 `APPROVED` 규칙만 판정에 사용한다.

`CAP_MINUS_VERIFIED_OFFSETS`의 실행 계약은 다음과 같다.

```text
QualifiedRentPaid[t] = max(0, verified_monthly_rent_paid[t])
BaseRentSupport[t] = min(QualifiedRentPaid[t], cap_won)
VerifiedOffsets[t]
= Σ max(0, verified_monthly_rent_offsets[t][i].amount)
PolicyCash[t] = max(0, BaseRentSupport[t] - VerifiedOffsets[t])
```

`verified_monthly_rent_offsets`의 각 항목은 `source_id`, 승인된 `interaction_rule_id`, `amount`를 가진다. 셋 중 하나라도 없으면 차감액으로 쓰지 않고 규칙 전체를 `NEEDS_CONFIRMATION`으로 보낸다. 월세 지급 증빙, 선정 상태, 지급월이 확인되지 않아도 `PolicyCash`를 만들지 않는다. 이 계약은 실제 납부 월세보다 큰 지급과 음수 지급을 막는다.

### 14.2 판정·상호작용

| 구분 | 값 | 처리 |
|---|---|---|
| 사용자 판정 | `ELIGIBLE`, `INELIGIBLE`, `NEEDS_CONFIRMATION` | 미확정 조건은 확정 원장 이벤트를 만들지 않는다 |
| 규칙 상태 | `DRAFT`, `APPROVED`, `NEEDS_REVIEW`, `RETIRED` | 원문 변경·충돌 시 `NEEDS_REVIEW` |
| 이벤트 상태 | `CONFIRMED`, `ASSUMPTION`, `DISABLED` | 원장과 화면에서 확정·가정·미사용을 구분한다 |
| 상호작용 | `EXCLUSIVE`, `OFFSET`, `PREREQUISITE`, `ORDER`, `INDEPENDENT`, `UNVERIFIED_COMBINATION` | 상호 배제, 차감, 선행 조건, 시점, 독립, 미확정 조합을 구분한다 |
| 상호작용 검토 | `CONFIRMED`, `NEEDS_CONFIRMATION` | 미확정 조합은 확정 실행에 들어가지 않는다 |
| 확정 실행 행동 | `APPLY`, `NO_EVENT`, `SELECT_ONE`, `APPLY_OFFSET` | 상호작용별 실행 방식을 열거형으로 고정한다 |
| 가정 실행 행동 | `DISALLOW`, `ALLOW_WITH_LABEL` | 가정 실행 허용 여부와 라벨을 고정한다 |

`EXCLUSIVE`는 사용자가 하나를 고르지 않으면 두 이벤트 모두 만들지 않는다. `OFFSET`은 `offset_target_event_type`과 승인된 `offset_formula_id`를 요구하고 결과를 `max(0, target-offset)`으로 제한한다. `PREREQUISITE`가 충족되지 않으면 이벤트를 만들지 않는다. `ORDER`는 `APPLY + sequence`, `INDEPENDENT`는 `APPLY`로 매핑한다. `ORDER`는 금액을 바꾸지 않고 `effective_date`와 같은 날의 `sequence`만 정한다. `UNVERIFIED_COMBINATION`은 확정 실행에서 항상 `NO_EVENT`, 가정 실행에서만 `ALLOW_WITH_LABEL`이다.

이벤트는 유효기간 검사, 3상태 판정, 선행 조건 확인, 상호 배제 선택, 검증된 차감액 계산, 지급 일정 생성 순서로 만든다. 청년월세·월세액 세액공제·청년미래적금 사이의 모든 조합을 공식 원문으로 확정하지 못했으므로 기본값은 `UNVERIFIED_COMBINATION`이다.

### 20.2 인력 용량과 핵심 경로

6명×5주는 30인주다. 코어에 24인주, 통합·결함 수정·선택 기능에 6인주를 남긴다. 외부 API와 AI는 코어 완료 뒤 남은 용량으로만 진행한다.

| 작업 묶음 | 코어 인주 | 예비 인주 | 완료 기준 |
|---|---:|---:|---|
| FE 입력·상태·접근성 | 4 | 1 | 세 사용자 입력 E2E |
| FE 결과·근거·표/차트 | 4 | 1 | 원장·표·차트 일치 |
| BE 규칙·출처·API | 4 | 1 | 세 규칙 골든 케이스 |
| BE 계산 엔진 | 4 | 1 | 예금·적금·대출·세제 원장 ±1원 |
| AI/Data 정책·서비스·사용성 | 4 | 1 | 원문 검수와 과업 진행 |
| AI/Data QA·보안·배포 | 4 | 1 | 회귀·개인정보·재배포 게이트 |
| 합계 | 24 | 6 | 30인주 이내 |

핵심 경로는 W1 규칙·원장 계약 → W2 엔진·API → W3 세 유형 E2E → W4 회귀·접근성 → W5 동결 순서다. API 자동 반입과 AI 설명은 핵심 경로에 넣지 않는다. W2 말에 코어 E2E가 없으면 두 선택 기능을 시작하지 않는다.

코드 작성자와 검증자는 같은 항목을 단독 승인하지 않는다. AI/Data 1은 규칙 승인, Backend 2는 엔진 구현, AI/Data 2는 독립 골든 원장 대조를 맡는다.

## 25. UNVERIFIED / BLOCKED

### UNVERIFIED

- 청년미래적금 후속 모집의 확정 일정·대상·취급기관 전체
- 취급기관별 최신 기본금리·우대금리·우대조건 전체
- 2027년 이후 청년월세 조건·모집 기간
- MVP 세 규칙 사이의 모든 중복·상계 조합
- 온통청년 API의 실제 응답 필드·호출 한도·갱신주기
- Finlife API의 키 발급·실제 응답·호출량
- 모든 대출상품의 수수료율·면제 조건·일할 계산 규칙
- 한국어 정책 문서 AI 추출 정확도와 인용 누락률
- 시나리오 UI가 실제 저축 증가나 부채 감소를 유발한다는 인과효과
- 36개월·6실행 1초 이내 계산 목표의 실제 성능

### BLOCKED

- 허가·계약 없이 실사용자 계좌·대출·세무자료를 자동 조회하는 기능
- 증빙·예산·기관 심사 없이 정책 수혜와 대출 승인을 확정하는 기능
- 개별 법률 검토 전 개인화 금융상품 추천·중개를 포함한 공개 상용 운영
- 국내 전체 시장에 같은 기능이 없다는 완전한 부재 증명

## 28. 자체검수 체크리스트

아래 체크는 기획 문서의 포함·정합성만 뜻한다. 구현, E2E, 골든 원장, API, 성능 PoC는 모두 `NOT_RUN`이며 19장의 게이트를 통과하기 전에는 기술 구현 성공으로 보고하지 않는다.

- [x] 한 문장 제품 정의와 사용자 행동 → 앱 처리 → 결과가 문서 맨 앞에 있다.
- [x] 정책·세제·예금·적금·대출 상환을 하나의 36개월 원장으로 연결했다.
- [x] 문제 → 개념 솔루션 → 기능 → 기술의 WHY A/B/C를 추적할 수 있다.
- [x] 설득력과 기술력 파트를 구분했다.
- [x] 세 사용자 유형이 같은 입력 계약과 월별 엔진을 쓴다.
- [x] 개별 효과와 결합 효과를 같은 가정에서 비교한다.
- [x] 근거 없는 수익·절감 수치를 만들지 않았다.
- [x] 결정론적 계산과 AI 설명을 분리했다.
- [x] 6인 5주 MVP, 제외 범위, 고도화 조건, 범위 절감 순서를 구분했다.
- [x] 요구사항 추적표, 주장·근거 검증표, `UNVERIFIED/BLOCKED`, 참고문헌을 포함했다.
- [x] 정책 기준일 2026-08-23과 기술·링크 재검사일 2026-08-24를 구분했다.
- [x] 제외 요청 범위의 주제를 포함하지 않았다.
