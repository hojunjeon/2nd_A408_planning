## 1. 요약

- **한 줄 정의**: 불규칙한 소득의 청년에게 규칙적인 재무 구조를 만들어주는 **실행형 머니 플로우 엔진**
- **해결하는 문제**: 수입은 불규칙한데 지출은 규칙적이라는 미스매치, 그리고 예산을 세워도 이체·납부·저축은 사용자가 직접 해야 하는 계획과 실행의 간극(Plan-Do Gap)
- **해결 방식**: 원장(기록) → 의사결정 엔진(산정) → 자동 실행(이체·납부·저축) → 피드백(재산출)의 폐쇄 루프. 매월 소득 변동성과 소비 실적으로 지급액을 다시 계산해 자동 조정한다
- **핵심 차별점**
  1. 계획에서 끝나지 않고 **실행**한다. 배분 이체·정기결제·적금 납입까지 서비스가 수행한다
  2. 있는 돈만 관리하지 않고 **들어올 돈을 늘린다**. 정책 지원금을 현금흐름에 직접 꽂는다
  3. 숫자는 결정론적 엔진이 만들고 LLM은 설명만 한다. 코치의 조언이 곧 실행 버튼이다
  4. 카드 건별 할부, 월세·전세, 학자금, 청년 정책, 연말정산 등 한국 청년의 실제 구조를 다룬다
- **카테고리 판정**: PFM(개인 재무 관리) + 자동 실행형(Auto-pilot) 핀테크. 판단·실행·인프라 3개 단계를 모두 충족한다. 비교군은 Qapital(규칙 기반 자동 이체), Digit(소득 분석 자동 저축), 국내 티클(자동 저축)

## 2. 배경과 문제 정의

### 2-1. 문제 구조

기존 배경이었던 "청년 정책 정보가 파편화되어 찾기 어렵다"는 정보 접근 문제였다. 재정의된 배경은 **청년의 현금흐름 구조 문제**다.

**① 불규칙한 수입 vs 규칙적인 지출의 미스매치** `📊`

대학생·취준생·사회초년생의 수입은 불규칙하다. 알바비는 근무량에 따라 들쭉날쭉하고, 지원금은 분기·반기 단위로 들어오며, 프리랜스 수입은 예측이 어렵다. 반면 지출은 규칙적이다. 월세, 통신비, 할부금, 교통비는 매달 같은 날 같은 금액이 나간다. 이 미스매치가 청년 재무 불안의 구조적 원인이며, 수입이 많았던 달의 잉여는 관리되지 않은 채 소비로 증발한다.

**② 계획과 실행의 간극 (Plan-Do Gap)** `📊`

가계부 앱과 예산 서비스(YNAB, 뱅크샐러드 등)는 돈의 흐름을 기록하고 계획하지만, 실행은 전적으로 사용자의 몫이다. "이번 달 식비 30만"이라고 적어도 이체·저축·납부는 사용자가 은행 앱을 열어 직접 해야 하고, 이 간극에서 대부분의 예산 계획이 무너진다. 예산 관리의 실패는 의지의 문제가 아니라 **실행 자동화의 부재** 문제다.

**③ 수입 기회와 새는 돈이 현금흐름에 통합되지 않음** `📊`

청년이 놓치는 정책 지원금(월세지원 최대 480만, 국취제 300만 등)은 사실상 유일하게 늘릴 수 있는 수입이고, 할부 수수료와 불필요한 이자는 대표적으로 새는 돈이다. 그러나 정책 서비스는 정보만 주고, 카드 앱은 명세만 보여줄 뿐, 어느 것도 "들어올 돈을 찾아 현금흐름에 꽂아주고, 새는 돈을 막아 저축으로 돌리는" 통합을 하지 않는다.

### 2-2. 기존 대안의 한계

| 대안 유형 | 하는 일 | 멈추는 지점 |
| --- | --- | --- |
| 가계부·PFM (뱅크샐러드 등) | 기록·분류·조회 | 원장 대사와 실행이 없다 |
| 예산 도구 (YNAB) | 제로베이스 예산 계획 | 이체·저축·납부는 사용자가 은행 앱에서 직접 |
| 정책 정보 서비스 | 자격 검색·안내 | 지원금이 현금흐름에 연결되지 않는다 |
| 카드사 앱 | 명세·청구 조회 | 결제일 전 자금 준비를 대신 해주지 않는다 |
| 은행 자동이체 | 정해진 금액을 정해진 날 이체 | 금액·시점을 사용자가 정한다. 재계산이 없다 |

### 2-3. 의사결정 배경: 컨설팅 지적과 대응

| # | 컨설팅 지적 | 원인 진단 | 개편 대응 |
| --- | --- | --- | --- |
| 1 | 핀테크적 내용이 겉돌고 핵심을 관통하지 못함 | 핵심이 정책 추천(정보 서비스)이고, 금융 기능은 전부 "계산기"였음. 돈이 실제로 움직이지 않음 | **돈이 실제로 움직이는 머니 플로우 엔진을 코어로 재정의.** 금융망 API(입출금·이체·정기결제·예적금·대출)가 전 단계에서 실사용됨 |
| 2 | 실질적으로 큰 지원을 주는 청년 정책이 많지 않아 활용 가치 부족 | 정책이 메인이라 자격 미달 사용자에게 서비스가 빈 껍데기가 됨 | 정책을 메인에서 **수입 측 인텔리전스(부스터)로 강등.** 정책 자격이 없어도 코어 가치(현금흐름 자동화)는 온전히 작동 |
| 3 | 실질적 자산 형성·분석 기능 부재 | 지출(할부)과 수입(정책)만 다루고 "모은 돈을 굴리는" 기능이 없었음 | 가상 봉투 예산 + 자동 저축 파킹 + 목표 기반 자산 형성 플랜을 신설 |
| 4 | 자산 관리가 메인, 정책·예적금·대출이 부가가 되어야 하지 않나 | 타당하나, 단순 역전은 토스·뱅샐 열화판이 될 위험 | 역전이 아닌 **합성**. 자산 관리(현금흐름 자동화)가 메인, 정책·예적금·대출은 그 플로우의 부품으로 재배치 |

### 2-4. 필요성 요약

> 청년에게 필요한 것은 또 하나의 가계부나 정책 검색 서비스가 아니라, **불규칙한 현금흐름을 규칙적인 재무 구조로 바꿔주고, 계획을 실제 이체·납부·저축으로 실행해주는 자동화 엔진**이다.

## 4. 타깃 사용자

### 4-1. 대상 정의

Stage 0(대학생)부터 Stage 2(사회초년생)까지, **수입이 불규칙하고 예산 관리 경험이 적은 청년**이다. 예산 애호가가 아니라 예산 초심자를 대상으로 한다.

코어 타겟과 시연 서사는 Stage 0~2 전 구간을 하나의 성장 스토리로 커버하되, 취업 이벤트로 자산 형성 기능이 해금되는 스킬트리 UX를 적용한다. 대학생 때 정책·봉투 때문에 유입된 사용자가 취업 후에도 남는 리텐션 구조이며, 서비스명 셋업의 서사와 일치한다.

### 4-2. 단계별 사용자

| Stage | 대상 | 재무 과제 | 이 서비스로 달라지는 것 |
| --- | --- | --- | --- |
| **0** | 대학생 | 수입 만들기 + 지키기 | 들쭉날쭉한 알바비가 매달 같은 날 같은 금액의 생활비로 바뀐다 |
| **1** | 취준생 | 버티기 | 수당 기반 생존 예산이 자동 배분되고 학자금 상환이 자동화된다 |
| **2** | 사회초년생 | 본격 자산 형성 | 목표 기반 저축 포트폴리오가 개설되고 자동 납입된다 |

> 상세 페르소나(구체적 인물 설정, 소득 구간, 계좌 구성)는 원본 문서에 정의되어 있지 않다. `TBD`

## 5. 서비스 정의와 포지셔닝

### 5-1. 한 줄 정의

**불규칙한 소득의 청년에게 규칙적인 재무 구조를 만들어주는 실행형 머니 플로우 엔진**

### 5-2. 네이밍 근거

'셋업(Setup)'은 금융 자립의 초기 구조(월급 시스템, 예산 봉투, 저축 파이프라인)를 대신 세팅해준다는 뜻이다.

### 5-3. 포지셔닝

| 유형 | 판정 |
| --- | --- |
| 기록하는 가계부 (뱅샐) | ❌ |
| 계획하는 예산표 (YNAB) | ❌ |
| **계획하고 실행하는 엔진** | ⭕ |

**은행 자동이체와의 차이**: 은행 자동이체는 사용자가 금액·날짜를 정한다. 셋업은 **얼마를, 언제, 어디로 보낼지를 소득 변동성과 소비 실적으로 계산하고, 매월 재계산해 자동 조정**한다. "산출 → 실행 → 원장 반영 → 재산출" 루프 자체가 이 서비스의 핀테크 정체성이다.

### 6-1. [F-01] 원장(Ledger)과 가상 봉투

| 항목 | 내용 |
| --- | --- |
| **목적** | 여러 계좌·여러 결제수단에서 발생하는 모든 자금 이동을 하나의 정합적인 원장으로 통합하고, 소비를 카테고리 예산에 정확히 한 번 반영한다 |
| **입력** | 금융망 API 계좌·카드 목록, 잔액, 입출금·카드 사용·정기결제 내역, 사용자의 관리 대상 선택(opt-in)과 역할 태그 |
| **출력** | 봉투별 잔여 예산, 계좌별 현금 여유, 복식 기록 원장, 대사 결과 |
| **의존** | F-02(봉투 예산의 총액 제약), F-04(거래 이벤트 공급) |

**처리**

- **역할 기반 계좌 모델**: 계좌 수를 고정하지 않는다. 금융망 API로 조회한 계좌·카드 중 사용자가 관리 대상으로 선택한 것들 위에 원장 레이어를 얹는다. 각 계좌에 역할 태그를 부여한다.

| 역할 태그 | 정의 |
| --- | --- |
| `수입` | 급여·알바비·지원금이 들어오는 계좌 |
| `소비` | 셀프 월급이 지급되고 체크카드가 연결된 생활비 계좌. 여러 개 가능 |
| `고정지출` | 정기결제·신용카드 청구가 걸린 출금 계좌들 |
| `저축` | 예적금 |

  하나의 계좌가 여러 역할을 겸할 수 있다. 한 역할에 여러 계좌가 있을 수 있고, 없는 역할은 온보딩 시 금융망 API로 생성한다. 비상금·가족 계좌처럼 건드리지 않을 계좌는 제외할 수 있으며, 엔진의 이체·충당은 선택된 계좌 안에서만 일어난다.

- **가상 봉투는 잔액의 분할이 아니라 예산이다**: 사용자는 체크카드(즉시 출금), 신용카드(결제일 일괄 청구), 계좌이체를 계좌별로 섞어 쓴다. 특정 계좌 잔액을 쪼개는 방식으로는 신용카드 소비를 반영할 수 없으므로, 봉투는 **결제수단·계좌와 무관한 카테고리별 월 지출 한도**로 정의한다. 예산은 사용자가 직접 설정하거나 F-05의 가이드로 책정하며, Σ(봉투 예산) ≤ 셀프 월급 *S* 를 만족하도록 연결된다.
- **결제수단 무관 자동 차감**: 어떤 채널에서 소비가 발생해도 소비 분류 모델이 카테고리를 판별해 해당 봉투의 잔여 예산을 차감한다. 신용카드는 **승인 시점에 차감**하고, 결제일의 청구 출금은 승인 건과 매칭해 이중 차감을 막는다(F-04).
- **복식 기록 원칙**: 모든 거래는 실계좌·카드 변동과 원장(봉투·역할 계정) 변동의 쌍으로 기록된다.
- **Safe-to-Spend 이원화**: 홈 화면에 두 값을 나란히 표시한다.

| 지표 | 정의 |
| --- | --- |
| ① 예산상 남은 돈 | Σ(봉투 잔여 예산) |
| ② 계좌별 현금 여유 | 각 계좌 잔액 − 다음 결제일까지 그 계좌에서 나갈 예정액(정기결제·카드 청구·충당 예정) |

  총잔액 하나가 아니라 **계좌별로 여유와 부족을 보여주어** 어느 계좌를 채워야 하는지가 바로 드러나게 하고, 총합은 보조 지표로 둔다. 신용카드 때문에 ①과 ②가 갈라지는 것이 청년 재무 사고의 전형이므로, 괴리 자체를 경고 신호로 사용한다.

**예외·경계**

- 봉투 소진 시 리밸런싱을 제안한다("여가비를 식비에서 차입하시겠어요?"). 차단이 아닌 넛지다.
- 결제수단이 여러 개일수록 대사가 어려워지며, 이것이 백엔드 최우선 기술 과제다(T1).

**수용 기준**

| ID | 기준 |
| --- | --- |
| AC-01-1 | **거래 반영 정합성 불변식**: 모든 소비 거래는 정확히 하나의 봉투에 정확히 한 번 반영된다 (누락 0, 중복 0) |
| AC-01-2 | 매 폴링 주기마다 "감지된 소비 거래 총액 = 봉투 차감 총액" 대사를 수행한다 |
| AC-01-3 | 불일치 시 자동 조정하지 않고 예외 격리·리뷰 대상으로 처리한다 |

### 6-2. [F-02] 의사결정 엔진: 셀프 월급 지급액 산정

| 항목 | 내용 |
| --- | --- |
| **목적** | 불규칙 수입에 인공적인 월급날을 만든다. 모든 수입은 `수입` 역할 계좌로 모이고, 엔진이 산출한 금액만 지정일에 `소비` 역할 계좌로 이체된다 |
| **출력** | 셀프 월급 *S*, 봉투별 배분 예산, 산출 근거(입력값·기준 기간·적용 수식) |
| **의존** | F-01(잔액·봉투), F-03(청구 예정액), F-05(배분 비율) |

**입력**

| 기호 | 정의 | 출처 |
| --- | --- | --- |
| *I₁ … I_N* | 최근 *N*개월(기본 6) 월별 순수입 | 금융망 입출금 내역 |
| *F* | 월 고정지출 합계 = **확정형**(월세·통신 등 금액 고정 정기결제) + **변동형**(신용카드 청구 예정액. 결제 주기 승인 누적 + 할부 회차분, F-03에서 매일 산출) | 선택 계좌 정기결제·카드 내역 통합 + 사용자 확인 |
| *s* | 월 저축 목표액 (Stage 2 목표 플랜 연동, 기본 0) | 사용자 설정 |
| *R* | `수입` 역할 계좌 잔액 합계 | 금융망 잔액 조회 |
| *B_min* | 비상금 하한 (기본: *F* 의 1개월분) | 규칙 |

**처리: 산출식**

```
I_safe = Q25(I₁ … I_N) × ( 1 − k · σ_I / μ_I )        # k 기본 0.2

S = max( 0, I_safe − F − s )        s.t.  R − S ≥ B_min
```

- 평균이 아닌 **하위 25% 분위(Q25)** 를 기준으로 삼아 "수입이 나쁜 달에도 지킬 수 있는 금액"을 구하고, 변동성 계수(σ/μ)가 클수록 보수화 계수 *k* 만큼 추가 할인한다.
- 셀프 월급 *S* 는 안전 수입에서 고정지출과 저축 목표를 선차감한 금액이다. 수입 계좌 잔액이 비상금 하한을 침범하면 *S* 를 하향 조정한다.
- **봉투 배분**: *S* 를 F-05가 산출한 카테고리 비율로 분할해 봉투 예산을 확정한다.

**처리: 재산출 (피드백)**

- 매월 말 실현 수입, 봉투별 초과·잔여, 고정지출 변동을 반영해 *I_safe*, *S*, 배분 비율을 재계산한다.
- 3개월 연속 잔여가 발생한 봉투는 예산을 줄이고 차액을 저축 파킹으로 돌리는 식의 조정안을 제시하고, 사용자 승인 후 다음 달 실행에 반영한다.

**예외·경계**

- 산출값이 직전 대비 급변하거나 대사 잔차가 미해결이면 실행을 보류한다(F-06 ②).

**수용 기준**

| ID | 기준 |
| --- | --- |
| AC-02-1 | 모든 산출은 결정론적이다. 동일 입력이면 동일 출력이 나온다 |
| AC-02-2 | 화면에 근거(입력값·기준 기간·적용 수식)를 함께 표시한다 |
| AC-02-3 | 백테스트에서 비상금 고갈 확률이 평균 기반 대조군 대비 유의하게 낮다 |
| AC-02-4 | 지급액의 월간 변동폭이 수입 변동폭보다 작다 |

### 6-3. [F-03] 자동 실행 (Execution)

| 항목 | 내용 |
| --- | --- |
| **목적** | 의사결정 엔진의 산출을 금융망 API로 실제 실행해 Plan-Do Gap을 제거한다 |
| **원칙** | 모든 실행은 **사용자 명의 계좌 간 이체 지시**다. 셋업이 자금을 보유하거나 결제를 차단하는 일은 없으며, 사용자가 미리 설정한 규칙에 따른 자기 구속 장치다 |
| **의존** | F-02(산출값), F-06(안전장치), F-04(실행 결과 확인) |

**처리: 실행 유형**

| 실행 | 내용 | 금융망 API |
| --- | --- | --- |
| **셀프 월급 이체** | 지정일에 `수입` 계좌 → `소비` 계좌로 *S* 이체 | 이체 |
| **신용카드 청구 예정액 산출** | 카드별 결제일·결제 주기를 기준으로 **이번 달 청구될 금액을 매일 재계산**. 주기 내 일시불 승인 누적 + 이번 회차 할부 원금 + 유이자 할부 수수료(카드사 수수료율 기반 회차별 계산). 산출액은 변동형 고정지출로 *F* 와 사전 충당에 반영 | 조회 |
| **고정지출 사전 충당 (Pre-funding)** | 선택된 계좌·카드의 정기결제 스케줄과 카드 청구 예정액을 통합해 결제일별 필요 금액을 산출하고, **각 결제일 전날 해당 출금 계좌에 부족액을 자동 이체**. 신용카드 결제일 청구 계좌도 충당 대상이라 카드 대금 연체(신용점수 직결)를 원천 차단하며, 충당된 금액은 소비 가능 잔액에서 빠져나가 사실상 격리된다 | 조회·이체 |
| **고정지출 자동 납부** | 월세·통신비·할부 회차(원금+수수료)가 충당된 출금 계좌에서 정기결제로 집행 | 정기결제 |
| **저축 파킹 (Sweep)** | 월말 봉투 잔여액과 `수입` 계좌 잉여를 예적금에 자동 납입. Stage 2에서는 목표 기반 포트폴리오 납입으로 연결 | 예적금 |
| **부채 실행** | 대출 상환액 자동 이체, 할부 최적화 Agent가 산출한 선결제 실행 | 이체·대출 |

**예외·경계**

- 할부 수수료율을 API가 주지 않으면 사용자 입력으로 폴백하고 신뢰도(`높음 / 중간 / 범위 추정`)를 표시한다. `❓ Q-04`
- 이체 API 실패, 다단계 실행의 부분 실패 처리는 F-06 ④를 따른다.

**수용 기준**

| ID | 기준 |
| --- | --- |
| AC-03-1 | 모든 실행 거래는 API 호출 시점에 원장에 선반영되고 자체 트랜잭션 ID를 갖는다 |
| AC-03-2 | 동일 요청 반복·타임아웃 후 재시도·폴링과 실행 동시 발생 시나리오에서 이중 이체 0건 |
| AC-03-3 | 결제일 실제 청구액과 예정액의 오차 원인(선결제·취소)을 100% 분류한다 |

### 6-4. [F-04] 거래 감지와 피드백 루프

| 항목 | 내용 |
| --- | --- |
| **목적** | 실제로 일어난 거래를 감지해 원장에 반영하고, 재산출 입력을 갱신해 루프를 닫는다 |
| **입력** | 금융망 API 계좌 입출금·카드 사용·정기결제 내역 |
| **출력** | 신규 거래 이벤트, 봉투 차감, 예외 큐, 갱신된 재산출 입력 |

**처리**

- **폴링 기반 준실시간 감지**: 금융망 API는 이벤트 푸시(webhook)가 없으므로, 백엔드 스케줄러가 내역을 주기적으로 조회하고 diff로 신규 거래 이벤트를 생성한다. API 호출 한도(rate limit)를 명세에서 확인한 후 폴링 주기를 결정한다. `❓ Q-01`
- **거래 출처 구분에 의한 중복 방지**
  - 우리가 실행한 거래(F-03)는 이미 원장에 선반영되어 있으므로, 폴링이 이를 감지하면 트랜잭션 ID·금액·시각 매칭으로 "이미 아는 거래"로 판별해 **확인 처리만** 한다.
  - 외부 발생 거래(사용자의 카드 결제·계좌이체·현금 인출 등)만 봉투 차감을 실행한다.
  - **신용카드 승인-청구 매칭**: 카드 승인 내역은 발생 시 봉투를 차감하고, 결제일에 청구 계좌에서 나가는 일괄 출금은 해당 기간 승인 건들의 합과 매칭해 **소비가 아닌 부채 상환**으로 원장에 기록한다.
- **멱등성**: 거래 고유번호 기준 처리 이력으로 동일 거래의 이중 반영·이중 이체를 차단한다.
- **루프 완성**: 감지된 거래가 원장에 반영되면 F-02의 재산출 입력이 갱신되어 다음 달 지급액·배분이 조정된다.

**예외 처리: 대사 잔차가 감지 신호다**

예상 원장과 실제 거래가 어긋나면(금액 불일치·미매칭 입금·예정 외 출금) 자동 조정하지 않고 **원인 분류 → 자동 매칭 시도 → 실패 시 사용자 확인 큐**로 보낸다.

| 예외 케이스 | 처리 |
| --- | --- |
| **결제 취소** | 취소 거래를 원 승인 건과 매칭(카드·금액·가맹점·원승인번호)해 봉투 잔여 예산을 복원한다. 부분 취소는 금액만 복원. 원 거래가 지난달이라 봉투가 마감됐으면 당월 봉투에 환입. 원 거래를 못 찾으면 "미매칭 환급"으로 확인 요청. `❓` 취소 구분 필드가 없으면 동일 가맹점·반대 부호 매칭 휴리스틱으로 대체 (Q-02) |
| **일괄 결제 후 정산 (더치페이)** | 정산 입금은 API상 일반 개인 입금과 구분되지 않고, 여러 건을 한 번에 정산받으면 어느 결제의 정산인지도 판별할 수 없어 **자동 감지·자동 매칭을 하지 않는다.** 결제 직후 알림에서 사용자가 "정산 예정" 플래그를 켜면 해당 건은 원장에 `받을 돈(미수금)`으로 잡히고 봉투에서는 내 몫만 차감된다. 이후 개인 입금이 감지되면 "정산 대기 목록에 배정하시겠어요?"라고 한 번만 묻고, 배정은 **전적으로 사용자가 지정**한다. 미배정 미수금은 기한 경과 시 사용자 확인 후 소비로 확정 |
| **할부 선결제·일시납 (카드사 앱에서 직접 실행)** | 정확한 감지는 **금융망 API의 할부 잔액·잔여 회차 조회로 건별 재동기화**하는 것이 유일한 방법이다. 해당 API가 없으면 결제일 청구 출금액이 예정액을 초과하는 **청구 대사 잔차를 "무언가 선결제됨"의 트리거로만** 사용한다. 초과분은 어느 할부 건인지 말해주지 않으므로 자동 판별하지 않고, 보유 할부 건 목록을 보여주어 사용자가 선택하게 한 뒤 스케줄·청구 예정액을 재계산한다. 초과액이 정확히 한 건의 잔여 원금과 일치할 때만 그 건을 기본 선택으로 제안. 셋업이 실행한 선결제는 F-03에서 이미 선반영되어 있어 해당 없음 `❓ Q-03` |

**프로젝트 범위 원칙**

금융망 API를 본 서비스의 **금융 백엔드**로 삼는다. 통장·카드·예적금·대출 상품의 생성·가입·조회와 입출금·카드 사용·정기결제 내역이 모두 API로 제공되므로, 서비스의 모든 금융 기능은 이 위에서 완결된다. 실사용 환경의 데이터 수집(SMS·알림 파싱)이나 상용화 라이선스 이슈는 MVP 범위에서 제외하고, **핀테크 엔진의 완결성과 정합성에 집중**한다.

### 6-5. [F-05] AI 머니 코치

| 항목 | 내용 |
| --- | --- |
| **목적** | 엔진의 입력(예산 책정)과 출력(리포트·경고·조정안)을 하나의 코치 페르소나가 담당한다 |
| **위치** | 정체성은 엔진에 있고, 코치는 전달 수단이다. 참고 모델은 Cleo(AI 재정 코치, Roast·Hype Mode, 18~36세 타겟)이지만 **Cleo는 계좌를 읽고 말하는 데서 끝나고 셋업의 코치는 실행 엔진 위에 있다**. 조언이 곧 실행 버튼이다 |

**① 도구 호출(tool-calling) 아키텍처: 숫자는 LLM이 만들지 않는다**

- 코치는 결정론적 엔진의 API를 도구로 호출하고, 그 결과만 자연어로 설명한다. 금액·판정·자격 상태는 어떤 경우에도 LLM이 생성하지 않는다.
- 대표 도구: `Safe-to-Spend 조회`, `카드 청구 예정액 조회`, `봉투 상태 조회`, `what-if 시뮬레이션`, `실행 제안 생성`.
- **what-if 시뮬레이션**: "적금 10만 원 늘리면?", "이번 주말 5만 원 써도 돼?" 같은 질문에 F-02 재산출을 가상 실행해 결과를 보여준다. 질문에 답하는 것을 넘어 "그렇게 하려면 여가비 봉투를 2만 원 줄여야 해요. 적용할까요? [승인]"까지 이어진다.
- 측정 가능한 과제: 도구 선택 정확도, 응답의 수치 grounding 검증, 환각 0건.

**② 예산 책정과 리밸런싱 (엔진의 입력)**

- **초기 예산 책정**: 온보딩 시 금융망 API로 조회한 거래 이력을 소비 분류 모델로 카테고리화하고, 소비 패턴·고정지출·수입 수준을 반영한 **개인 맞춤 봉투 예산안을 자동 제안**한다. 사용자는 승인·조정만 한다. 결과는 F-02의 배분 비율로 들어간다.
- **주간·월간 소비 리포트**: 카테고리별 추이, 유사 소득 구간 대비 비교, 이상 지출 감지(평소 대비 급증 카테고리).
- **예산 리밸런싱 제안**: 매월 말 실적 기반으로 다음 달 배분 조정안을 제시하고("식비는 3개월 연속 남았어요. 2만 원을 저축 파킹으로 돌릴까요?") 승인 시 F-02 재산출에 반영한다.

**③ 메모리: 구조화 프로필 + 이벤트 로그**

- 사용자 목표, 예외 처리 선택 이력(정산 습관, 자주 조정하는 봉투), 제안 승인·거절 이력을 구조화 프로필과 이벤트 로그로 저장해 개인화한다. 벡터 메모리 같은 무거운 구조는 두지 않으며, 대화 이력 검색이 필요하면 기존 FAISS 인프라를 재활용한다.
- 예: 3회 연속 거절된 유형의 제안은 빈도를 낮추고, 매월 말 반복되는 봉투 초과는 예산 책정 시 선반영한다.

**④ 캐릭터 기반 전달** → F-09

**⑤ 경계**

- 코치는 **제안만 하고 실행은 사용자 승인 후 엔진이 수행**한다(F-06). 코치가 임의로 자금을 움직이는 경로는 존재하지 않는다.
- 금융 조언의 책임 경계: 정보 제공이며 투자 권유·세무 대리가 아님을 화면 디스클레이머로 유지한다.
- 음성 인터페이스는 MVP 제외(P2).

**수용 기준**

| ID | 기준 |
| --- | --- |
| AC-05-1 | 응답 내 모든 숫자가 도구 호출 결과에서 유래했는지 자동 검사를 통과한다. 근거 없는 숫자 0건 |
| AC-05-2 | 코치의 제안은 사용자 승인 없이 실행되지 않는다 |

### 6-6. [F-06] 실행 안전장치와 신뢰성

자동 이체를 실행하는 서비스에서 잘못된 실행은 곧 사용자 피해다. 다음 장치를 실행 경로의 **필수 구성요소**로 둔다.

**① 사전 동의와 한도**

- 실행 유형별(셀프 월급 이체·사전 충당·저축 파킹·부채 실행) **사용자 opt-in 규칙**. 동의하지 않은 유형은 제안만 하고 실행하지 않는다.
- **1회·1일 이체 한도**를 사용자가 설정한다. 한도 초과 실행은 자동 보류 + 승인 요청.
- 관리 대상 계좌(F-01 opt-in) 밖으로의 이체는 어떤 경우에도 불가하다.

**② 예측 이탈 시 보류**

- 산출값이 직전 대비 급변하거나(예: 셀프 월급 *S* 가 전월 대비 ±30% 초과 변동), 대사 잔차가 미해결 상태이면 해당 실행을 **보류하고 사용자 확인**을 받는다. 데이터가 의심스러울 때 돈을 움직이지 않는다.

**③ 예고와 취소 창**

- 모든 실행은 **N시간 전 예고 알림**(기본 12시간)을 보내고, 그 안에 사용자가 취소·금액 수정할 수 있다. 예고 없는 즉시 실행은 사용자가 직접 트리거한 경우에 한한다.

**④ 실패 처리와 보상**

- 이체 API 실패 시 **idempotency key를 동반한 지수 백오프 재시도**. 재시도 한도 초과 시 긴급 알림을 보낸다. 특히 사전 충당 실패는 결제 실패로 이어지므로 결제일 전 반드시 사용자에게 도달해야 한다.
- 다단계 실행(충당 → 납부)의 부분 실패는 **보상 트랜잭션(saga)** 으로 원장을 일관 상태로 되돌린다.

**⑤ 감사 로그**

- 모든 실행·보류·취소·실패에 대해 **누가(사용자·엔진), 언제, 무엇을, 왜(적용 규칙·입력값·수식)** 를 불변 로그로 남긴다. 사용자는 "이 이체가 왜 일어났는지"를 화면에서 근거와 함께 확인할 수 있다.

### 6-7. [F-07] 신용 관리(Credit Health) 축

문서 곳곳에 흩어진 부채·카드 관련 기능을 하나의 축으로 묶는다. 이 축이 있어 셋업은 가계부(PFM)를 넘어 **여신 인접 영역**에 걸친다.

| 기능 | 위치 | 신용 관리 관점의 가치 |
| --- | --- | --- |
| 신용카드 청구 예정액 매일 산출 | F-03 | "이번 달 카드값"을 결제일 전에 안다 |
| 카드 청구 계좌 사전 충당 | F-03 | 카드 대금 연체(신용점수 직결) 원천 차단 |
| 유이자 할부 수수료 계산·선결제 순편익 판정 | F-03, F-08 | 불필요한 금융비용 절감, 잔여 회차 관리 |
| 대출 상환 스케줄·자동 이체·대환 순편익 | F-03, F-08 | 상환 연체 방지, 총비용 최소화 |
| 승인-청구 매칭 → 부채 상환 기록 | F-04 | 소비와 부채를 원장에서 분리 인식 |
| 카드·대출 실행 결과의 신용 영향 안내 | F-05 | 청년의 첫 신용 이력 형성 가이드 |

### 6-8. [F-08] 인텔리전스 레이어

기존 기획의 차별화 자산은 폐기되지 않고, 머니 플로우 엔진에 데이터를 공급하는 지능 레이어로 재배치된다.

| 기존 자산 | 개편 후 역할 |
| --- | --- |
| 정책 로드맵 엔진 + Agentic RAG | **수입 측 인텔리전스**. 놓친 지원금을 찾아 현금흐름(봉투)에 꽂아주는 부스터. "남들은 못 찾는 공돈 발굴기" |
| 할부 최적화 Agent | **지출 측 인텔리전스**. 유이자 할부의 회차별 수수료를 계산해 카드 청구 예정액(F-03)에 반영하고, 선결제 순편익 판정에서 실행(이체 API)까지 연결 |
| 소득 컷오프 경보 | 수입 계좌 흐름 분석의 파생 기능으로 유지 (정책 수혜자 한정) |
| 대출 상환·대환 계산 엔진 | Stage 1~2의 부채 관리 모듈. 대출 API로 상환 시뮬레이션을 실계좌 흐름으로 검증 |
| 세제 혜택 계산 (확장 v1) | Stage 2 연말정산 모듈로 유지 |
| 정책 변경 감지·Diff | 인텔리전스 레이어의 데이터 신선도 유지 장치로 통합 (Source Version Service와 일원화) |
| 소비 분류 파인튜닝 모델 | 카드 사용·출금 내역의 카테고리 판별 → 가상 봉투 **자동 차감 엔진**, F-05의 데이터 공급원 |

**핵심 원칙**: 정책 자격이 없는 사용자에게도 서비스의 코어(셀프 월급·봉투·사전 충당·파킹)는 100% 작동한다. 정책은 있으면 더 좋은 부스터일 뿐이다. → 컨설팅 지적 ② 해소.

### 6-9. [F-09] 게이미피케이션

숫자 경고는 무시되지만 캐릭터의 상태와 스트릭은 무시하기 어렵다는 점을 활용한다.

- 봉투별 상태를 **캐릭터의 감정 상태·게이지 이미지**로 표현한다. 여유(활기참) → 주의(걱정) → 소진(시듦).
- **스트릭(연속 달성)**: 예산 안에서 하루를 마치면 적립. 주간·월간 달성 뱃지로 규칙적 소비 습관을 강화한다.
- PUSH·대화 톤을 캐릭터 화법으로 통일한다: "여가비 봉투가 시들고 있어요 🥀 이번 주말은 식비 봉투가 도와줄 수 있대요."
- 예산 초심자에게 통제감이 아닌 **성취감 기반 습관 형성**을 제공한다. "자동+넛지" 철학의 UX 구현체다.

## 7. 사용자 플로우와 시나리오

### 7-1. 온보딩 플로우

1. 프로필 입력 (생애단계 포함)
2. 금융망 API로 계좌·카드 조회 → 사용자가 **관리 대상 선택(opt-in)** 과 역할 태그 지정. 비상금·가족 계좌는 제외 가능
3. 없는 역할 계좌는 금융망 API로 생성
4. 거래 이력 분석 → 소비 분류 → **맞춤 봉투 예산안 자동 제안**
5. 셀프 월급 금액·지급일 제안 → 사용자 승인·조정
6. 실행 유형별 opt-in 동의와 이체 한도 설정 (F-06 ①)
7. 원클릭 세팅: 자동이체·정기결제 등록

### 7-2. 정상 운영 루프

```
수입 입금 감지 → 셀프 월급 산정(F-02) → 지정일 이체(F-03)
      ↑                                        ↓
   재산출 입력 갱신                    봉투 예산 확정(F-01)
      ↑                                        ↓
  월말 실적 집계 ← 봉투 차감·대사(F-04) ← 소비 발생
      ↓
 사전 충당 → 고정지출 자동 납부 → 잔여 저축 파킹(F-03)
```

### 7-3. 플래그십 데모 시나리오 (심사용)

**주인공**: 알바하는 대학생에서 취준을 거쳐 취업까지 간 한 사용자의 성장 스토리 (스킬트리 해금 연출)

| # | 이벤트 | 사용자가 보는 것 | 시스템이 하는 일 | 관련 기능 |
| --- | --- | --- | --- | --- |
| 1 | **[Stage 0] 셋업 온보딩** | "월 50만 셀프 월급 + 맞춤 봉투 예산 5개" 자동 책정안 → 승인 | 거래 이력 분석, 예산안 산출, 계좌 생성·자동이체 등록 | F-01, F-02, F-05 |
| 2 | **입금 이벤트** | PUSH: "알바비 감지. 생활비 30만 배분, 25일 월세 출금 계좌에 20만 원 미리 채워뒀어요" | 알바비 45만 입금을 1분 내 감지 → 자동 배분 실행 | F-04, F-03 |
| 3 | **정책 부스터** | 월세지원 자격 발견 → 신청 로드맵 안내 | (수혜 가정) 지원금 20만 입금을 월세 출금 계좌 사전 충당에 투입, 정기결제로 월세 자동 납부, 아낀 돈은 파킹 | F-08, F-03 |
| 4 | **소비 이벤트** | 식비 캐릭터가 '걱정' 상태로 전환, 리밸런싱 제안 | 결제 발생 → 분류 모델이 "식비" 판별 → 봉투 차감 | F-04, F-01, F-09 |
| 5 | **코치 대화** | "이번 주말 여행 5만 원 써도 돼?" → "여가비 봉투가 1.2만 원 남아서 부족해요. 식비 봉투에서 4만 원 옮기면 가능하고, 이번 달 저축 파킹은 그대로예요. 옮길까요? [승인]" | Safe-to-Spend·what-if 도구 호출. 숫자는 전부 엔진 산출 | F-05 |
| 6 | **월말** | AI 소비 리포트 + 다음 달 예산 조정 제안, 예산 달성 스트릭 뱃지 | 봉투 잔여 7만 → 자유적립 적금 자동 파킹 (12시간 전 예고 알림 후 실행) | F-05, F-03, F-06, F-09 |
| 7 | **취업 이벤트 (해금 연출)** | 자산 형성 플랜 해금 → "2년 내 전세보증금 1,000만" 목표 설정 | 적금 포트폴리오 개설·자동 납입 + 학자금 상환 최적화 실행 | F-03, F-08 |

한 시나리오 안에서 금융망 API 5개 기능군, 파인튜닝 모델, 도구 호출 코치, 실행 안전장치(예고 알림), 정책 RAG가 전부 자연스럽게 등장한다.

### 8-3. 외부 연동: 금융망 API 활용 맵

컨설팅 지적 ①("핀테크가 겉돈다")의 해소 근거다.

| 금융망 API 기능 | 사용처 | Stage |
| --- | --- | --- |
| **입출금 데이터 조회** | 수입 감지(폴링) → 셀프 월급 산정 입력, 출금 감지 → 봉투 차감, 소득 흐름 분석 | 0·1·2 |
| **카드 사용·정기결제 내역 조회** | 결제 감지 → 소비 분류 → 봉투 차감, 고정지출 *F* 자동 집계, 할부 회차 추적 | 0·1·2 |
| **이체** | 셀프 월급 지급(`수입` → `소비`), 고정지출 사전 충당, 할부 선결제, 저축 파킹 | 0·1·2 |
| **정기 결제** | 월세 자동 납부, 고정지출 자동화, 적금 자동 납입 | 0·1·2 |
| **예적금 상품 등록·가입** | 자동 저축 파킹, 청년미래적금 모사 상품, 목표 기반 포트폴리오 | 0·2 |
| **대출 상품 등록** | 학자금대출 재현·상환 자동화, 대환 시뮬레이션 실검증 | 1·2 |

조회·이체·정기결제·예적금·대출 전 기능군이 전 단계에서 실사용되며, "핀테크가 Stage 2에만 있다"는 구조적 문제가 해소된다.

### 8-4. 핵심 알고리즘 요약

F-02의 산출식과 입력 정의를 그대로 사용한다. 파라미터 *N*(기본 6), *k*(기본 0.2), *B_min*(기본 *F* 1개월분)은 백테스트 결과로 정당화한다(§10).

## 10. 검증 전략

"구현했다"가 아니라 **"검증했다"** 를 배포 조건으로 삼는다.

| 대상 | 검증 방법 | 합격 기준 |
| --- | --- | --- |
| **원장 정합성** (F-01, F-04) | **속성 기반 테스트(property-based)**: 승인·취소·청구·이체·정산·선결제가 혼합된 무작위 거래 시퀀스를 생성해 불변식("모든 소비 거래는 정확히 한 봉투에 정확히 한 번") 검사. 예외 케이스별 시나리오 테스트 | 대사 불일치 0건. 불일치 발생 시 100% 예외 큐로 격리 |
| **셀프 월급 알고리즘** (F-02) | **백테스트**: 금융망 생성 데이터 + 합성 소득 시나리오(정규·계절성·급감)로 과거 구간 시뮬레이션. 비상금 고갈 확률, 지급액 변동폭, 잉여 축적량을 측정하고 **평균 기반 대조군**과 비교해 Q25·*k* 파라미터를 정당화 | 비상금 고갈 확률이 대조군 대비 유의하게 낮고, 지급액 월간 변동폭이 수입 변동폭보다 작음 |
| **실행·멱등성** (F-03, F-06) | 동일 요청 반복, 타임아웃 후 재시도, 폴링과 실행 동시 발생 시나리오 테스트 | 이중 이체 0건, 보상 트랜잭션 후 원장 일관 |
| **청구 예정액 산출** (F-03) | 결제일 실제 청구액과 예정액 대조 | 오차율 및 원인(선결제·취소) 분류 100% |
| **소비 분류 모델** (F-08) | 홀드아웃 정확도, 카테고리별 혼동 행렬 | 목표 정확도 설정 후 미달 카테고리는 사용자 확인으로 폴백 |
| **코치 grounding** (F-05) | 응답 내 모든 숫자가 도구 호출 결과에서 유래했는지 자동 검사 | 근거 없는 숫자 0건 |

**학습 데이터 확보**

소비 분류 모델은 금융망 모의 데이터의 가맹점명·카테고리 다양성을 먼저 확인하고, 부족하면 공개 소비 데이터셋과 **합성 거래 생성(가맹점명 템플릿 × 카테고리 × 금액 분포)** 으로 학습셋을 구축한다. 라벨링 기준을 문서화해 재현 가능하게 한다.

## 12. 기술 과제와 역할

각 항목을 **난이도**(구현이 어려운가), **참신성**(흔한 CRUD가 아닌가), **어필도**(심사에서 기술로 인정되는가)로 평가한다.

| ID | 도전 과제 | 내용 | 난이도 | 참신성 | 어필도 | 담당 |
| --- | --- | --- | --- | --- | --- | --- |
| **T1** | **원장 정합성 & 대사** | 복식 기록, 결제수단 다중(체크·신용·이체)에서 "모든 소비 거래는 정확히 한 봉투에 정확히 한 번" 불변식 유지. 신용카드 승인-청구 매칭, 취소·정산·선결제 예외 큐 | **상** | 상 | **상** | BE |
| **T2** | **멱등성 & 동시성 제어** | 폴링 감지와 실행 스케줄러가 같은 거래를 동시에 만질 때의 race, 이체 API 재시도 시 이중 이체 방지, 실행 실패 시 보상 처리 | 중상 | 중 | 중상 | BE |

## 16. 용어집

| 용어 | 정의 |
| --- | --- |
| **셀프 월급** | 불규칙 수입을 `수입` 역할 계좌에 모으고 매달 지정일에 엔진이 산출한 금액만 `소비` 계좌로 자동이체해 인공적 월급날을 만드는 것 |
| **역할 기반 계좌 모델** | 사용자가 관리 대상으로 선택한 N개 계좌에 수입·소비·고정지출·저축 역할 태그를 부여해 관리하는 모델. 계좌 수를 고정하지 않으며, 선택되지 않은 계좌는 엔진이 건드리지 않음 |
| **신용카드 청구 예정액 산출** | 카드별 결제일·결제 주기를 기준으로 이번 달 청구될 금액을 매일 재계산하는 것. 주기 내 일시불 승인 누적 + 이번 회차 할부 원금 + 유이자 할부 수수료. 수수료율을 API가 주지 않으면 사용자 입력 폴백에 신뢰도(높음·중간·범위 추정)를 표시 |
| **고정지출 사전 충당 (Pre-funding)** | 선택 계좌·카드의 정기결제 스케줄과 카드 청구 예정액을 통합해, 각 결제일 전날 해당 출금 계좌에 부족액을 자동 이체하는 것. 연체 방지와 소비 가능 잔액에서의 격리 효과 |
| **고정지출 (확정형·변동형)** | 확정형은 월세·통신처럼 금액이 고정된 정기결제, 변동형은 신용카드 청구처럼 결제일은 고정이나 금액이 승인 누적·할부 회차로 변하는 지출. 변동형은 엔진이 매일 예정액을 재계산 |
| **가상 봉투** | 결제수단·계좌와 무관한 카테고리별 월 지출 한도(예산). 사용자 설정 또는 AI 가이드로 책정하며, 어떤 채널의 소비든 분류되어 잔여 예산을 차감. 잔액 분할이 아니라 예산이므로 신용카드 소비도 반영 가능. 강제력 없는 넛지 |
| **Safe-to-Spend** | ① 예산상 남은 돈(Σ봉투 잔여 예산)과 ② 계좌별 현금 여유(각 계좌 잔액 − 다음 결제일까지 그 계좌에서 나갈 예정액)를 나란히 보여주는 홈 화면 대표 지표. 총합보다 계좌별 여유·부족을 우선 표시하며, 둘의 괴리가 경고 신호 |
| **AI 머니 코치** | 엔진의 입력(예산 책정)과 출력(리포트·경고·조정안)을 담당하는 대화형 페르소나. 결정론적 엔진 API를 도구로 호출해 결과만 설명하며, 숫자를 스스로 생성하지 않음. 제안만 하고 실행은 사용자 승인 후 |
| **what-if 시뮬레이션** | "적금 10만 늘리면?" 같은 가정 질문에 재산출을 가상 실행해 결과와 실행 제안을 보여주는 도구 |
| **grounding 검사** | 코치 응답 내 모든 숫자가 도구 호출 결과에서 유래했는지 자동 검증하는 절차. 근거 없는 숫자 0건이 합격 기준 |
| **감사 로그** | 모든 실행·보류·취소·실패에 대해 누가·언제·무엇을·왜(규칙·입력값·수식)를 남기는 불변 기록 |
| **스트릭** | 예산 안에서 하루 또는 한 주를 마친 연속 기록. 게이미피케이션 피드백의 핵심 지표 |
| **파킹(Sweep)** | 봉투 잔여액·수입 잉여를 규칙 기반으로 예적금에 자동 납입하는 것 |
| **Plan-Do Gap** | 예산 계획과 실제 이체·납부·저축 실행 사이의 간극. 기존 예산 앱의 구조적 한계 |
| **대사 (Reconciliation)** | 감지된 소비 거래 총액과 봉투 차감 총액을 맞춰보는 절차. 잔차는 예외 감지 신호로 사용 |
| **예외 큐** | 자동 매칭에 실패한 거래를 자동 조정하지 않고 사용자 확인 대상으로 격리하는 대기열 |

## 부록 A. 핀테크 적합성 판정

### A-1. 판정 기준

핀테크 여부는 "금융을 다루는가"가 아니라 **"서비스가 돈에 대해 무엇을 하는가"** 로 판별한다.

| 단계 | 서비스가 돈에 하는 일 | 예시 | 판정 |
| --- | --- | --- | --- |
| 정보 | 금융 정보를 보여줌 | 금융 뉴스, 정책 검색 | ❌ 콘텐츠·GovTech |
| 기록 | 돈의 흐름을 기록·분류 | 가계부 | ⚠️ 경계 (PFM 인정되나 약함) |
| **판단** | 돈을 어떻게 할지 계산·결정 | 로보어드바이저, 심사 엔진 | ⭕ |
| **실행** | 돈을 실제로 이동·운용 | 송금, 결제, 자동 저축 | ⭕ |
| **인프라** | 원장·대사·API·정산 | 뱅킹 코어, PG | ⭕ |

보조 판별 질문: **"이 서비스에서 돈을 빼면 무엇이 남는가?"** 무언가 남으면(습관 루프, 콘텐츠) 핀테크가 아니고, 아무것도 남지 않으면 핀테크다.

### A-2. 기존 기획 vs 현재 기획 매핑

| 기능 | 기존 기획 (컨설팅 전) | 현재 (v2·v3) |
| --- | --- | --- |
| 정책 로드맵·RAG | **핵심** — 정보 단계 | 부가 (수입 측 인텔리전스) |
| 할부 수수료 계산 | 계산기 — 기록 단계 | 청구 예정액 산출 + 선결제 **실행** |
| 소득 컷오프 경보 | 정보 단계 | 파생 기능 |
| 원장(복식 기록·대사) | 없음 | **핵심 — 인프라 단계** |
| 셀프 월급 산정 알고리즘 | 없음 | **핵심 — 판단 단계** |
| 자동 이체·정기결제·저축 파킹 | 없음 | **핵심 — 실행 단계** |
| 고정지출 사전 충당 | 없음 | **핵심 — 판단+실행** |
| 예적금·대출 상품 연동 | 시뮬레이션(기록) | 상품 생성·가입·자동 납입(**실행**) |

기존 기획은 정보·기록 단계에 머물렀고, 현재는 판단·실행·인프라 세 단계를 모두 갖췄다. 돈을 빼면 남는 것은 없다.

### A-3. 판정 유지 조건

핀테크 프로젝트로 적합하다. 단, 다음 3가지가 문서와 발표에서 지켜져야 "겉돈다"는 지적이 재발하지 않는다.

| 조건 | 상태 | 근거 위치 |
| --- | --- | --- |
| ① "은행 자동이체와 뭐가 다르냐"에 대한 답이 문서에 있어야 함 | ⭕ 산출 → 실행 → 원장 반영 → 재산출 루프, 지급액 산정 수식 명시 | §5-3, F-02 |
| ② 실행 기능이 시연에서만 되는 것이 아님을 설명할 수 있어야 함 | ⭕ 금융망 API를 서비스의 금융 백엔드로 정의, 실사용 이슈는 범위 외로 명시 | F-04 프로젝트 범위 원칙 |
| ③ 비핀테크 요소(정책 RAG·게이미피케이션·AI 리포트)가 코어보다 앞에 오지 않아야 함 | ⭕ §6 순서: 원장 → 판단 → 실행 → 피드백 → AI → UX | §6 구조 |

## 부록 B. 종합 판정

| 항목 | 판정 | 비고 |
| --- | --- | --- |
| 핀테크 카테고리 성립 | ⭕ | PFM + 자동 실행형. 판단·실행·인프라 3단계 충족 |
| "겉돈다" 지적 해소 | ⭕ (조건부) | 3조건 반영됨. 신용 관리 축 명명으로 더 견고 |
| 기술적 도전 과제 존재 | ⭕ | T1·T3·T4가 실질적 도전. CRUD 프로젝트 아님 |
| 기술적 도전의 검증·보호 | ⭕ | G1·G4 → F-06, G2·G3·G5 → §10, 신용 관리 축 → F-07, AI 코치 → F-05 |
| 발표 우선순위 | 원장(T1) → 사전 충당(T3) → 셀프 월급(T4) → 안전장치(G1) → AI → 정책 → UX | 비핀테크 요소는 뒤로 |

**한 줄 결론**: 기획은 핀테크로 적합하고 도전 과제도 충분하다. 점검에서 발견된 공백 G1~G5는 F-06(안전장치·신뢰성)과 §10(검증 전략)으로 반영되었고, 신용 관리 축(F-07)과 AI 머니 코치(F-05, Cleo 대비 차별화 §5-4 ②)도 추가되었다.
