# 셋업(Setup) 기획 발표 서사 v2

## 「신비한 건축사전」 고조회수 문법 적용본

- 기준 기획: 「개선된 기획 고도화 v4」, 「셋업 사용자 여정 v4」
- 채널 조사 기준: 2026년 8월 30일
- 발표 길이: 약 7분
- 발표 제목: **돈을 잘 썼는데도 아무것도 쌓이지 않는 이유**
- 부제: **소비가 도시가 되는 생활 금융 서비스, 셋업**

> 채널의 문장이나 고유 표현을 복제하지 않고, `익숙한 장면 → 모순 → 당연한 해법의 실패 → 발상 전환 → 작동 원리 → 현재 장면 회수`라는 검증된 구조만 적용한다.

---

## 1. 이번 발표가 따를 구조

```text
익숙한 월말 화면
→ 돈은 남았지만 성취는 남지 않는 모순
→ 더 자세한 분석과 알림이라는 첫 해법
→ 정보만 늘고 행동은 바뀌지 않는 한계
→ 게임과 보상이라는 두 번째 해법
→ 소비와 게임이 분리되거나 소비를 부추기는 한계
→ 문제 재정의
→ 소비 자체를 도시의 건축 규칙으로 전환
→ 거래·예산·결제 준비가 도시를 움직이는 원리
→ 사용자의 한 달이 달라진 상태
→ 첫 문장 회수
```

핵심 반전은 발표 중간에 둔다.

> **금융 앱에 게임을 붙이는 대신, 한 달의 소비 자체를 도시의 건축 규칙으로 만든다.**

## 2. 슬라이드별 발표 서사

| # | 시간 | 슬라이드 제목 | 발표 나레이션 | 화면에 보여줄 것 |
|---:|---:|---|---|---|
| 1 | 0:00~0:25 | 돈은 남았는데, 성취는 남지 않습니다 | “한 달 동안 예산을 잘 지켰습니다. 돈도 남았습니다. 그런데 가계부를 열면 남는 건 숫자와 그래프뿐입니다. 내가 잘한 한 달은 어디에도 쌓이지 않고, 다음 달이 되면 다시 처음부터 시작합니다.” | 월말 가계부 화면 하나. 숫자 옆에는 텅 빈 도시 부지. 문구는 `돈은 남았다 / 성취는 남지 않았다` 두 줄만 둔다. |
| 2 | 0:25~0:50 | 우리는 이미 충분히 기록하고 있습니다 | “거래 내역은 자동으로 모이고 식비, 교통, 주거, 구독으로 분류됩니다. 지난달보다 얼마나 더 썼는지도 알 수 있습니다. 문제는 기록이 부족한 게 아닙니다. 알아도 계속 보지 않는다는 겁니다.” | 계좌·카드 거래가 한 화면으로 모이는 흐름. 기능명 대신 `수집 → 분류 → 리포트` 세 단계만 표시한다. |
| 3 | 0:50~1:15 | 그럼 분석을 더 자세히 보여주면 될까요? | “AI가 소비를 분석하고, 그래프를 더 정교하게 만들고, 예산 초과 알림을 자주 보내면 해결될 것 같습니다. 실제 금융앱도 대부분 이 방향으로 발전했습니다.” | 그래프·알림·AI 조언 카드가 화면에 하나씩 추가되는 장면. 청중이 먼저 떠올릴 답을 충분히 인정한다. |
| 4 | 1:15~1:45 | 정보가 늘어도 들어올 이유는 생기지 않습니다 | “하지만 분석은 앱을 연 순간에만 작동합니다. 해외 앱 통계에서 금융앱의 30일차 평균 리텐션은 4.2%였습니다. 보지 않는 분석은 행동을 바꾸지 못합니다. 결제일이 오면 사용자는 여전히 날짜와 금액과 계좌를 기억하고, 필요한 돈을 직접 옮깁니다.” | 30일이 지나며 알림 카드가 사라지는 장면. 숫자는 `D30 4.2%` 하나만 크게 쓰고 `해외 앱 통계 기준`을 각주로 남긴다. |
| 5 | 1:45~2:10 | 그럼 게임을 붙이면 될까요? | “매일 들어오게 만들려면 출석, 미션, 코인을 붙일 수 있습니다. 실제 금융앱의 만보기와 리워드는 재방문을 잘 만듭니다. 소비를 도시로 바꾼 Fortune City도 이미 존재합니다.” | `금융 기능`과 `게임 화면`을 나란히 놓는다. Fortune City는 선행 사례로 공정하게 인정한다. |
| 6 | 2:10~2:45 | 문제는 보상의 기준입니다 | “게임이 소비와 무관하면 사용자는 게임만 잘하게 됩니다. 반대로 기록량과 지출량을 보상하면 도시를 키우려고 더 쓰는 역효과가 생길 수 있습니다. 게임을 붙였지만 소비 습관은 그대로인 셈입니다.” | 두 갈래 단면. `출석 보상 → 소비와 무관`, `지출 보상 → 더 쓰고 싶은 유혹`. 가운데에 끊어진 연결선을 보여준다. |
| 7 | 2:45~3:15 | 진짜 문제는 두 시스템이 떨어져 있다는 것입니다 | “소비 관리 기능과 앱에 다시 들어올 이유가 서로 떨어져 있었습니다. 한쪽은 숫자를 보여주지만 재미가 없고, 다른 쪽은 재미있지만 내 소비를 바꾸지 못합니다. 관리와 게임이 다른 규칙으로 움직이는 것이 진짜 문제였습니다.” | 왼쪽 `관리: 정확하지만 닫힘`, 오른쪽 `게임: 재밌지만 무관`. 둘 사이의 빈 공간을 강조한다. |
| 8 | 3:15~3:40 | 그래서 셋업은 게임을 붙이지 않았습니다 | “셋업은 금융 앱에 게임을 붙이지 않습니다. 한 달의 소비 자체를 도시의 건축 규칙으로 만듭니다. 예산은 설계도, 소비는 공정, 월말은 준공 검사입니다.” | 빈 공간이 하나의 도시 단면으로 합쳐지는 제품 공개 장면. `예산=설계도 / 소비=공정 / 월말=준공`만 남긴다. |
| 9 | 3:40~4:10 | 가입하는 순간, 내 소비로 만든 도시가 생깁니다 | “계좌와 카드를 연결하면 직전 1~3개월의 거래가 자동으로 분류됩니다. 중앙에는 중앙은행이 서고, 주변 여덟 부지에는 식비, 교통, 주거, 구독 같은 카테고리 건물이 생깁니다. 그래서 사용자는 빈 땅이 아니라 이미 완성된 Lv.1 도시에서 시작합니다. 이미 당신의 소비로 만든 도시입니다.” | 중앙은행과 팔방 Lv.1 건물이 생기는 온보딩 애니메이션. 건물을 탭하면 원인 거래로 내려가는 단면을 한 번 보여준다. |
| 10 | 4:10~4:45 | 건물은 돈을 덜 썼다고 무조건 자라지 않습니다 | “변동 소비는 월 진행률과 예산 소진률을 비교한 페이스로 보고, 월세와 구독 같은 고정 지출은 제때 준비하고 출금했는지로 판단합니다. 저축의 기준은 목표 달성률입니다. 서로 다른 소비를 같은 잣대로 벌주지 않습니다.” | 세 건물 단면. `변동 소비=페이스`, `고정 지출=이행`, `저축=목표`. 복잡한 임계값 표는 부록으로 보낸다. |
| 11 | 4:45~5:15 | 도시를 키우는 방법은 하나뿐입니다 | “보상 기준은 계획 준수 하나입니다. 한 주를 계획 속도로 보내면 주간 코인으로 가로수와 조명을 꾸미고, 한 달을 완주하면 월간 코인으로 건물을 키웁니다. 출석, 클릭, 공유에는 코인을 주지 않습니다. 현금 구매와 랭킹도 넣지 않습니다. 계획을 지킨 결과로 도시가 자랍니다.” | 주간 코인은 꾸미기, 월간 코인은 성장으로 갈라지는 두 경로. `획득 조건: 계획 준수`를 하나의 입구로 표시한다. |
| 12 | 5:15~5:45 | 도시 뒤에서는 돈도 필요한 곳에 제때 준비됩니다 | “건물은 단순한 그림이 아닙니다. 고정 지출 건물은 결제일 전에 필요한 돈이 지정 계좌에 준비되면 안정됩니다. 불필요한 구독을 해지하면 그 자리에 공원이 생기고, 할부를 완납하면 다리가 완성됩니다. 금융 기능의 실행 결과가 도시에 남습니다.” | `출금 D-3 → 필요한 금액 계산 → 지정 결제 계좌 이동 → 건물 안정` 흐름. 구독 해지 뒤 생기는 공원, 할부 완납 뒤 완성되는 다리를 이어 보여준다. |
| 13 | 5:45~6:15 | 사용자는 도시를 보러 오고, 금융 행동을 바꾸고 나갑니다 | “가입할 때 Lv.1 도시를 받고, 매일 어제의 소비가 반영된 도시를 확인합니다. 매주 코인으로 꾸미고, 매월 건물을 업그레이드하며 다음 달 예산을 조정합니다. 위험 상태에서도 남은 기간의 회복 경로를 보여줍니다. 한 번의 실패가 도시 전체를 포기하게 만들지 않습니다.” | `온보딩 → 일일 확인 → 주간 꾸미기 → 월간 성장 → 다음 달 설계`의 원형 루프. 위험 건물 옆에는 `남은 N일, 하루 X원` 복구 경로를 표시한다. |
| 14 | 6:15~6:45 | 이번 프로젝트에서 검증할 것은 도시의 행동 효과입니다 | “프로젝트에서는 발주처 내부 API와 데모 거래 데이터만 사용하며, 실제 금융기관 계좌와는 연동하지 않습니다. MVP 구현 범위는 중앙은행과 팔방 도시 생성, 월말 판정, 월간 코인, 부실 건물에서 원인 거래로 내려가는 흐름까지입니다. 목표는 금융앱 평균 4.2%를 넘는 D30 리텐션 10%와 계획 준수율의 개선입니다. 아직 성과가 아니라 검증할 가설입니다.” | `내부 API·데모` 범위 표시. MVP 네 항목과 `D30 10% 목표`를 분리하고, 목표 옆에 `검증 전` 배지를 붙인다. |
| 15 | 6:45~7:10 | 지킨 계획이 도시로 남습니다 | “처음에는 돈은 남았지만 성취는 남지 않았습니다. 셋업에서는 다릅니다. 한 달 동안 지킨 계획이 건물과 거리와 랜드마크로 남습니다. 셋업은 소비를 기록하는 가계부가 아닙니다. 한 달의 소비로 나만의 도시를 짓고, 그 뒤에서 소비 분석과 결제 자금 준비가 함께 작동하는 생활 금융 서비스입니다.” | 1번 슬라이드의 월말 화면으로 돌아온다. 텅 빈 부지가 완성된 도시로 바뀐다. 마지막 문구는 `지킨 계획이 도시로 남는다` 한 줄만 둔다. |

## 3. 발표용 연결 문장

슬라이드 사이에서 다음 문장만 고정한다. 채널의 고유 문구는 사용하지 않는다.

| 전환 | 연결 문장 |
|---|---|
| 기록 → 첫 해법 | “기록이 부족하지 않다면, 더 정확하게 알려주면 될까요?” |
| 첫 해법 → 한계 | “문제는 분석의 정확도가 아니라, 그 화면을 다시 열 이유였습니다.” |
| 한계 → 두 번째 해법 | “그래서 금융앱들은 외부의 게임 요소를 도입하기 시작했습니다.” |
| 두 번째 해법 → 한계 | “그런데 게임 점수와 소비 결과의 기준은 서로 달랐습니다.” |
| 문제 재정의 → 제품 공개 | “셋업은 두 시스템을 연결하지 않았습니다. 처음부터 하나의 규칙으로 만들었습니다.” |
| 제품 원리 → 실행 기능 | “도시가 자라는 장면 뒤에는 실제 금융 행동이 있습니다.” |
| 성공 상태 → 결말 | “이제 처음의 월말 화면으로 돌아가 보겠습니다.” |

## 4. 화면 제작 규칙

「신비한 건축사전」의 현재 인기 영상은 장식보다 인과를 보여준다. 발표 화면도 같은 원칙을 따른다.

1. 한 슬라이드에는 대상 하나와 질문 하나만 둔다.
2. 숫자는 한 장에 하나만 크게 쓴다.
3. 도시 전체를 보여준 뒤 건물 단면과 원인 거래로 확대한다.
4. 빨간 강조선은 데이터 이동, 위험, 기준선에만 사용한다.
5. 기능 목록 대신 `입력 → 판단 → 도시 변화`를 움직임으로 보여준다.
6. 제품 공개 전에는 완성된 도시 화면을 전부 보여주지 않는다.
7. 반전 뒤에는 말보다 작동 장면을 길게 보여준다.
8. 마지막 슬라이드는 첫 슬라이드와 같은 구도를 사용해 빈 부지와 완성 도시만 바꾼다.

## 5. 발표에서 빼야 할 것

- `만약 이런 서비스가 있다면`으로 시작하는 가상 질문
- 초반의 핵심 기능 8개 나열
- 한 슬라이드에 여러 통계와 경쟁사를 동시에 넣는 구성
- 도시를 단순 리워드 스킨으로 설명하는 표현
- 출석·클릭·공유로 코인을 얻는 것처럼 들리는 설명
- 실제 금융기관 연동이 된 것처럼 보이는 시연 문구
- D30 10% 목표를 달성 결과처럼 말하는 표현
- 채널의 시그니처 문장을 그대로 따라 하는 표현

## 6. 30초 요약본

> “한 달 동안 예산을 지켜도 가계부에 남는 건 숫자와 그래프뿐입니다. 분석을 더 자세히 보여줘도 다시 들어올 이유는 생기지 않고, 게임을 따로 붙이면 소비 행동과 보상이 분리됩니다. 셋업은 이 구조를 뒤집었습니다. 예산을 설계도로, 소비를 공정으로 바꿔 한 달의 계획 준수 자체가 도시를 키우게 합니다. 사용자는 도시를 보러 오고, 그 뒤에서 소비 분석과 결제 자금 준비가 작동합니다. 셋업에서는 지킨 계획이 도시로 남습니다.”
