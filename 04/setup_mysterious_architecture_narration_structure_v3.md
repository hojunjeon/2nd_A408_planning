# 셋업(Setup) 기획 발표 서사 v3

## 「신비한 건축사전」 고조회수 문법 적용본

- 기준 기획: 「개선된 기획 고도화 v4」, 「셋업 사용자 여정 v4」
- 채널 조사 기준: 2026년 8월 30일
- 발표 길이: 약 7분
- 발표 제목: **돈을 잘 썼는데도 아무것도 쌓이지 않는 이유**
- 부제: **소비가 도시가 되는 생활 금융 서비스, 셋업**

> 채널의 문장이나 고유 표현을 복제하지 않고 `익숙한 장면 → 모순 → 당연한 해법의 실패 → 발상 전환 → 작동 원리 → 현재 장면 회수`라는 검증된 구조만 적용한다.

**v2 → v3 변경 사항**

[격차 분석](RESEARCH/mysterious-architecture-channel_2026-08-30/pitch-gap-analysis.md)에서 확인된 다섯 가지를 반영했다.

1. 반전 이후 185초의 무긴장 구간을 끊기 위해 2차 문제 슬라이드를 신설했다. 판정이 틀릴 수 있다는 약점을 발표자가 먼저 말한다.
2. 9~12의 재요약이던 루프 슬라이드를 삭제하고 그 자리에 검증 설계를 넣었다.
3. 문제 정의에 리볼빙 이월잔액과 수수료율을 넣어 규모를 금액으로 증명한다. 구독 관련 수치는 발표 범위에서 제외하고 질의응답용으로 남긴다.
4. 미구현 제품을 작동 중으로 오인하지 않도록 슬라이드 9~13 화면에 `설계안` 라벨을 상시 노출한다.
5. 마지막에 요청 한 줄을 넣고 통념 기각에 마이데이터 제도 근거를 붙였다.

## 1. 이번 발표가 따를 구조

```text
익숙한 월말 화면
→ 돈은 남았지만 성취는 남지 않는 모순
→ 문제의 규모를 금액으로 증명
→ 더 자세한 분석과 알림이라는 첫 해법
→ 정보만 늘고 행동은 바뀌지 않는 한계
→ 게임과 보상이라는 두 번째 해법
→ 소비와 게임이 분리되거나 소비를 부추기는 한계
→ 문제 재정의
→ 소비 자체를 도시의 건축 규칙으로 전환
→ 거래·예산·결제 준비가 도시를 움직이는 원리
→ 그 판정이 틀릴 수 있다는 2차 문제와 보정
→ 효과를 어떻게 측정할지
→ 사용자의 한 달이 달라진 상태
→ 첫 문장 회수
```

핵심 반전은 발표 중간에 둔다.

> **금융 앱에 게임을 붙이는 대신, 한 달의 소비 자체를 도시의 건축 규칙으로 만든다.**

반전 이후를 기능 나열로 채우지 않는다. 원리를 보여준 다음 곧바로 그 원리의 약점을 꺼내고 그것을 어떻게 검증할지 말한다.

| 14 | 6:05~6:40 | 이 효과는 이렇게 측정합니다 | “프로젝트에서는 발주처 내부 API와 데모 거래 데이터만 사용하며, 실제 금융기관 계좌와는 연동하지 않습니다. MVP는 도시 생성, 월말 판정, 월간 코인, 부실 건물에서 원인 거래로 내려가는 흐름까지 만듭니다. 측정은 도시를 본 코호트와 보지 않은 코호트의 카테고리별 예산 준수율 변화를 비교하는 방식입니다. 목표는 금융앱 평균 4.2%를 넘는 D30 리텐션 10% 이상입니다. 코인을 받으려고 월말에 소비를 미루는 왜곡이 생기는지도 함께 감시합니다. 아직 성과가 아니라 검증할 가설입니다.” | 왼쪽에 `내부 API·데모` 범위, 오른쪽에 `노출 코호트 대 미노출 코호트` 비교 설계. `D30 10% 이상` 옆에 `검증 전` 배지를 붙이고, 아래에 가드레일 지표 한 줄을 둔다. |
| 15 | 6:40~7:10 | 지킨 계획이 도시로 남습니다 | “처음에는 돈은 남았지만 성취는 남지 않았습니다. 셋업에서는 다릅니다. 한 달 동안 지킨 계획이 건물과 거리와 랜드마크로 남습니다. 셋업은 소비를 기록하는 가계부가 아닙니다. 한 달의 소비로 나만의 도시를 짓는 소비 관리 게임이고, 그 뒤에서 소비 분석과 결제 자금 준비가 함께 작동합니다. 이 구조로 MVP를 만들어 도시의 행동 효과를 검증하려 합니다.” | 1번 슬라이드의 월말 화면으로 돌아온다. 텅 빈 부지가 완성된 도시로 바뀐다. 마지막 문구는 `지킨 계획이 도시로 남는다` 한 줄, 그 아래 요청 한 줄을 둔다. |

## 3. 발표용 연결 문장

슬라이드 사이에서 다음 문장만 고정한다. 채널의 고유 문구는 사용하지 않는다.

| 전환 | 연결 문장 |
|---|---|
| 문제 규모 → 첫 해법 | “비용이 이렇게 큰데도 왜 아직 안 풀렸을까요?” |
| 첫 해법 → 한계 | “문제는 분석의 정확도가 아니라, 그 화면을 다시 열 이유였습니다.” |
| 한계 → 두 번째 해법 | “그래서 금융앱들은 외부의 게임 요소를 도입하기 시작했습니다.” |
| 두 번째 해법 → 한계 | “그런데 게임 점수와 소비 결과의 기준은 서로 달랐습니다.” |
| 문제 재정의 → 제품 공개 | “셋업은 두 시스템을 연결하지 않았습니다. 처음부터 하나의 규칙으로 만들었습니다.” |
| 판정 규칙 → 2차 문제 | “그런데 이 판정을 그대로 믿으면 안 되는 이유가 있습니다.” |
| 보정 → 보상 체계 | “판정을 신뢰할 수 있게 만든 다음에야 보상을 걸 수 있습니다.” |
| 제품 원리 → 측정 설계 | “여기까지가 설계이고, 남은 건 이게 실제로 통하는지 확인하는 일입니다.” |
| 성공 상태 → 결말 | “이제 처음의 월말 화면으로 돌아가 보겠습니다.” |

## 4. 화면 제작 규칙

「신비한 건축사전」의 현재 인기 영상은 장식보다 인과를 보여준다. 발표 화면도 같은 원칙을 따른다.

1. 한 슬라이드에는 대상 하나와 질문 하나만 둔다.
2. 크게 쓰는 숫자는 슬라이드마다 하나로 제한한다. 보조 근거는 각주로 붙이되 화면에서 빼지 않는다. 발표 전체의 숫자 총량을 줄이는 규칙이 아니다.
3. 도시 전체를 보여준 뒤 건물 단면과 원인 거래로 확대한다.
4. 빨간 강조선은 데이터 이동, 위험, 기준선에만 사용한다.
5. 기능 목록 대신 `입력 → 판단 → 도시 변화`를 움직임으로 보여준다.
6. 제품 공개 전에는 완성된 도시 화면을 전부 보여주지 않는다.
7. 반전 뒤에는 말보다 작동 장면을 길게 보여준다.
8. 마지막 슬라이드는 첫 슬라이드와 같은 구도를 사용해 빈 부지와 완성 도시만 바꾼다.
9. 슬라이드 9부터 13까지는 화면 모서리에 `설계안` 라벨을 계속 띄운다. 구현된 제품으로 오인되지 않게 하는 장치다.
10. 인용한 통계에는 출처와 기준 시점을 화면에 함께 표기한다.

## 5. 발표에서 빼야 할 것

- `만약 이런 서비스가 있다면`으로 시작하는 가상 질문
- 초반의 핵심 기능 8개 나열
- 한 슬라이드에 여러 통계와 경쟁사를 동시에 넣는 구성
- 도시를 단순 리워드 스킨으로 설명하는 표현
- 출석·클릭·공유로 코인을 얻는 것처럼 들리는 설명
- 실제 금융기관 연동이 된 것처럼 보이는 시연 문구
- D30 10% 목표를 달성 결과처럼 말하는 표현
- 채널의 시그니처 문장을 그대로 따라 하는 표현
- 판정이 항상 정확한 것처럼 들리는 설명. 예산이 AI 추정치라는 사실을 감추지 않는다
- 반전 이후 기능을 네 개 이상 연달아 설명하는 구성
- 앞 슬라이드를 다시 요약하는 슬라이드

## 8. 부록: 질의응답 대비

슬라이드를 늘리지 않고 방어하기 위한 표다. 앞쪽은 기획서에 답이 있으므로 근거만 확인하면 되고 뒤쪽은 아직 정하지 않은 부분이므로 모른다고 답해야 한다.

### 8-1. 기획서에 답이 있는 질문

| 질문 | 답변 요지 | 근거 |
|---|---|---|
| 예산이 틀리면 판정도 틀리지 않나 | 10% 이내 초과는 부실로 보지 않는다. AI 제안값의 오차 책임을 사용자에게 넘기지 않기 위한 규칙이다 | v4 상태 판정 규칙 |
| 월초 거래 몇 건으로 위험 판정이 나오지 않나 | 변동 소비형은 1~5일차 판정을 유보한다. 소액 예산은 절대 여유액 기준을 병행하며 잔여 예산이 평균 1회 결제액 이상이면 강등하지 않는다 | v4 보정 장치 |
| 이사나 여행이 있는 달은 어떻게 되나 | 특별 공사 기간으로 표시하면 강등 판정에서 제외한다. 연 2~3회로 제한한다 | v4 엣지 케이스 |
| 한 카테고리 실패로 도시 전체가 무너지나 | 도시 전체 상태는 카테고리별 예산 가중 평균이다. 한 건물 실패가 전체로 번지지 않는다 | v4 복구 메커니즘 |
| 실패한 사용자가 앱을 피하지 않나 | 경고에는 반드시 회복 경로를 함께 낸다. 위험 진입 후 7일 내 미접속률을 가드레일 지표로 감시한다 | v4 복구 메커니즘, 성과 지표 |
| 코인 때문에 소비를 미루는 왜곡이 없나 | 월말 급감과 익월 초 반동 패턴을 감시하며 발생하면 지급 규칙을 조정한다 | v4 성과 지표 가드레일 |
| 게임 에셋 제작 비용을 감당할 수 있나 | 3D 없이 2D 타일로 만들고 팔방 구조는 아이소메트릭이나 탑뷰 3×3 그리드로 구현한다. 건물 외형과 상태 오버레이와 꾸미기 레이어를 분리해 원화 작업량을 줄인다 | v4 구현 로드맵 기술 노트 |
| 실서비스로 가면 규제가 막지 않나 | 이번 범위 밖이다. 전환 시 마이데이터 연동과 오픈뱅킹 출금이체 동의 또는 제휴 기관 방식을 검토한다 | v4 프로젝트 범위와 제약 |
| 왜 기존 앱은 이걸 안 했나 | 개별 앱의 역량 문제가 아니라 마이데이터가 조회 중심으로 제한된 제도 공백이다. 금융위도 한계를 공식 인정했다 | v4 시장·경쟁 구도 |

### 8-2. 아직 정하지 않은 것

질문이 나오면 정해지지 않았다고 답하고 검토 대상으로 남긴다. 있는 것처럼 말하지 않는다.

- 자동 분류가 틀렸을 때 사용자가 고치는 방법, 고친 뒤 판정과 지급된 코인의 재계산 규칙
- 자동 준비 이체 자체가 실패했을 때의 재시도와 통지 절차. 현재는 건물의 이행 실패 표시만 있다
- 거래 내역을 다루는 만큼 필요한 개인정보 보호와 보안 설계
- 혜택을 놓친다는 문제의 정량 근거. 기획서에도 추가 조사 예정으로 표기되어 있다
- 팀 구성과 역할 분담, 단계별 기간. 렌더링 방식과 상태 계산 구조는 기획서 기술 노트에 있지만 구체적인 프레임워크와 언어는 정해지지 않았다
