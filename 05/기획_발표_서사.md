# 기획 발표 서사

발표 제목: 숫자를 보여줘도 돈 관리가 달라지지 않는 이유

부제: 소비를 알아보고 행동까지 챙기는 캐릭터 AI 금융 비서

예상 길이: 약 7분 20초

상태: 설계안

> 「신비한 건축사전」의 고유 문장이나 표현은 복제하지 않는다. `익숙한 장면 → 모순 → 당연한 해법의 실패 → 발상 전환 → 작동 원리 → 2차 문제 → 검증 → 첫 장면 회수`라는 서사 구조만 적용한다.

## 1. 발표의 핵심 반전

> 금융 정보를 캐릭터로 꾸미는 것이 아니라, 캐릭터가 그 정보를 이해하고 다음 행동까지 챙기게 합니다.

반전 전에는 사용자가 익숙하게 겪는 장면과 기존 해법의 한계를 보여준다. 반전 뒤에는 기능을 나열하지 않고 `상태 → 설명 → 제안 → 승인 → 실행`이 이어지는 장면을 보여준다.

## 2. 전체 흐름

```text
잔액은 보이는데 지금 쓸 수 있는 돈은 모르는 장면
→ 정보가 있어도 행동으로 이어지지 않는 모순
→ 그래프와 알림을 늘리는 첫 해법
→ 사용자가 직접 해석해야 하는 한계
→ 소비를 도시로 바꾸는 두 번째 해법
→ 카테고리 예산과 자유로운 꾸미기 규칙의 충돌
→ 문제 재정의
→ 캐릭터를 AI 금융 비서로 전환
→ 상태·설명·제안·승인·실행의 원리
→ AI의 오판과 과신이라는 2차 문제
→ 계산·설명 분리와 승인 장치
→ MVP 검증 범위
→ 첫 장면 회수
```

## 4. 고정 연결 문장

| 전환 | 연결 문장 |
|---|---|
| 익숙한 장면 → 문제 | “정보가 없어서 어려운 걸까요?” |
| 첫 해법 → 한계 | “그래프가 정확해져도, 그다음 판단은 여전히 사용자가 해야 합니다.” |
| 두 번째 해법 → 한계 | “도시는 매력적이지만, 예산과 꾸미기가 같은 규칙으로 움직이지는 않습니다.” |
| 문제 재정의 → 제품 공개 | “그래서 모든 금융 정보를 건물에 대응시키는 일을 멈췄습니다.” |
| 설명 → 제안 | “상황을 알았다면, 이제 할 수 있는 일을 말해야 합니다.” |
| 제안 → 승인 | “다만 제안과 실행 사이에는 반드시 사용자가 있습니다.” |
| 작동 원리 → 2차 문제 | “여기서 캐릭터의 친근함만큼 주의해야 할 문제가 생깁니다.” |
| 안전장치 → 검증 | “이제 이 구조가 실제로 이해와 행동을 잇는지 확인할 차례입니다.” |
| 검증 → 결말 | “처음의 잔액 화면으로 돌아가 보겠습니다.” |

## 5. 발표 화면 규칙

1. 한 슬라이드에는 장면 하나와 질문 하나만 둔다.
2. 제품 공개 전에는 완성된 방과 전체 기능을 한꺼번에 보여주지 않는다.
3. 반전 뒤에는 `입력 → 계산 → 설명 → 선택 → 결과`를 움직임으로 보여준다.
4. 금융 숫자와 캐릭터 말풍선을 같은 화면에 두어 근거 관계를 끊지 않는다.
5. 슬라이드 8~14에는 `설계안`, 11에는 `모의 실행` 라벨을 계속 표시한다.
6. 승인 버튼을 보여줄 때는 대상, 금액, 시점도 함께 보여준다.
7. 첫 화면과 마지막 화면의 구도를 같게 만들고, 마지막에 행동 카드만 추가한다.
8. 통계나 외부 수치를 추가한다면 출처와 기준 시점을 화면에 함께 적는다.
9. 캐릭터가 사용자를 혼내거나 수익을 약속하는 장면은 쓰지 않는다.
10. 채널의 고유 문구와 시그니처 표현은 복제하지 않는다.

## 6. 발표에서 빼야 할 내용

- 초반 핵심 기능 전체 나열
- 캐릭터의 외형과 아이템 종류를 길게 설명하는 구성
- 결제 금액과 거래 횟수에 따른 보상
- 실제 금융기관 연동이 끝난 것처럼 보이는 화면
- AI가 잔액과 예산을 직접 계산하는 것처럼 들리는 설명
- 사용자의 승인 없이 송금이나 상품 가입을 실행하는 장면
- 상호명만으로 모든 소비 행동을 단정하는 연출
- 검증 전 목표를 달성 성과처럼 말하는 표현
- 앞 슬라이드를 다시 요약하는 별도 슬라이드

## 7. 30초 요약본

> “금융 앱에는 잔액과 소비와 일정이 이미 있습니다. 그런데 사용자는 그 숫자를 직접 해석하고 다음 행동까지 정해야 합니다. 그래프를 더 자세히 만들어도 이 간격은 남습니다. 소비를 도시로 바꾸면 예산 카테고리와 자유로운 꾸미기 규칙이 충돌합니다. 그래서 금융 정보는 카드에 남기고, 캐릭터를 금융 비서로 바꿨습니다. 소비가 반영되면 규칙으로 상태를 계산하고, 캐릭터가 쉬운 말로 설명한 뒤 필요한 행동을 제안합니다. 자금이 움직이는 일은 사용자가 승인한 경우에만 실행합니다.”

## 8. 질의응답 경계

### 기획안에서 답할 수 있는 질문

| 질문 | 답변 요지 |
|---|---|
| 캐릭터가 왜 필요한가 | 금융 상태를 쉬운 말로 설명하고 행동까지 이어 주는 인터페이스다. |
| 도시 방식은 왜 버렸나 | 예산 카테고리를 건물에 대응시키면 자유로운 꾸미기와 충돌하고, 도시 전체로 단순화하면 카테고리별 관리가 약해지기 때문이다. |
| AI가 잔액을 잘못 계산하면 어떻게 하나 | 잔액, 예산, 예정액은 규칙으로 계산한다. AI는 설명과 선택지만 만든다. |
| 캐릭터가 마음대로 송금하나 | 아니다. 대상, 금액, 시점을 보여주고 사용자가 승인한 행동만 실행한다. |
| 모든 결제가 캐릭터 행동으로 바뀌나 | 아니다. 분류가 명확한 일부 소비만 연결한다. |
| 과소비를 유도하지 않나 | 결제 금액이나 횟수에는 보상하지 않고 관리 행동에만 보상한다. |
| 실제 계좌가 연결되나 | MVP는 데모 데이터와 모의 실행으로 검증한다. 실제 연동은 범위 밖이다. |

### 아직 정하지 않은 질문

- 서비스명과 캐릭터명
- 실제 데이터와 금융기관의 연동 범위
- 분류 신뢰도 임계값과 사용자가 고친 뒤의 재계산 규칙
- 재화 지급량과 아이템 가격
- 개인정보의 구체적인 보관·삭제 정책
- 실제 송금 또는 자동이체 실행 방식
- MVP 정량 성공 기준

모르는 항목은 발표에서 정해졌다고 말하지 않는다.
