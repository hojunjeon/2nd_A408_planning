# 캐릭터 AI 금융비서 기획

작성일: 2026년 8월 30일

상태: 기획안

기준 원문: [Notion 「AI에이전트 캐릭터 서비스」](https://app.notion.com/p/AI-3caf938dd4cd80099859f3995c1a9792?source=copy_link)

## 1. 서비스 한 줄 정의

내 소비를 알아보고 필요한 금융 행동까지 챙기되, 실행 전에는 반드시 허락을 구하는 캐릭터형 AI 금융 비서.

## 2. 출발점

금융 앱에는 잔액, 소비 내역, 예산, 자동이체 일정이 이미 있다. 문제는 정보가 흩어져 있다는 점이다. 사용자는 숫자를 직접 읽고 현재 상황을 해석한 뒤, 무엇을 해야 할지 다시 판단해야 한다. 앱이 정보를 보여줘도 행동까지 이어지지 않는 이유다.

이 서비스는 숫자를 더 꾸미는 대신 그 사이를 잇는다. 캐릭터가 사용자의 금융 상태를 알아보고 쉬운 말로 설명한 뒤, 지금 필요한 행동을 제안한다. 중요한 행동은 사용자가 승인한 뒤에만 실행한다.

## 3. 핵심 사용자와 문제 가설

### 핵심 사용자

예산을 세우거나 소비를 관리하고 싶지만 숫자와 금융 용어를 매번 해석하는 일이 부담스러운 사용자다. 정확한 연령, 소득, 직업 범위는 아직 정하지 않았다.

### 해결할 문제

1. 사용자는 현재 쓸 수 있는 금액과 곧 빠져나갈 돈을 한눈에 알기 어렵다.
2. 소비 내역을 확인해도 다음 행동을 정하기 어렵다.
3. 금융 앱의 정보 화면과 사용자의 실제 행동 사이에 간격이 있다.
4. 일회성 알림만으로는 다시 들어올 이유와 관리 습관이 생기기 어렵다.

## 4. 제품 원칙

| 원칙 | 적용 방식 |
|---|---|
| 캐릭터는 금융 비서다 | 상태를 설명하고 다음 행동을 제안한다. 장식에만 머물지 않는다. |
| 금융 정보는 분리해서 보여준다 | 숫자와 일정은 카드에서 정확히 보여주고, 캐릭터는 그 의미를 설명한다. |
| 계산과 설명을 구분한다 | 잔액, 예산 소진률, 자동이체 예정액은 규칙으로 계산한다. AI는 계산 결과를 자연어로 풀고 선택지를 제안한다. |
| 실행 전에 묻는다 | 송금처럼 자금이 움직이는 행동은 대상, 금액, 시점을 다시 보여준 뒤 사용자가 승인해야 실행한다. |
| 모르면 단정하지 않는다 | 상호명만으로 소비 행동을 특정하기 어렵거나 데이터가 부족하면 캐릭터 행동과 억지로 연결하지 않는다. |
| 보상은 과소비를 부추기지 않는다 | 결제 금액이나 거래 횟수가 아니라 예산 확인, 점검, 절약 행동과 연결한다. |
| 설계안은 설계안이라고 밝힌다 | 데모와 발표에서 미구현 기능, AI 추론, 실제 실행 결과를 구분해서 표시한다. |

## 5. 도시 대신 캐릭터와 방을 택한 이유

도시 방식은 카테고리별 예산과 게임 요소를 같은 건물에 담으려다 규칙이 복잡해진다. 식비, 교통비, 쇼핑비를 각각 특정 건물로 표현하면 사용자가 원하는 건물을 자유롭게 배치하는 꾸미기와 충돌하고, 공용 재화로 아무 건물이나 사게 하면 각 건물이 어떤 예산을 뜻하는지 흐려진다. 반대로 도시 전체 상태로 단순화하면 핵심인 카테고리별 예산 관리가 약해진다.

캐릭터와 방 방식은 두 역할을 분리한다. 금융 정보는 카드에서 정확히 보여주고, 캐릭터는 그 정보를 설명하고 행동을 돕는다. 방과 액세서리는 지속적인 이용 동기를 담당한다. 예산 카테고리를 꾸미기 요소에 억지로 대응시키지 않아도 된다.

## 6. 핵심 경험

```text
소비 또는 예정된 지출 발생
→ 금융 상태 갱신
→ 캐릭터가 상황 인식
→ 쉬운 말로 설명
→ 필요한 행동 제안
→ 사용자가 승인·거절·보류
→ 승인된 행동만 실행
→ 결과 확인과 보상
→ 다음 점검으로 연결
```

캐릭터의 말은 항상 세 가지를 담는다. 무엇이 바뀌었는지, 왜 그렇게 판단했는지, 사용자가 무엇을 선택할 수 있는지다.

### 예시

> “현재 식비 예산이 얼마 남지 않았어요. 이번 주는 조금 아껴볼까요?”

> “오늘 새롭게 들어온 결제 내역이 있어요. 함께 확인할까요?”

> “며칠 뒤 자동이체가 예정되어 있어요. 미리 출금 계좌로 돈을 옮겨둘까요?”

위 문장은 원문의 사용 장면을 바탕으로 쓴 예시다. 실제 서비스에서는 각 말풍선 옆에 기준 데이터와 갱신 시점을 함께 표시한다.

## 7. 정보 구조

### 홈

한 화면에 캐릭터, 방, 금융 상태 카드를 둔다. 캐릭터는 오늘 확인해야 할 한 가지를 말한다. 금융 상태 카드가 담는 항목은 8.1에 정리했다.

### 소비 내역

최신 결제 내역과 자동 분류 결과를 보여준다. 사용자는 분류가 틀리면 직접 고칠 수 있어야 한다. 이 수정 방법과 수정 뒤 재계산 규칙은 상세 설계가 필요하다.

### 코칭

행동 판단에 필요한 내용만 8.5의 기준으로 보여준다. AI의 설명과 규칙 계산값은 구분해서 표시한다.

### 꾸미기

금융 활동으로 얻은 재화로 액세서리와 방 꾸미기 요소를 산다. 현금 구매 여부와 구체적인 재화 규칙은 MVP 검증 뒤 정한다.

## 8. 기능 정의

### 8.1 자산 상태 가시화

- 현재 예산 잔액
- 카테고리별 예산 상태
- 고정지출과 자동이체 예정 내역
- 최근 소비 내역
- 월 소비 진행 상황

표시 순서는 총액보다 행동 가능성을 먼저 고려한다. 예를 들어 계좌 잔액만 보여주지 않고 다음 자동이체를 뺀 뒤 실제로 쓸 수 있는 금액을 함께 보여준다.

### 8.2 소비와 캐릭터 행동 연동

모든 결제를 행동으로 바꾸지 않는다. 상호명과 업종이 명확한 일부 소비만 캐릭터의 짧은 행동으로 표현한다.

| 결제 예시 | 캐릭터 행동 |
|---|---|
| 카페 | 커피 마시기 |
| 음식점 | 음식 먹기 |
| 영화관 | 영화 보기 |
| 쇼핑 | 쇼핑백 들기 |

결제 내역은 배치로 갱신할 수 있다. 사용자가 나중에 접속해도 최근 소비가 반영된 상태를 확인한다. 분류 신뢰도가 낮으면 기본 대기 동작을 유지하고 소비 카드만 갱신한다.

### 8.3 상태별 모션과 말투

캐릭터의 상태는 전날 소비와 예정된 지출에 따라 달라진다. 다만 사용자를 꾸짖거나 과장해서 칭찬하지 않는다.

| 상태 | 표현 원칙 | 예시 방향 |
|---|---|---|
| 안정 | 차분한 표정과 짧은 확인 | “이번 주 식비는 계획 안이에요.” |
| 주의 | 원인과 회복 경로를 함께 제시 | “카페 지출이 늘었어요. 남은 기간 하루 평균 금액을 확인할까요?” |
| 실행 필요 | 예정일, 금액, 행동을 분명히 제시 | “3일 뒤 자동이체가 있어요. 부족한 금액을 옮길까요?” |
| 데이터 부족 | 추측하지 않고 확인 요청 | “이 결제는 분류하기 어려워요. 어디에 쓴 금액인지 알려주세요.” |

전날 소비를 반영하는 장면은 다음처럼 제한한다.

| 트리거 | 모션 | 멘트 방향 |
|---|---|---|
| 카페 결제가 확정됨 | 커피를 한 모금 마심 | 최근 카페 지출과 예산 잔액을 함께 알림 |
| 음식점 결제가 확정됨 | 식탁에 앉음 | 최근 식비와 남은 기간을 함께 알림 |
| 자동이체 예정액이 가용 금액보다 큼 | 달력과 지갑을 번갈아 확인함 | 예정일, 부족 예상액, 준비 행동을 제안 |
| 분류 신뢰도가 낮음 | 영수증을 살펴봄 | 추측하지 않고 사용자가 분류하도록 요청 |

모션은 상황을 알아차리게 하는 보조 표현이다. 분노, 비난, 과장된 부의 약속은 사용하지 않는다.

### 8.4 금융 상태 계산

AI가 금액을 자유롭게 계산하지 않도록 입력 상태와 계산 규칙을 먼저 고정한다.

| 결과 | 규칙 | 표시 방식 |
|---|---|---|
| 확정 예산 잔액 | 확정 예산에서 확정 결제를 뺀다. | 기준 시점과 함께 표시한다. |
| 예상 예산 잔액 | 확정 예산에서 확정 결제와 승인 대기 결제를 뺀다. | `예상` 라벨을 붙인다. |
| 카테고리 소진률 | 확정 결제를 사용자가 확정한 카테고리 예산으로 나눈다. | 예산이 없으면 판정하지 않는다. |
| 일정 반영 가용 금액 | 현재 잔액에서 아직 잔액에 반영되지 않은 승인 대기 출금과 선택 기간의 예정 지출을 뺀다. | 이미 잔액에 반영된 금액은 다시 빼지 않는다. |
| 예산 소진 예상일 | 확정 결제의 일평균 속도를 남은 예산에 적용한다. | 월초나 데이터가 부족하면 예상일을 내지 않는다. |

모든 값에는 데이터 갱신 시점과 `확정·예상·미확정` 상태를 붙인다. 승인 대기 결제의 포함 여부는 데이터 제공처의 상태값으로 정하며, 같은 금액을 두 번 차감하지 않는다.

### 8.5 AI 코칭

AI 코칭은 계산값을 새로 만들지 않는다. 검증된 데이터와 규칙 계산 결과를 보고 설명과 선택지를 만든다.

```text
거래·예산·일정 데이터
→ 규칙 계산
→ 근거가 붙은 상태 객체
→ AI 설명과 행동 후보
→ 사용자 확인
```

코칭 예시는 다음과 같다.

- 이번 달 카페 지출의 전월 대비 변화 설명
- 현재 소비 속도로 본 예산 소진 예상일 안내
- 목표 예산을 맞추기 위한 남은 기간의 조정안 제시
- 자동이체 예정액을 반영한 현재 가용 금액 안내

### 8.6 금융 행동 제안과 승인

캐릭터는 행동을 먼저 실행하지 않는다. 제안 카드는 최소한 다음 항목을 보여준다.

- 행동 대상
- 금액
- 실행 시점
- 제안 근거
- 실행 뒤 예상 상태
- 승인, 거절, 나중에 결정

실제 금융기관 연동이 없는 프로젝트 단계에서는 실행을 시뮬레이션하거나 사용자의 직접 실행을 기록한다. 연동되지 않은 행동을 완료로 표시하지 않는다.

### 8.7 보상과 성장

사용자는 금융 활동으로 재화를 얻고 캐릭터의 액세서리나 방 꾸미기 요소를 산다. 재화 지급은 다음 행동과 연결한다.

- 예산을 확인하고 확정하기
- 주간 소비를 점검하기
- 필요한 금융 행동을 검토하기
- 절약 목표를 달성하기
- 자동이체를 미리 준비하기

결제 금액, 결제 횟수, 투자 횟수에는 보상을 주지 않는다. 캐릭터 성장은 금융 행동을 더 자주 하게 만드는 장치가 아니다. 사용자가 자신의 상태를 이해하고 관리한 기록이 쌓이도록 설계한다.

제안을 승인했는지는 보상 조건으로 삼지 않는다. 승인, 거절, 보류 중 무엇을 선택해도 제안을 충분히 검토했다면 같은 점검 보상을 한 번만 받는다. 같은 제안이나 같은 기간의 점검으로 보상을 반복해서 받지 않도록 제안 식별자와 지급 이력을 기록한다.

## 9. 핵심 사용자 여정

| 단계 | 사용자 행동 | 서비스 동작 | 캐릭터의 역할 | 완료 조건 |
|---|---|---|---|---|
| 온보딩 | 데이터 연결 범위와 예산을 확인한다 | 최근 소비와 예정 지출을 정리한다 | 첫 상태를 설명하고 틀린 정보를 고치게 한다 | 사용자가 데이터 범위와 예산을 확인함 |
| 일일 확인 | 홈에서 캐릭터와 금융 상태를 본다 | 새 소비와 일정을 갱신한다 | 오늘 확인할 한 가지를 말한다 | 사용자가 상태를 이해함 |
| 소비 반영 | 결제 내역을 확인한다 | 분류하고 예산 상태를 다시 계산한다 | 명확한 소비만 행동으로 표현한다 | 분류 또는 미확정 상태가 기록됨 |
| 코칭 | 제안의 근거와 선택지를 본다 | 규칙 계산값으로 행동 후보를 만든다 | 쉬운 말로 설명하고 선택을 기다린다 | 승인·거절·보류 중 하나를 선택함 |
| 실행 | 승인 내용을 다시 확인한다 | 승인된 행동만 실행하거나 기록한다 | 결과를 정확히 알린다 | 성공·실패·미실행이 구분됨 |
| 보상 | 받은 재화를 사용한다 | 금융 행동 기록에 맞춰 재화를 지급한다 | 캐릭터와 방이 변한다 | 보상 지급 근거가 기록됨 |
| 회고 | 주간 또는 월간 변화를 확인한다 | 소비, 예산, 행동 결과를 묶어 보여준다 | 다음에 고칠 한 가지를 제안한다 | 다음 점검 행동이 정해짐 |

## 10. 제품 비전과 MVP 경계

완성된 서비스는 사용자가 승인한 금융 행동을 실제로 수행하는 것을 목표로 한다. 다만 실제 금융기관 계좌에서 자금을 움직이려면 연동 방식, 권한, 동의 절차와 법적 범위를 먼저 확정해야 한다.

프로젝트 MVP는 합성한 데모 소비 내역, 사용자가 정한 예산, 가상의 자동이체 일정을 사용한다. 실제 개인 금융 데이터를 불러오지 않으며 실제 계좌와 연결하지 않는다. 실행 단계는 샌드박스가 제공될 때만 샌드박스 응답을 사용하고, 그 외에는 `모의 실행`으로 표시한다.

## 11. MVP

MVP에서는 아래 한 가지 루프를 끝까지 연결한다.

```text
데모 소비 데이터 반영
→ 예산 상태 계산
→ 캐릭터 설명
→ 자동이체 준비 행동 한 건 제안
→ 승인·거절
→ 모의 실행 결과
→ 보상 지급과 방 변화
```

### 포함

1. 캐릭터와 방이 있는 홈
2. 현재 예산 잔액, 카테고리별 상태, 예정 지출 카드
3. 최근 소비 배치 반영
4. 명확한 소비 네 종류의 캐릭터 행동
5. 규칙 계산을 근거로 한 AI 설명
6. 행동 제안과 승인·거절·보류
7. 모의 실행 결과
8. 재화 지급과 액세서리 또는 방 꾸미기 한 종류

### 제외

- 실제 금융기관 계좌에서 자금 이동
- 투자 종목 추천과 자동 매매
- 모든 상호명을 캐릭터 행동으로 바꾸는 범용 분류
- 여러 캐릭터, 복잡한 세계관, 소셜 랭킹
- 현금 결제형 재화와 대규모 아이템 상점
- 장기 예측과 정교한 자산 배분

## 12. 데이터와 안전 경계

| 구분 | 화면 표시 | 처리 원칙 |
|---|---|---|
| 원천 사실 | 결제 금액, 일시, 예산, 예정 지출 | 수정하지 않고 기준 시점을 표시한다. |
| 규칙 계산 | 잔액, 소진률, 가용 금액, 부족 예상액 | 계산식을 고정하고 테스트한다. |
| AI 해석 | 소비 변화 설명, 행동 선택지 | 추론임을 표시하고 근거 링크를 제공한다. |
| 사용자 승인 | 승인·거절·보류, 대상, 금액, 시점 | 승인 기록을 남기고 중복 실행을 막는다. |
| 실행 결과 | 성공·실패·미실행 | 응답 결과를 그대로 표시하고 성공을 추정하지 않는다. |

실제 금융 데이터 사용 전에는 개인정보 수집 목적, 보관 기간, 삭제와 동의 철회, 접근 권한, 로그 정책을 별도로 확정해야 한다. 실제 송금이나 금융상품 추천으로 확장할 때는 관련 법률과 금융기관 연동 방식을 먼저 검토한다.

## 13. 검증 계획

정량 목표치는 사용자 조사와 기준값 확인 뒤 정한다. MVP에서는 다음 질문에 답한다.

| 검증 질문 | 관찰 지표 |
|---|---|
| 캐릭터 설명이 현재 금융 상태를 이해하는 데 도움이 되는가 | 상태 확인 뒤 이해도, 재설명 요청률 |
| 제안의 근거가 충분히 보이는가 | 제안 상세 열람률, 근거 확인률 |
| 사용자가 승인과 실행을 구분하는가 | 승인 화면 오인율, 실행 결과 오인율 |
| 소비 행동 연동이 재방문 이유가 되는가 | 최근 소비 반영 뒤 재방문율, 캐릭터 행동 확인률 |
| 보상이 과소비를 유도하지 않는가 | 보상 전후 결제 횟수·금액의 비정상 변화 |
| 캐릭터가 금융 판단을 과도하게 대신한다고 느끼지 않는가 | 과신 응답, 제안 거절 가능성 인지율 |

승인 없는 실행 건수와 실행 결과 오인 건수는 0건을 지켜야 하는 안전 지표다.

## 14. 주요 리스크와 대응

| 리스크 | 대응 |
|---|---|
| 친근한 캐릭터 때문에 AI를 과신함 | 데이터 근거, 기준 시점, 추론 여부를 함께 표시한다. |
| 잘못된 소비 분류가 잘못된 코칭으로 이어짐 | 낮은 신뢰도는 미확정으로 두고 사용자가 고치게 한다. |
| 캐릭터의 반응이 사용자를 비난함 | 중립적인 표현과 회복 행동을 함께 제시한다. |
| 보상이 과소비나 불필요한 거래를 유도함 | 관리 행동에만 보상하고 소비량·거래량은 보상하지 않는다. |
| 실제 연동처럼 보이는 데모가 오해를 만듦 | 모든 모의 화면에 `설계안` 또는 `모의 실행`을 표시한다. |
| 승인 뒤 실행이 중복됨 | 실행 식별자와 최종 상태를 기록하고 같은 요청을 다시 실행하지 않는다. |

## 15. 미확정 항목

- 서비스명과 캐릭터명
- 핵심 사용자의 연령과 생활 조건
- 실제 데이터 연동 범위
- 실제 송금이나 자동이체 실행 여부
- 소비 분류 신뢰도 기준과 사용자 수정 뒤 재계산 규칙
- 재화 획득량, 가격, 초기화 규칙
- 캐릭터 모션과 말투의 구체 기준
- 개인정보 보관 기간과 삭제 정책
- MVP 성공 기준의 목표 수치

## 16. 한 문장 결론

이 서비스의 캐릭터는 소비를 보여주는 마스코트가 아니다. 사용자의 금융 상태를 읽고 설명하며, 필요한 행동을 제안하고, 허락받은 일만 수행하는 AI 금융 비서다.
