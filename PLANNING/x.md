# x — 청년 정책·세제·예적금·대출 상환 결합 미래 자산 시뮬레이션

기준일: 2026-08-23(Asia/Seoul) / 대상: SSAFY 팀·심사위원 / 구현 조건: 기획기간 제외 6인 5주

## 0. 한눈에 보는 제품

### 한 문장 정의

청년이 자신의 소득·거주·부채 상태를 입력하면, 정책 지원금과 세제 혜택, 예적금 이자, 대출 이자비용을 같은 월별 타임라인 위에서 계산해 "언제 무엇을 시작하고 갚을지"를 가정 기반 시나리오로 비교해 주는 앱이다.

### 사용자 행동 → 앱 처리 → 결과

| 단계 | 사용자 행동 | 앱 처리 | 결과 |
| --- | --- | --- | --- |
| 진단 | 나이·지역·소득·주거·부채·목표를 입력 | 프로필을 정책/세제/상품 규칙 스냅샷과 대조 | 신청 가능·불가·조건부 항목과 놓치는 항목 목록 |
| 설계 | 월 저축 가능액과 목표 시점을 설정 | 현금흐름 모델에 정책 수혜·세후 이자·대출 상환을 배치 | 월별 잔액·자산·부채·순자산 타임라인 |
| 비교 | 시나리오(예: 즉시 적금 vs 먼저 부분상환)를 선택 | 동일 가정으로 두 경로의 세후수익·이자비용·수혜액 재계산 | 만기 순자산 차이와 원인 분해 |
| 행동 | 추천 시점 카드 확인 | 계산 근거·출처·갱신일·불확실성 표시 | 다음 분기에 실행할 행동과 유지 조건 |

본 문서는 예측 서비스가 아니라 **가정 기반 시나리오 비교 도구**를 기획한다. 금리·정책 조건은 확정값으로 고정하지 않고 사용자 입력 또는 갱신 가능한 스냅샷 변수로 둔다.

## 1. 문서 구조와 채택 이유

실제 공개 자료에서 구조가 확인된 네 방법론을 결합했다. Working Backwards는 고객 혜택을 기술보다 먼저 검증하는 5개 질문과 PR/FAQ 흐름을 제공하고(AWS 발표자료, 2019; 확인일 2026-08-23; B), Intercom Job Story는 상황-동기-결과를 분리해 기능 요청을 사용자 목적으로 바꾼다(2016-06-28; B). Atlassian PRD는 목표·성공지표·가정·범위 외 항목으로 구현 가능성을 묶고(확인일 2026-08-23; B), GOV.UK Service Standard는 전체 여정·단순성·성과지표·기술 선택·보안을 함께 요구한다(확인일 2026-08-23; B).

채택 결과는 다음과 같다.

1. PRFAQ식 고객 질문으로 문제와 최소 솔루션을 검증한다(제2장).
2. Job Story로 핵심 기능을 파생한다(제3장).
3. Atlassian식 목표·가정·범위 외로 MVP를 고정한다(제5~7장).
4. GOV.UK식 전체 여정·성공지표·보안으로 데모와 운영 안전장치를 검증한다(제4·8장).

이름 나열이 아니라, "사용자가 어떤 결정을 더 잘하게 되는가"를 먼저 확인한 뒤 계산 엔진과 UI를 붙이는 순서를 채택한 것이다. 금융 계산 화면은 공공 계산기들이 초기값→납입/기간→수익률 범위→복리 빈도를 단계로 받는 패턴과, 제출 전 입력을 key-value로 검토하는 Check Answers 패턴을 따른다(Investor.gov Compound Interest Calculator, 확인일 2026-08-23; B / GOV.UK Design System, 확인일 2026-08-23; B). SEC 자동화 금융도구 안내처럼 방법론·핵심 가정·한계를 노출한다(Investor.gov Investor Alert, 2015-05-08; B).

### 2.2 WHY A — 왜 이 문제를 이 솔루션으로 푸는가

- 청년의 실제 결정은 "어떤 정책이 좋은가", "어떤 예적금이 좋은가", "언제 대출을 갚아야 하는가"가 따로 오지 않는다. 월급날에는 저축과 상환과 신청 마감이 동시에 경쟁한다.
- 개별 계산기는 이미 존재하므로, 부족한 것은 네 축을 같은 달력과 같은 가정 위에 놓고 교환관계를 보여주는 것이다. 예: 정책 수혜 30만원을 적금에 넣을지, 학자금대출 의무상환 선납에 쓸지는 세후 이자와 이자비용·유예 조건을 함께 계산해야만 답할 수 있다.
- 따라서 개념적 솔루션은 "추천 상품 나열"이 아니라 **규칙 스냅샷 + 현금흐름 + 결정론적 시뮬레이션 + 가정 노출**이다. LLM은 계산자가 아니라 설명자로 제한한다.

### 2.3 PRFAQ식 고객 FAQ

**Q1. 누구를 위한 제품인가?** 20~34세의 대학생·취준생·사회초년생·부채 보유 청년 중, 정책·세제·상품·부채를 한 번에 판단해야 하는 사람이다.

**Q2. 무엇을 해결하는가?** "이번 달 돈을 어디에 두고, 무엇부터 신청하고, 언제 얼마를 갚을지"를 스스로 계산하기 어려운 문제다.

**Q3. 가장 중요한 고객 혜택은?** 네 축이 섞인 선택지를 만기 시점 순자산과 월 현금흐름으로 비교해, 다음 분기 행동을 고르게 하는 것이다. 절대적 수익 보장이 아니다.

**Q4. 어떻게 아는가?** 위 문제 근거 표와, 공개 계산기·정책 플랫폼이 분절되어 있다는 공식 페이지 관찰로 뒷받침한다. 로그인 내 경쟁 기능과 전체 시장은 UNVERIFIED로 남긴다.

**Q5. 경험은 어떤 모습인가?** 3분 진단 → 가정 확인 → 시나리오 비교 → 다음 행동 저장. 결과 화면에는 항상 출처·갱신일·오차 범위가 함께 보인다.

## 3. 핵심 기능과 WHY

### 기능 F1 — 규칙 스냅샷 기반 정책·세제 진단

- 내용: 온통청년 API에서 수집한 정책 메타데이터를 원문·확인일·시행기간과 함께 저장하고, 사용자 프로필로 자격을 조건 매칭한다. 세제 항목은 월세 세액공제(17%/15%, 연 1천만원 한도), 연금저축 600만원·연금저축+IRP 등 900만원 한도와 12~15% 공제율을 규칙 레코드로 둔다.
- 출처: https://www.data.go.kr/data/15143273/openapi.do (수정일 2025-05-09; A), https://www.law.go.kr/LSW/lsLawLinkInfo.do?chrClsCd=010202&lsJoLnkSeq=1000027473 (시행 2026-01-01; A), https://j.nts.go.kr/nts/cm/cntnts/cntntsView.do?cntntsId=7875&mi=6596 (확인일 2026-08-23; B).
- WHY B: 사용자가 필요한 첫 정보는 "지금 신청 가능한가"와 "얼마나 받는가"다. 진단이 없으면 시뮬레이션 입력 자체가 생긴다. 중복수혜·우선순위는 정책 레코드의 조건 필드로 처리한다.
- WHY C: API 메타데이터와 법령 조문은 구조화된 데이터라 규칙 엔진으로 매핑하기 적합하다. LLM이 자격을 판정하게 하면 출처·시행기간 추적이 깨진다.

### 기능 F2 — 결합 현금흐름 시뮬레이션 엔진

- 내용: 월별로 정책 수혜, 세후 이자, 세액공제 환급, 대출 이자·상환을 하나의 잔액 모델에 합산한다. 적금은 월납입×연이율×기간 후 15.4% 일반 과세(또는 사용자 지정 비과세/특례), 대출은 원리금균등·원금균등·소득연계(학자금)를 지원한다.
- 계산식:

```text
적금 세전이자(월초 납입 근사) = M × (r/12) × N(N+1)/2
적금 세전이자(월말 납입 근사) = M × (r/12) × N(N-1)/2
세후 이자 = 세전 이자 × (1 - 세율)

원리금균등 PMT = iA / (1 - (1+i)^(-N))
n회차 이자 = 직전잔액 × i, n회차 원금 = PMT - 이자

원금균등 C = A / N
n회차 이자 = [A - C(n-1)] × i

학자금 소득연계 = 소득 ≤ 상환기준소득이면 유예,
                  소득 > 기준이면 (소득 - 기준) × 상환율을 의무상환으로 반영
```

- 출처: https://extension.colostate.edu/resource/long-term-loan-repayment-methods/ (reviewed 2025-08; A), https://www.law.go.kr/lsLinkCommonInfo.do?lsJoLnkSeq=1017632265 (시행 2026-07-01; A), 교육부 학자금 고시(시행 2026-07-01; A).
- WHY B: 사용자의 선택은 단일 상품의 절대 수익이 아니라 "같은 돈을 어디에 두느냐"의 상대 비교다. 현금흐름을 하나로 묶어야 정책 수혜→저축 vs 부분상환의 교환관계가 드러난다.
- WHY C: 위 식들은 입력이 같으면 결과가 같은 결정론적 함수다. Decimal과 PostgreSQL numeric으로 구현하면 재현성과 감사가 가능하다(https://docs.python.org/3/library/decimal.html, 확인일 2026-08-23; B / https://www.postgresql.org/docs/current/datatype-numeric.html, 2026-08; B).

### 기능 F3 — 상환 기간·시기 시나리오 비교

- 내용: 대출별 잔액·금리(APR 별도 입력)·중도상환수수료·상환방식·유예조건을 입력받아, (a) 약정 유지 (b) 정책수혜로 부분중도상환 (c) 적금 우선 후 만기 일시상환 (d) 학자금 유예 유지 중 자발적 상환 시나리오의 월별 총이자·잔액·순자산을 비교한다.
- 출처: 중도상환수수료 실비용 산정체계 시행(https://fsc.go.kr/no010101/83833, 2025-01-09 게시/2025-01-13 시행; B), 금융소비자보호법상 상환시기 설명 의무(법령 시행 2026-01-02; A), APR·선납 페널티 개념(CFPB, 확인일 2026-08-23; B).
- WHY B: "얼마를 빌렸나"보다 사용자가 못 고르는 것은 "언제 갚느냐"다. 시나리오 비교는 상환시점의 기회비용을 숫자로 만든다.
- WHY C: 상환 스케줄은 회차별 반복 계산이라 결정론적 엔진이 정확히 다루는 영역이며, 중도상환수수료는 상품별 약관 변수로 사용자 입력에 남긴다.

### 기능 F4 — 가정·출처 노출형 시나리오 UI

- 내용: 입력은 한 화면 한 질문으로 나누고, 제출 전 Check Answers 요약을 보여준다. 결과는 기준/보수/낙관 범위, 원금·수혜·이자·세금 분해, "가정 보기"(금리·세율·출처·갱신일·일수기준·반올림)를 함께 표시한다.
- WHY B: 금융 결과는 입력 가정에 민감하므로, 가정이 보이지 않으면 사용자가 예측으로 오해한다. 범위와 분해는 "왜 이 결과가 나왔는가"를 설명하는 최소 장치다.
- WHY C: 단계형 질문·Check Answers·Error Summary는 공식 디자인 시스템 패턴으로 검증되어 있고, SEC는 자동화 도구에 방법론·가정·한계 명시를 요구한다(GOV.UK Design System, 확인일 2026-08-23; B / Investor.gov, 2015-05-08; B).

### 기능 F5 — AI 설명 계층(계산 권한 없음)

- 내용: LLM은 자연어 입력을 구조화 필드로 변환하고, 계산 결과 JSON을 받아 "왜 차이가 났는가"를 요약한다. 금액·세율·자격·스케줄을 생성하거나 수정하지 못한다.
- WHY B: 사용자가 멈추는 지점은 계산 자체보다 용어와 원인 해석이다. 그러나 정책 판정을 LLM에 맡기면 출처 추적이 불가능하다.
- WHY C: NIST AI RMF는 투명성·설명가능성을 요구하고, ASOP/Fed 모델 리스크 지침은 가정·재현성·독립 검증을 요구한다. 결정론적 코어와 AI 설명을 분리하면 둘 다 충족된다(https://airc.nist.gov/airmf-resources/airmf/3-sec-characteristics/, 2023; A / https://www.actuarialstandardsboard.org/asops/modeling/, 2020-10-01 효력; A).

데모의 X·Y는 사전 등록된 시나리오 데이터에서 계산기가 산출한 값으로 채운다. 발표용 수치를 사전에 하드코딩하지 않고, 같은 엔진 호출 결과를 보여준다.

## 7. 데이터 모델·계산식·아키텍처

### 7.1 데이터 모델(PostgreSQL)

```text
policies(id PK, source_url, policy_code, title, eligibility jsonb,
         benefit_rule jsonb, effective_from date, effective_to date,
         exclusions text[], priority int, fetched_at timestamptz, raw_doc jsonb)
tax_rules(id PK, rule_type, year, condition jsonb, rate numeric,
          limit_amount numeric, source_url, verified_at date)
products(id PK, type, name, issuer, base_rate numeric, preferential_rule jsonb,
         tax_treatment, term_months int, max_monthly numeric, source_url,
         verified_at date, is_variable bool)
loans(id PK, user_id FK, kind, principal numeric, apr numeric,
      nominal_rate numeric, term_months int, method enum,
      grace_rule jsonb, prepay_fee_rule jsonb, start_date date)
profiles(id PK, age, region_code, income_monthly numeric, asset numeric,
         housing_status, employment_status, dependents int, goal jsonb)
simulations(id PK, profile_id FK, assumptions_hash, scenario_set jsonb,
            result_summary jsonb, engine_version, created_at)
audit_logs(id PK, simulation_id FK, input_snapshot jsonb,
           rule_snapshot jsonb, output_hash, created_at)
```

금액 컬럼은 `numeric`, 규칙은 `jsonb`로 원문 필드를 보존한다. PostgreSQL은 정확성이 필요한 값에 numeric을 권장한다(https://www.postgresql.org/docs/current/datatype-numeric.html, 2026-08; B).

### 7.2 계산 흐름

1. 프로필 정규화 → 자격 규칙 매칭 → 수혜 스케줄 생성.
2. 상품 스케줄 생성(적금 납입·세후 이자, 대출 회차표).
3. 세제 반영(월세 공제 환급 시점, 연말정산 환급 월 분할 가정).
4. 월별 집계: `순자산(t) = 현금 + 저축잔액 + 정책수혜누적 - 대출잔액`.
5. 시나리오 차이 분해: `Δ순자산 = Δ수혜 + Δ세후이자 - Δ이자비용 - Δ수수료 - Δ세금`.

### 7.3 아키텍처

```text
[Android App RN/Expo]
   ├─ REST ─▶ [FastAPI 계산·조회] ─▶ PostgreSQL(numeric/jsonb)
   │                 ▲                    ▲
   └─ LLM 설명 요청 ─▶ [LLM Adapter]     │
                        │(스키마 강제)    │
[Spring Boot Batch] ────┴─ 정책/세제/상품 스냅샷 수집 ─▶ S3 원문 보관
```

LLM은 계산 엔진 출력만 받아 설명한다. 정책 판정·금액 생성 권한이 없으므로, LLM 출력이 스키마를 벗어나면 거부한다.
